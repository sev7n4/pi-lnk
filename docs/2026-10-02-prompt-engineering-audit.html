01结论摘要

先说结论：这个项目的提示词工程处于「能跑、有意识、但没体系」的阶段。 上下文-engineering 层面做得比大多数团队好（静态/动态分治、不污染历史、CJK 感知的 token 估算、 byte-stable 截断、信任边界标注），但「提示词本身作为产品资产」的管理维度基本空白—— 没有单一权威源、没有版本、没有回归集、没有一个-pass 的 eval。这直接解释了一个反复出现的现象： 你们已经两次证明了「模型能逐字复述指令，但不会照做」（load_tools 触发率 0）。 那不是模型问题，是提示词工程的结构性问题。

04P0 缺口：不做的话，后面所有优化都不可验证

P0-1没有提示词评测体系 —— 改一个标点不知道线上变好还是变差
现象
全仓不存在任何 eval harness、黄金集、judge 脚本。提示词的「测试」只有单元测试里的字符串包含断言（expect(createOpts.systemPrompt).toContain('⟦plan⟧')）——它只证明文本拼进去了，完全不证明模型会不会照做。
后果
这直接解释了 load_tools 触发率 0 这个现象：你们已经两次观测到「模型能逐字复述指令却不调用」，但没有任何机制能定量回答「改了文案之后触发率有没有上升」。于是每次改动都是拍脑袋 + 线上猜。
建议
先建两层的 eval：
  • L1 行为回归集（离线，CI 可跑）：≥30 条 case，每条 = { 用户话术, 画布初始态, 期望：调用了哪些工具 / 没调用哪些 / 是否先复述 / 是否问澄清 }。用 LLM-judge 打 pass@1，阈值门作成 CI 硬闸。
  • L2 在线指标：load_tools/load_skill 触发率、澄清率、每个 turn 的工具调用步数分布、规则违反计数器（见 P0-3）。
首批 case 应直接来自线上真实失败样本（"只看到文件名"、"挡 Repo 蝴蝶文件内容 RW"、假称已出图），不要自造。
P0-2规则文本是「逐字考古」而非「为模型重写」
证据
规则 4 原文 911 字符，内含 ≥9 个动作 + 3 个反例 + 2 个例外分支；规则 5 同理。注释明写「explore.py:95-112 逐字拷贝（含无空格拼接点）」pi-prompt-assembler.service.ts:108-114。注入顺序是 1,2,3,7,14,4,5,11,12,13，而编号上限已经到 14 :131-140。
后果
① 编号跳跃会削弱模型对「规则清单」的整体遵从先验；② 一条规则里的 9 个约束互相竞争注意力，最靠后的（往往是例外/反例）最先被丢，而反例恰恰是最贵的那条；③ 注释里那句「含无空格拼接点」是逐字考古留下的痕迹——CJK 与拉丁字符之间不加空格，会让 tokenizer 切分质量下降，进而影响规则文本的语义完整性。
建议
做一次规则原子化重写：
  • 每条规则 = 一个动词 + 一个条件，中文 ≤ 30 字；一条不够就拆两条，编号连续。
  • 用 XML 分区承载语义：<identity> / <capability> / <rules> / <negative_examples> / <output_format> / <workflow>。
  • 把散落在规则 4/5/7 里的反例抽到统一的 <negative_examples> 段并配正向替代（"不要 X → 改为 Y"）。
  • 重写必须锁版本 v1，并与 P0-1 的回归集同时上线（没有 eval 就不要重写）。
P0-3提示词没有版本号，没有一处能被生产回答「这一轮用的是哪版提示词」
证据
PromptManifest 算了 promptHash（sha256 前 12 位）与分层 token， 但只喂给了 Nest 的 Logger（this.logger.log(this.lastManifest)） pi-prompt-assembler.service.ts:209-224。
production 侧 metrics.ts 有 system_prompt_bytes / dynamic_budget_* / transform_context_*，唯独没有 prompt version / hash 指标，也没写进会话 meta.json。
后果
线上出一次「假称已出图」事故，事后无法回答「那批请求用的是不是同一版提示词」，回溯链条断在最关键一环。这也让 A/B 完全不可行。
建议
三件事，都很小：
  • 静态段常量加 PROMPT_VERSION = "2026.10.02-1"，随 createSession 一起传下去。
  • pi-runtime 暴露 gauge pi_runtime_prompt_info{version,hash} 1（BuildInfo 同款写法）。
  • writeSessionMeta 里落 promptVersion + promptHash，磁盘 resume 时校验不一致要 warn。
P0-4工具 schema 是上下文最大的消费者，却不在任何一个预算口径里
证据
常驻工具 30 个通通送 full JSON Schema tiering.ts:22-60； dynamic-budget.ts 的预算只作用于 dynamicBlocks（48k 字）与 mentions etc，对工具 schema 完全无感； metrics 里也没任何 tool-schema 相关的 token 度量。
后果
① 每轮固定成本居高不下、prompt cache 的前缀稳定性被拖累； ② BYOK 场景致命：DEFAULT_CONTEXT_WINDOW = 128_000、用户可以自带 8k 窗口模型 model-assembly.ts:129-131，8k 窗口下「1.9k 字规则 + 3k 字索引 + 30 个 schema + 动态块」必然爆窗， 而系统对此没有任何降级策略。
建议
  • 先把 tool schema token 纳入审计口径（估算值 each turn → gauge），别急着优化都不知道优化了多少。
  • 按 contextWindow 分档的提示词分级降级：≥64k 全量 / 16–64k 去 skills 索引+去 genTools 规则组 / <16k 只留 ≤10 个最小工具集。
  • ALWAYS_ON 再做一轮「真高频」裁剪：arrange_nodes 等被 skill 点名的工具进常驻理由充分，但 6 个 run_* 是否都需要常驻，拿工具调用频次数据说话（目前没有任何频次指标）。

05P1 缺口：直接决定 agent 的可用性与一致性

P1-1人格与语气层缺失 —— 全系统只有一句「用简洁中文回答」
证据
CORE_RULES_PREFIX pi-prompt-assembler.service.ts:89-92 是唯一的身份/风格定义。
后果
没有定义：回复长度、是否复述用户意图、是否汇报进度、Markdown 用法、进度时怎么说话、 失败时怎么说话、是否用称谓/表情、中文还是中英混排。结果就是同一个用户的两轮对话，agent 的"人格"可能完全不同。 尤其「多步任务」场景下（你们已经有 ⟦plan⟧ 机制），缺了 "plan 之外我也简短地告诉你在干嘛" 的约定，用户体验全靠模型随机发挥。
建议
补三段固定总字数的 <identity> / <style> / <output_format>， 并明确 「先一句话交代要做什么 → 调工具 → 一句话汇报结果」 的默认节奏（与 QUEUE_GUIDANCE 呼应，形成统一语态）。
P1-2纯禁令体 —— 只说不许做什么，几乎不说该做什么
证据
规则文本里「禁止 / 不得 / 不要 / 别」高频出现，缺少对应的正向替代动作。典型案例是规则 7 的 「禁止问『I1 对应画布哪张图』」，但没有告诉模型那遇到这种情况到底应该说什么。
后果
禁令型指令只能学到「回避」，模型在遇到未覆盖情形时会自由发挥而不是做保守的事。 这也是「我只看到文件名」那类线上问题的根源：它知道不许说 X，但不知道那该说 Y。
建议
规则改写一半位的原则：每条禁令必须配一条「改为做 」，形成 don't → do instead 配对。 同时补一条兜底：「不确定时，先用 ask_user 问，而不是猜会不会做」—— 这条比任何具体禁令都值钱。
P1-3零 few-shot —— 没有一条端到端的 canonical trajectory
证据
唯一的示例是 ⟦plan⟧ 的那一行 JSON agent.service.ts:812。 没有任何「用户话术 → 工具调用序列 → 回复」的完整示例。
后果
规则 4/5 描述的是一条 5 步以上的工具编排链（upsert → set_text → connect → apply_sidebar → propose）， 纯靠自然语言描述这种序列，遵从率是结构性地低。主流实践里，多步工具编排靠 few-shot，不靠描述。
建议
写 3 条 canonical trajectory 放进静态段（约 600 字，可控）： ① 「画一张 XX」单图；② 「参考 @I1 出三视图」带侧栏；③ 「闲聊/谢谢」应不调任何工具的负例。 第③条最关键——负例 trajectory 的成本远低于负例文字描述。
P1-4load_tools 触发率 0 —— discoverability 从未被设计
证据
延迟索引块只有一句触发语「需要时调用 load_tools 按名加载」tiering.ts:84， 位于 system prompt 的尾部区块。项目侧已做过「强指令化」实验，同样失败（模型能逐字复述指令却不调用）， 根因另有嫌疑：harness/execution/tools.ts:84 的 immediateError 会把工具返回吞掉。
建议
两手都要做：① 在 <tool_policy> 段写条件式触发规则 （“若你要完成某动作但当前没有对应工具 → 先调 load_tools(['...']) 而不是放弃或假装”）， 并补一句正向兜底：不要把「手上没这个工具」当成「这件事做不成”； ② 按 vendor 侧的 immediateError 走一遍，确认工具返回不会因为 provider 层原因被吞掉。 两者都用 P0-1 的 eval case 量化，别再靠肉眼观测。
P1-5工具没有编写规范：description 混语言、「what/when/how」混在一坨、summary 缺失
证据
· 41/43 工具无 summary → 索引块退化为长 description 铺板 tools/types.ts:56-76
· 中英混排：同一个工具里 description 用英文、parameters 用中文的混搭现象普遍 （例：canvas-write.ts:49-52：description 英文、"用户短需求原文，作 prompt 节点标题" 中文）
· description 同时承担 what / when / how / 反例（例：upsert_media_node 的 description 里塞了 "Does not start generation — use propose_generation after"）
后果
工具的 description 本身就是给模型的提示词。混语言拉低小模型/弱模型的遵从；what+when+how 混写让 description 长度失控， 最终吃掉的就是 prompt cache 与 BYOK 小窗口。
建议
立一份工具元信息契约并写进 CI 校验（不是文档）：
  • description ≤ 2 句，只答 what + when；how / 反例 移到系统提示的 tool policy 段或 body 注释。
  • summary 必填，≤ 12 字；索引块消费 summary，缺 summary 就 CI 失败。
  • 单一语言：工具元信息统一跟随模型语言（中文），英文只在必要的技术名词保留。
  • 每个工具加 examples（1 条最小正例），作为工具级 few-shot 的素材库。
P1-68 个 SKILL.md 是「没人管的第二套提示词」
证据
skills/ 下 8 个 SKILL.md（107–156 行/个，总量约 1,100 行），版本手工维护 （0.1.0–0.5.0），frontmatter 只有 name / version / description； loader 明确「lnkpi.* 扩展元数据与 prompt_version 机制不迁」skills/loader.ts:1-5； load_skill 的 description 是英文，而它指向的索引块是中文 tools/skill-tool.ts:19-22。
后果
Skill 的正文是注入上下文最长的一段提示词，但它没有 owner、没有触发测试、 没有 changelog，也没有任何机制回答「改了一个 skill 会不会连带影响别的 skill」。
建议
  • frontmatter 增加 owner / changelog / eval_cases[]。
  • 每个 skill 至少 3 条触发语句 fixture（"帮我做角色三视图" → 应命中 drama-character-design）， CI 断言路由准确率；同时包含 ≥1 条不该命中的近似语句。
  • 统一 load_skill 的 description 语言；把 SKILL.md 也纳入 P0-3 的版本体系。

06P2 缺口：健壮性与长期演进

P2-1压缩摘要 100% 依赖 vendor，宿主只有事后告警权
证据
compaction-summary.ts 只做必需段白名单的事后告警；宿主侧没有 「必须跨压缩保留的状态」清单（pending confirm 的节点 id、用户已确认的偏好、本会话已跑过的关键工具结论）。
建议
在 vendor 摘要产出之后，由宿主追加一段结构化的「保留段」 —— 把上述状态以 <retention> XML 块强制 append。这是唯一能把「压缩后信息丢失」变成可控的手段。
P2-2trust-boundary 是安全补丁，不是 prompt 设计；且缺少 revision 语义
证据
trust-boundary.ts 用 ≤500 字符硬截断 提取目标 trust-boundary.ts:52-56：会从句子中间切断，复述出半句话； 且缺失「用户在新一轮里推翻了前一轮要求」的处理约定 —— 复述总是最新 user 消息，多轮修订场景下模型会同时看到互斥的两个"目标"。
建议
① 截断按句边界并加省略提示（保留语义完整性的成本极低）； ② 增修订语义：复述带上「这是最新指令，取代同主题的前序要求」。这两条都能用单测钉死。
P2-3thinkingLevel 只透传标量，没有 per-task 推理预算策略
证据
thinkingLevel 由 UI 两档映射 agent.service.ts:831，与任务类型无关。 temperature / top_p / stop / max_output_tokens 全链路零配置。
建议
至少做「闲聊 / 单步 / 多步编排」三档 effort 路由；对确定性强的输出（⟦plan⟧ JSON、vision QA JSON） 单开低温度路径。别一次做完，先补 query 复杂度分类器 + 三档。
P2-4vision 子提示词是「外挂孤岛」，与主体无契约
证据
sidebar-media-parse-prompt.ts 是一份完整的独立视觉提示词（含 JSON schema）， 注释自己写「两边改任一处都要同步」sidebar-media-parse-prompt.ts:1-7——这句话就是孤岛的认罪书。
建议
纳入统一 Prompt Registry 并标 kind: sub-prompt、owner、 output_schema；对输出做运行时校验（现在是 JSON.parse 后信任）， 缺失字段要 structured error 而不是静默。
P2-5没有任何 A/B 或灰度能力
证据
PI_RUNTIME_SYSTEM_PROMPT 这个 env 存在但从未使用 session-manager.ts:494，注释写着「覆盖默认系统提示词」——实际是维护态兜底，不是实验开关。
建议
会话级 prompt variant 注入（variant: "v1" | "v2"）+ 按 userId 哈希分流 + 以 P0-1 的在线指标做对比。在 eval 和版本化落地之前不要做 A/B，否则你拿到指标也不知道读的是哪一版。

07目标形态：重排后的 system prompt 骨架

不是让你们照抄这份文案，而是给出分区契约：每个区干一件事、可被单独版本化、可被单独 eval。 建议把这份骨架作为 Prompt Registry 的 v1 schema。

<identity>
你是 lnkpi 无限画布助手，帮用户在画布上完成创意生产。
用简洁中文回答；专业术语保留原文。
</identity>

<style>
默认节奏：一句话交代要做什么 → 调工具 → 一句话汇报结果。
用户追加插话时：先复述这条新要求及其对当前计划的影响，再继续动工具。
不确定该做什么时：先用 ask_user 问，不要猜，也不要说「我做不到」就停下。
</style>

<capability>
可以做：画布读写、意义在本台;quot;生成图片/视频/音频/文本、Web 搜索与抓取、保存与回忆用户偏好。
当前不可做：工作流模板（用户要模板时用「节点 + 连线」搭骨架并如实说明）。
</capability>

<rules>
<!-- 每条一个动词、≤30 字、编号连续；原来是 1,2,3,7,14,4,5,11,12,13 -->
1. 一切画布读写都必须通过工具，不要口播「已完成」。
2. 不要否认平台的图片/视频生成能力，也不要引导用户去第三方工具。
3. 用户明确确认前不要调用 run_*_generation，也不要说「正在生成」。
4. 出图前先把节点建好并 propose_generation，等用户确认。
5. 侧栏 @I* 芯片只用 apply_sidebar_attachments 挂载，不要用 connect_nodes 连。
6. 闲聊、致谢、纯提问不要创建任何节点，也不要 propose_generation。
7. 造 ≥2 个媒体节点的请求要拆成多个节点 + 连线，不要压成单个节点。
8. 用户要取消生成时调用 cancel_generation，如实转述结果。
</rules>

<tool_policy>
需要某个动作但手上没有对应工具时 → 先调 load_tools(["..."])，不要放弃，也不要说做不了。
你的意图匹配「可用技能」里某项的描述时 → 先调 load_skill 加载完整说明再执行。
</tool_policy>

<negative_examples>
<!-- 每条禁令配一条正向替代 -->

× 「这是 XX 模板的标准流程」      → ✓ 「平台还没有模板能力，我用节点 + 连线搭一个骨架」
</negative_examples>

<examples>
<!-- 3 条 canonical trajectory: ① 单图 ② 带侧栏参考 ③ 闲聊不调工具 -->

</examples>

08建议路线图

窗口动作验收判据
第 1–2 周
地基		 ① 抽 Prompt Registry：把 Nest 两处 + pi-runtime 一处的提示词文本收进单一源，打 version；
② 建 ≥30 条黄金回归集（首批直接取线上失败样本）+ LLM-judge；

第 3–4 周

第 5–6 周

实验		 会话级 variant 注入 + 按 user 哈希分流 + 指标对比 能在一周内跑完一次双臂实验并给出置信结论
最后一句提醒：这份报告里最容易做、也最容易被跳过的是 P0-1（eval）和 P0-3（版本号）。 它们不产生任何用户可见的功能，所以在排期会上最容易被压后。但跳过它们， 第 3–4 周的「规则重写」就会变成一次无法回滚、无法归因的冒险—— 而规则重写恰好是全项目风险最高的一次提示词变更。
