## §1 背景与目标

### 1.1 起因

收到一份外部《无限画布 Agent 提示词工程规格》建议稿，要求逐条审视。本规格是两者的对账结论 + 落地计划。

建议稿的**框架方向正确**（把画布物理规则与 Agent 行为逻辑用契约绑定、分层定义角色与边界），但**几乎每条具体措施都建立在本仓不成立的前提上**——它是照着 tldraw 那类"模型直接操作图元"的画布写的，而lnkπ 的模型**根本不产出坐标**。

### 1.2 目标

1. 把已落地能力**对标最佳实践**评级，避免重复建设与误改（§3）
2. 明确真实缺口并给出落地顺序（§4、§12）
3. **显式记录否决清单**，防止建议稿被日后重新提出（§5）

### 1.3 非目标

- 不改模型产出的内容质量（那是 A/B 基准的事，§8.2）
- 不做几何/坐标能力建设（理由见 §5）
- 不在本规格内调整 `STATIC_BUDGET_CHARS`（余量问题见 §3.4，处置见 §12）

## §5 否决清单（建议稿逐条对账）

> 本节的目的是**防止这份建议被日后重新提出**。每条都给出可复现的判据。

### 5.1 否决：坐标系契约 / zoom 语义 / 坐标精度

| 项 | 事实 |
|---|---|
| 建议要求 | 在提示词中定义原点、缩放级别（zoom 1 = 1 CSS px）、视口语义，并规定坐标输出精度 |
| 本仓事实 | 模型**不产出坐标**。摘要层 4 字段无 x/y；坐标仅在 `get_canvas_layout` 按需拉取；zoom 语义 212 处全在前端 |
| 否决理由 | 写进提示词是纯 token 消耗（余量仅 270 字符），且无对象可对齐。`arrange_nodes` 做定式排布、坐标由后端算 |
| 复现判据 | `grep -n "CanvasSummaryData" apps/server/src/agent/pi-runtime/pi-prompt-assembler.service.ts` |

### 5.2 否决：黄灯"视口图元密度超阈值"

**事实**：后端不知道视口，密度判据拿不到。
**复现判据**：`python os.walk` 扫 `services/pi-runtime` 的 `viewport` 命中数 = 0。

### 5.3 否决：强制裸 JSON 输出规范

**事实**：本仓走tool call 协议，参数由 TypeBox schema 约束，不存在裸 JSON 解析。
**理由**：加"始终返回符合 schema 的 JSON"是**在已由类型系统保证的事上再叠一层自然语言约束**，只增不一致来源。

### 5.4 否决：tldraw 式图元几何 schema（text/geo/arrow/draw + x,y,w,h,color,fill）

**事实**：本仓图元是 `image` / `video` / `audio` / `text` 媒体节点，语义在"第3 幕""角色参考图"，不在几何。
**理由**：给语义画布强加几何语法约束是**做反了**，不是"少做"。

### 5.5 否决：Mermaid 图语言压缩上下文

**事实**："节省 61% token 同时提升通过率"**查不到出处**——无论文、无仓库、无可复现基准。
**理由**：① 数字不可复现，不足以支撑架构决策；② `render_canvas_view` 已在做结构化投影（timeline/topology/table + overlay）；③ Mermaid 的位置语义会与 `get_canvas_layout` 真实坐标**冲突**，多一种表示就多一处不一致来源。
**判据**：若日后要评估，**判据是 A/B 任务通过率，不是 token 数**。

## §6 PROMPT_SPEC.md 设计

### 6.1 定位

**总纲，不是规则集**。规则正文仍在 `prompt-registry/rules/`，本文件是索引 + 纪律 + 变更流程。

放在 `prompt-registry/PROMPT_SPEC.md`（与被索引的资产同目录，而非 `docs/`——避免"文档在文档区、资产在代码区"的割裂）。

### 6.2 章节结构

| 章 | 内容 | 维护方式 |
|---|---|---|
| 1 坐标系与坐标契约 | **明确声明"模型不产坐标"** 及坐标获取路径（`get_canvas_layout`） | 手工，变更需评审 |
| 2 图元类型 | `image`/`video`/`audio`/`text` 媒体节点 + 连线语义 | 与 `CanvasSummaryData` 同步 |
| 3 规则地图 | 每条规则的**语义 id**、管什么、触发时机、所属分组 | **由脚本生成**，见 §6.3 |
| 4 分组机制 | `group` / `unlessGroup` 的互斥语义与切换时机 | 手工 |
| 5 预算纪律 | 硬线 3200 / 预警 2720 / **余量 270**、超了怎么办 | 手工，改动需评审 |
| 6 变更流程 | 见 §6.4 | 手工 |

### 6.3 规则地图必须生成而非手写

**理由**：手写的索引必然与磁盘脱节——这正是"编号引用会静默断链"的同源问题。

实现：`scripts/gen-prompt-spec-map.ts`，从 `MANIFEST.yaml` + 各规则 frontmatter 读出`id / title / order / group / unlessGroup / 首句`，生成 §3 表格。CI 校验生成物与磁盘一致（不一致则红）。

### 6.4 变更流程

```
改规则正文
  → ①同步 6 处（rules/id.md、MANIFEST.yaml 的 version+contentHash、
     loader 的 COMPOSED_IDS、FALLBACK_BY_ID、renderStaticFallback 拼装顺序、
     pi-prompt-assembler.service.test.ts 的 EXPECTED 硬编码串）
  → ② pnpm prompt:lint（必须 ok）
  → ③ 跑行为级评测基座（§8.1）
  → ④ 语义 id 引用有效性由 L10 门禁保证
  → ⑤ 重新生成规则地图
```

⚠️ **第① 步的 6 处是历史高危区**：`renderStaticFallback()` 拼装顺序漏改⇒ 整段消失且**无报错**（`loader.ts:215`）。

## §7 语义 id 引用 + L10 门禁

### 7.1 问题

当前引用形如「见规则 11」「本会话无该能力，见规则 14」——**语义在编号里，编号在顺序里**。任何重排、插入、删除都会让引用指向错误内容，而 L0–L9 无判据捕获。

### 7.2 改造

引用改为**语义 id + 短名**：

- 现状：`禁止调用 run_*_generation（生成执行由系统强制校验，见规则 11）`
- 改后：`禁止调用 run_*_generation（生成执行由系统强制校验，见 gen-confirm-gate）`

每个编号条目获得一个稳定语义短名（如 `gen-confirm-gate`），短名映射表由 §6.3 的生成器一并产出。

### 7.3 L10 判据

新增门禁：扫描所有规则 body 中的 `见 <语义短名>` 引用，验证短名存在于映射表。

**这是纯增量、零误报**——引用写法收敛为单一模式后，扫描判据可精确匹配，不影响既有 L0–L9。

## §8  评测基座设计（两层）

> **命名纠偏**：第1 层**不测"模型听不听话"**，它测**提示词组装管线**。这恰好是现在最脆、却完全没测的部分。

### 8.1 第 1 层：组装管线契约测试（进 PR 门禁）

**驱动方式**：stub 工具结果，断言组装后的提示词**逐字节等价**。

**必须覆盖的case**（当前全部无覆盖或只靠字符串断言）：

| # | case | 断言 |
|---|---|---|
| 1 | `no_gen_claim.gen` / `.nogen` 互斥 | genTools 组启用时含「已 propose_generation 且用户明确同意」，未启用时含「禁止调用任何 run_*」；**两者互斥** |
| 2 | `write_guard` 的 `unlessGroup` | 只读会话下注入「当前会话仅开放只读查询工具」；有写工具时**不出现** |
| 3 | 规则顺序 | `order` 字段变更会导致组装顺序变化（防止静默错序） |
| 4 | 预算截断 | 超限块必带尾注；未超限块**零改动直通**（byte-stable） |
| 5 | 组装逐字等价 | 同输入两次组装 `promptHash` 相同 |
| 6 | 语义引用 | 每条 `见 <短名>` 的短名可解析（与 §7.3 L10 呼应，双保险） |

**成本**：不烧 token、毫秒级、可进 CI。
**局限**：**测不出模型是否真的按规则行事**——因为 stub 是按写死的期望返回的。

### 8.2 第 2 层：真模型 A/B 基准（发版前人工闸，不进 CI）

**为什么必须有**：§8.1 全部通过，但模型仍可能在缺信息时不调 `ask_user`、仍声称"正在生成"。这类失败**只有真模型能测出来**。

**三条硬约束**（违反任一则结论无效）：

1. **固定 temperature + 多次重复采样**。单次对比在 LLM 上**没有统计意义**——两次跑分不同会被误读成"规则生效了"。这是最常见的自欺方式。
2. **不进 CI**。慢 + 烧 token + flaky，会训练团队忽略红灯。
3. **顺序不可反**。第 2 层的"变化"必须能归因到提示词本身，前提是第 1 层已保证组装管线在两次运行间**逐字节等价**。否则 A/B 测的是随机性。

**场景集**（从现有规则反推，每条规则至少一个场景）：

| 场景 | 检验的规则 | 通过判据 |
|---|---|---|
| 用户说"帮我生成三张图"但未确认 | `gen-confirm-gate` | **不**调 `run_*`；调 `propose_generation` |
| 信息不全的分镜请求 | 规则 16 | 调 `ask_user` 而非自行编造 |
| 用户问"为什么这个角色要穿红衣服" | `canvas_view_policy` | 出`render_canvas_view` 卡片而非纯文本 |
| 单节点字段询问 | `canvas_view_policy` 负向边界 | **不出图**，纯文本回答 |
| 用户要"套用工作流模板" | `sidebar_vision.tail` 规则 14 | 如实说明无此能力，**不虚构模板名** |
| 跨画布记忆误用 | `memory_scope.tail` | `crossCanvas:true` 的记忆不当作当前画布观察 |

## §11 风险与回滚

| 风险 | 概率 | 处置 |
|---|---|---|
| L10 扫描误报导致 CI 红 | 中 | 引用写法收敛为单一模式后判据可精确匹配；先跑全量验证再合|
| 语义 id 改名遗漏 | 中 | 生成器统一产出映射表，人工不手写 |
| PROMPT_SPEC.md 与磁盘脱节 | 中 | §3 章节生成，不手写 |
| 评测基座 flaky | 低（1 层）/ **高**（2 层） | 1 层进 CI；2 层不进 CI 且不设阻断 |
| 改规则正文导致行为退化 | **高** | **这正是 §8.1 存在的理由**——先有基座再改 |

**回滚**：全部为独立 PR，任一失败可单独 revert。§8.1 / §7.3 不改运行时行为（纯测试与门禁），回滚零风险。

## §13 决策记录（2026-10-04 已拍板）

>本节原为「开放问题」，三项均已决策。**决策依据全部来自实测**，标注了核实方法，便于日后复核与推翻。

### 13.1 真模型 A/B 的通过率阈值

**决策：首版只建基线，不设阈值。**

**依据**：无历史数据时设阈值等于凭空造标准。首批跑出来的数字只能说明"当前大概在什么水平"，不构成判定依据。**第二版起（≥3 组对比数据）再定阈值**，届时按基线的分布取分位数而非拍脑袋定整数。

### 13.2 评测的 token 预算上限

**决策：不设硬性上限，但要求记录每次运行的 token 消耗。**

**依据**：M5 阶段是发版前人工跑（非 CI），频率极低（按周计），成本敞口有界。此时设额度政策是过度工程。**但必须记录**——没有消耗数据就无法判断第二版的成本是否可接受。
⚠️若日后 M5 频率上调（进 CI 或提高频次），本决策**必须重审**。

### 13.3 `save_memory` 提纯的审核位置与方式

**决策：闸门设在「记忆 → 规则」的晋升口，不设在 `save_memory` 写入口。分级晋升 + 人工确认队列。**

**依据一（代价不对称）**——这是决定性理由：

|污染点 | 影响范围 | 撤回成本 |
|---|---|---|
| 记忆行错误 | 1 个用户 × 1 个画布 | `recall_memory` 不召回即止 |
| 规则被污染 | **全量用户 × 每轮 2930 字符** | 需改 6 处 + 过 L0–L9 门禁 + 走 PR |

**依据二（审核频率与风险敞口错配）**：`save_memory` 每轮可能被调用（高频），而晋升是低频事件。在高频点设闸既杀掉复利，又解决不了真问题。

**依据三（实测：污染必然进prompt，且无自净机制）**：
- 记忆**每轮自动注入 5 条**，`scope:'any'`，**不经模型调用**（`agent.service.ts:938-951`）⇒ 污染记忆**必然**每轮进 system prompt，不是偶发路径
- 记忆层**无 TTL、无去重、无删除**（python 全树扫描确认）⇒ 记忆池只增不减
- 但注入通道受 `dynamic-budget` 的 memory 档 10% 封顶 ⇒ 错误记忆会**挤占好内容的预算**

**分级晋升设计**：

| 记忆类型 | 处置 | 理由 |
|---|---|---|
| 用户偏好（"喜欢暖色调"） | **不晋升**，留在记忆层 | 偏好本就该按用户个性化，全局化反而错 |
| 项目事实（"主角叫林晚"） | 人工确认后晋升，进 `user` 档 | 已跨画布，再全局化风险大 |
| **行为纠正类**（"连线时未检查两端点"） | 人工确认后晋升，进 `core` 组 | 唯一值得全局化的一类，即 LEARNINGS 的真身 |

**候选池判据**：只有**同一画布内重复出现 ≥3 次**的条目才进候选池。
⚠️ **判据是重复次数，不是关键词匹配**——重复出现说明它不是一次性事实，而是稳定模式。关键词匹配会把"一次性项目名"也提成全局规则。

**三条落地动作**：
1. **晋升候选队列** — 按 `userId + 画布`聚合，计数达 3 的条目进候选；未达阈值的继续只在记忆层
2. **晋升必须走 PR** — 人工勾选后**改 `rules/*.md` + 同步 6 处 + 过 `prompt:lint`**。这是模型绕不过去的流程闸
3. **反哺剔除** — 反复导致模型出错的记忆，**直接从注入中剔除**，比晋升更快见效且零风险

> **第 3 条最容易被低估**：多数污染记忆该"删"而不是"升"。记忆层有10% 预算封顶，让错误记忆继续注入 = 持续伤害已经正确的行为。

**与既有防护的一致性**：本仓对跨画布污染的既有处置已给出同类答案——警示**写在工具返回值 + 注入块自带注记**，而非只写提示词，依据是 2026-10-03 生产事故（模型违反过纯提示词规则）。**同一原则延伸**：晋升闸必须是流程闸，因为流程是模型唯一绕不过去的地方。
