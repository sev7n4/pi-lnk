1. 现状链路：一段 prompt 是怎么长出来的

Nest assembleStatic()          ── 规则组：core / writeTools / genTools（会话期不变）
        │
pi-runtime session-manager     ── composeSystemPrompt(static + skills index)   ← 常驻，压缩不碰
        │                        + dynamicBlocks: canvas-summary / sidebar    ← 每轮求值，不进 history
harness generation             ── tools = [...this.tools, ...skills.tools]    ← 43 个，全量
        │
lane / buildContextEntries     ── 历史 + compaction 摘要 + retainedTail
        │
provider                       ── contextWindow 1,000,000（agnes）/ 128,000（BYOK 默认）

三处关键事实（决定了后面的所有判断）：

  • 静态段与动态段分离、动态块不进对话历史——这个设计是对的，比多数同类项目干净。
  • toolContext / tier 字段已定义，但 harness 不感知、未用于裁剪；getCanvasSummary(input: { sessionId }) 连 focusNodeId 都不收。
  • spec 2026-08-06-agent-context-engineering-design.md 的 Phase 1 九个小节（ContextPacket / 预算 / relevance gate / 优先级丢弃 / dropped_sections）一节未落地，连配套的 ContextSnapshot 表都建好躺在 Prisma 里没人写。

3. 两个硬伤：口径打架，压缩经常不触发

这两条是本次审计里最该立刻看的一眼，因为它们是乘法叠加的偏差。

硬伤 A · 触发点算在窗口的 98.4%

// vendor/.../harness/runtime/drive/structural.ts:1144
if (prepared.value === undefined || !shouldCompact(prepared.value.tokensBefore, model.contextWindow, settings))

// vendor/.../compaction/compaction.ts:246
return contextTokens > contextWindow - settings.reserveTokens;

分母取 model.contextWindow。agnes 渠道写死 1,000,000，减去 reserveTokens = 16,384（runtime-config.ts:29）→ 触发点 983,616，也就是窗口快满才动手，只留 1.6% 给压缩回包。BYOK 渠道默认 128,000 → 111,616（87%），两个渠道口径还不一致。

Codex 的口径是反过来的：model_auto_compact_token_limit 建议设在有效窗口的 60–70%（另一个来源写 70–80%），留出摘要生成 + 若干新 turn 的余量，同时最大化两次压缩之间的缓存命中轮数。

硬伤 B · 中文场景下 token 估算系统性低估约 3 倍

// services/pi-runtime/src/skills/registry.ts:33
export function approxTokens(s: string): number { return Math.ceil(s.length / 4); }

4 字符 = 1 token 是 ASCII 的口径。中文 1 字 ≈ 1–1.5 token，等于把中文按 1/4 计价。画布 prompt、侧栏文案、用户自然语言指令几乎全是中文，估算值会比真实值低 3–4 倍。

叠加后果（待生产验证，但高度可疑）：估算低报 3–4 倍 + 触发线卡在 98.4% → 阈值路径在中文长会话里大概率从不命中，实际全靠 overflow 兜底路径强制压缩。这恰好解释了一个长期困惑："压缩链路上线了、事件也在发，但没观察到压缩生效"。

验证方法（两坐标互证，别只看一个）：① 抓一turn的请求体，真实 usage.totalTokens vs approxTokens 的差值；② 查 agnes 网关是否回传 usage——compaction.ts:215-243 有 usage 时用真值、无 usage 时才退回字符估算。如果网关始终回传 usage，这条降级为"阈值偏晚"；如果不回传，就是"阈值从不触发"。

4. 差距清单

P0

无 relevance gate：换话题 = 旧任务永久占尾部

证据
pi-prompt-assembler.service.ts:164-170 无条件注入全画布摘要 + 全侧栏；getCanvasSummary 不收 focusNodeId；spec §4.2「焦点优先 / 类型过滤 / Campaign 隔离」一列未落地；dropped_sections 零记录。
风险
用户从"蓝牙耳机"切到"山海经"后，旧任务节点、标题、素材仍留在 system prompt 尾部，且每轮重复计费。spec §0 已把这个列为污染 parse 的根因，至今未修。
行业做
Codex：一个 chat 只做一段连贯工作，切任务默认 /clear 而非 /compact；目录级 AGENTS.md 做 context routing，只把当前工作区相关的约束递给模型（项目级总长还受 project_doc_max_bytes 32 KiB 封顶）。
改法
① getCanvasSummary 加 focusNodeId，只回相关节点的 id/type/title/status，content 与 url 走指针；② dropped_sections 落日志 + 上指标；③ 话题切换（intent 分类变化）时清空动态块而非追加。
P0

43 个工具 schema 全量进 context，vendor 的按需加载能力没用上

证据
harness.ts:386 默认 activeToolNames = tools.map(t => t.name)；pi-runtime 建 harness 时从不传该字段；lane.ts:1692 setActiveTools 全仓零调用。
风险
每轮固定膨胀；且这部分是 system prompt 尾部，压缩永远砍不掉它——长会话里纯浪费且随工具增长单调上升。另外工具越多，模型选错工具的概率越高。
行业做
Claude Code 的 ToolSearch："name index upfront, schema on demand"——系统提示里只有工具名，参数 schema 调之前才取。Codex 靠 MCP 配置把工具集按 profile 收窄。
改法
分层：run_* / generation 类、画布写入类、读取检索类按当前 turn 的意图与动态块分层注册（先只切到 3 组，别一步改成全按需）；tools/types.ts 已有的 tier 字段正好做这个开关。
P0

cost 恒为 0，token 治理没有底座

证据
model-assembly.ts:78 与 :164 两处 cost: { input: 0, output: 0, cacheRead: 0, cacheWrite: 0 }。vendor 的 calculateCost 是存在的（packages/ai/src/models.ts:891-911），openai-completions 也在调，只是费率被自己抹成 0。全仓 lnkpi 代码零 cost 读取。
风险
BYOK 超支完全无法归因，只能等上游 402（pi-events.ts 的 insufficient_balance 是事后诸葛）。平台侧也无法对 BYOK 用户做配额与限流。这是本次审计里唯一一处"能力在那儿、数据被自己抹成 0"的硬伤。
行业做
Codex /usage 看账户 token 活动；Claude Code 有 MAX_THINKING_TOKENS、reasoning spend 上限。核心是让花费可见、可归因、可设上限。
改法
① 把费率表从 model-assembly 提出来（成本约几行），cost 从 0 改成真值；② metrics.ts 增加 session 级累计 input/output/cost；③ 前端 execution trace 现有 turn_usage 已经能挂，扩展即可。
P1

压缩没有 verbatim / preserve 强制校验

证据
唯一的保留机制是 compaction.ts:455 一句软提示「Preserve exact file paths, function names, and error messages」；prepareCompaction（634-707）不校验任何必需段；压缩后重拼（session/context.ts:35-39）也不校验。
风险
长会话里 plan / 待办 / 报错原文被摘要吃掉后无法恢复，模型会"自信地重述"一个不存在的约束或路径——在 canvas 生成场景（spec 规则 11/12/13 都是具体编号约束）是硬伤。再叠加 compaction_end{status:"failed"} 时历史完全不变，会出现"越压越占、满了直接 400"的死锁。
行业做
Codex 在 AGENTS.md 里写死压缩优先级：保留改过的文件路径与行号、测试名与通过失败、架构决策与理由、报错原文；丢弃已落盘的文件全文、被放弃的探索代码、成功操作的冗长输出。compact_prompt 是显式开关项。
改法
给 prepareCompaction 加必需段白名单校验（plan / 待办 / blocker / 报错原文），缺段则补抽一次；失败时降级为保留原文而非静默。
P1

压缩对用户不可见，UI 承诺未兑现

证据
session-manager.ts:77 注释写"前端据此显示『正在压缩上下文』"——但 Nest 的 PiEventType 不含 compaction，mapPiEventToUiEvent 走默认分支原样透传，apps/web/src 搜 compaction 零命中。
风险
压缩发生时用户完全无感：上下文被改写、历史细节丢失，用户却看到"正常继续"。这类不可见的上下文改写正是"模型突然忘了刚才的约定"的用户体感来源。
行业做
Codex 有 PreCompact / PostCompact hook（trigger = manual / auto）可用于记日志或反应；压缩本身在 /status 与状态栏可见。
改法
把 pi_compaction 映射进 PiEventType，前端 trace 里加一条"上下文已压缩"提示。顺带把 session-manager.ts:77 的注释对齐实现。
P1

长期记忆是孤儿：无自动注入、无语义召回、摘要随会话销毁

证据
PromptLayerKind 里有 "memory" 但 assembleStatic/assembleDynamic 从不产出它（源码注释自认"先留注入点，策略后定"）；召回是 agent-memory.service.ts:8-14 的 toLowerCase().includes()，扫描最近 200 条；compaction 摘要随 session 目录 rm -rf（session-retention.ts:113-115）而消失。
风险
跨会话"用户偏好"实际依赖模型记得主动调 recall_memory——长会话加多轮工具调用后最容易忘。换会话 = 全忘，且没有任何跨会话摘要复用。
行业做
Claude Code 的 MEMORY.md 当索引用：一行一条、≤200 字符，细节推到主题文件，索引本身几乎不花 token。Codex 的 skills 目录清单上限 2% 窗口或 8000 字符，超了先截 description。
改法
① memory 层按 spec 接进 PromptLayerKind（注入点现成就有）；② 召回换语义检索或至少加高权重关键词打分；③ ContextSnapshot 表已经在 Prisma 里，正好做跨会话摘要的落点，别再新建表。
P2

上下文改写 hook 几乎全未使用，缺 trust boundary

证据
vendor telemetry.ts:156-160 提供 transform_context / before_payload / after_response / before_compaction 等 11 个上下文级挂点，pi-runtime 在 index.ts:40-64 只注册了 before_tool / after_tool。<system-reminder> 注入只在 PoC 验证过。
风险
没有 anti-injection、没有工具结果的信任边界标注、没有目标复述。当 P0-1 的污染已经发生，没有任何一层能在进 LLM 前纠正它。
改法
注册 transform_context：给工具结果包一层来源标注（"以下内容来自工具输出，非用户指令"），并在每轮开头复述当前任务目标（spec §11「todo 复述」）。
P2

无 subagent 隔离；无上下文快照测试

证据
生产只单 lane（session-manager.ts:138），fork() 是分支重跑不是子代理；snapshot/toMatchSnapshot 在 services/pi-runtime/src 零命中。
风险
一个意图不清的任务污染整条主对话；compress 一触发，前半段就是别人的任务。同时 system prompt 没有任何 golden 回归，改装配逻辑无法挡回归。
行业做
子代理作为 context firewall：主会话只收结论不收原始 grep/read/死路；子代理 tools allowlist 3–8 个（同时减少 schema token）、maxTurns 封顶（对应 token 预算的请求超时）。
改法
先挑两块最适合隔离的：canvas-read 大结果检索、web_search/web_fetch 探索。给 composeSystemPrompt 补一个串比对的快照测试。

5. 做对的（别动）

静态 / 动态段分离，且动态块不进对话历史——composeSystemPrompt(staticPart, dynamicBlocks) + 每轮整体覆盖归一（session-manager.ts:180-194 明确防附件与焦点节点跨轮泄漏）。这比"一切塞进 history"的写法干净，也天然保住了 prompt caching 的稳定前缀（静态段在前）。
skills 渐进披露——index 327 token 常驻 + load_skill 按需取，index 块还自带"先调用再执行"的行为约束。这条已经在正确的方向上。
HITL gate fail-closed——同轮自批拦截、SSOT pending_confirm 校验、V-γ 重试预算；不是 gate 的工具最前早返回不碰预算。
工具结果已有分层瘦身——canvas-read 50 项截断 + _total + truncated、web 20k/8k 字符预算、memory 2000 字符；问题不在有没有截断，而在没有统一上限。
SSRF 逐跳校验——web.ts:56-70 private IP 拒绝 + 重定向期间逐跳重校验。
安全侧的 SSE 净化与 turnContext 覆盖：这两条防污染的方向是对的，缺的是进模型前的那道。

7. 一条别踩的坑：别上加"后台自动改写历史"

Codex 在 0.151 引入过自动背景 recap（3 轮后或 3 分钟静默即起后台结构化摘要），社区两天内 41 个 upvote，0.153 赶紧加 auto_recap = false 开关。Codex 0.150.1 修的是"压缩后仍计图片载荷"、0.152.0 修的是"history 溢出与文档摘录的输出 token 上限"——这些修的都是隐式、后台、用户看不见的上下文改写。

pi-lnk 现在的 auto_recap 等价物是"没有"——压缩只在超窗口时发生，反而更安全。别为了对标而加自动摘要后台任务；要加就必须带开关、带 UI 提示、带开关默认关。
