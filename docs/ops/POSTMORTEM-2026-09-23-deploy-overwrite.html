复盘：两个仓库并行开发，如何把生产上的 runtime 分流悄悄覆盖掉

事件日期 2026-09-23 · 影响对象：生产 CVM 119.29.173.89 上的 PI_RUNTIME_MODE=active 分流链路 · 结论：业务无损伤，根因已消除，1 处残留交叉点已于同日收窄

状态：已闭环 业务影响：无（数据/接口无损伤） 修复：发布门 + 防呆守卫 + 回滚保留 配套手册：RUNBOOK-single-release-gate.md

一页速览（TL;DR）

  • 现象：11:17 一次部署后，/opt/lnkpi/apps/server/src/agent/pi-runtime/ 目录整体消失，PI_RUNTIME_MODE=active 仍在 .env 里却不再生效 —— 所有请求静默走回老 LangGraph runtime，无报错、无回退提示。
  • 根因：pi-lnk 与 lnkpi 是 fork 关系的两个仓库，共用同一份 deploy.yml（diff = 0 行）、同一个部署目标 /opt/lnkpi，而同步动作是 rm -rf apps/server packages 后再解包 —— 包内没有的文件会被物理删除。lnkpi 源码不含 B4 分流文件，所以从 lnkpi 发版＝定时擦掉分流代码。
  • 为什么长期没暴露：覆盖后是"静默降级"而不是报错；且当时 pi-lnk 的工作流挂在 main 分支、实际工作在 master，等于没有自动化，无法形成对照。
  • 修复：① 历史合流（两仓库收敛到同一条链）② 部署脚本加 B4 防呆守卫 ③ 部署权收敛到单一发布门 pi-lnk（lnkpi 只自动发前端）④ 镜像保留上一版，回滚不再需要重建。
  • 代价（有意权衡）：lnkpi 的 API 改动不再自动上线，需过一次发布门；前端开发完全不受影响。
  • 残留（已收窄）：lnkpi 的 deploy-agent-runtime.yml 曾会自动 tar 覆盖 /opt/lnkpi 的部分源码文件（含守卫脚本本身）→ 存在"守卫被回退"的时间窗。✅ 2026-09-23 已收窄：该工作流的 tar 白名单化（只写 services/agent-runtime/**）+ 新增发布门不变量 Guard（见 5.3 ① 与第 6 节）。

2 · 现状问题分析（事故当时）

2.1 结构性问题：一个代码库、两条开发线、一个部署目标

两仓库是 fork 关系：lnkpi（画布主线，origin = lnkpi.git）与 pi-lnk（Phase-0 分支，origin = pi-lnk.git，upstream = lnkpi.git）。它们共享同一份工作流文件与同一个部署目录，而 pi-lnk 的工作流当时挂在 main、实际开发在 master —— 于是"谁在发版"和"谁有能力发版"是错位的。

2.2 覆盖机理：为什么"改的内容不相关"不构成保护

关键在同步动作的删除语义。两个工作流的同步步骤长得像，行为却不同：

  • deploy.yml（发 API 的那个）：rm -rf $DEPLOY_DIR/packages $DEPLOY_DIR/apps/server 之后再解包 → 包内没有的文件会被物理删除。
  • deploy-agent-runtime.yml：直接 tar -xzf - -C $DEPLOY_DIR → 只覆盖同名文件，不删除。

而 apps/server/** 与 deploy/** 恰好是两个仓库都有的路径。B4 的分流代码就住在 apps/server/src/agent/ 里，和画布后端代码同树同构建 —— 于是"我只改画布，没动 runtime"对覆盖毫无帮助。

2.3 为什么长期没被发现：静默降级

分流开关的三态里，active 的判定依赖"源码/镜像里存在 B4 + 运行时健康检查通过"。当 B4 代码根本不在构建产物里时，NestJS 走的是老 runtime 的分支 —— 接口照样返回 200，画布照样能用（因为老 runtime 一直在服役），没有任何日志告警说"分流没生效"。唯一能发现它的方式是对照指标：pi-runtime 的 sessions/:id/prompt 计数是否在涨。这也是后来把"指标增长"写进验收判据的原因。

2.4 次生问题：镜像 tag 污染与"回滚其实要重建"

  • 守卫脚本测试时误触发过一次真实构建，容器被重建、镜像 tag 变成 lnkpi-api:guard-test（已核查业务无损伤，并补了可辨识别名）。教训：launch-cvm-build.sh 传参即真实启动后台构建，测试必须用桩。
  • 原部署脚本会删除除当前 tag 与 latest 之外的所有 lnkpi-api 镜像 → 所谓"按旧 sha 回滚"实际需要重建（约 13 分钟），与文档口径不符。已在 15:10 修正（见第 4 节）。

3 · 解决方案（目标模式）

目标不是"禁止 lnkpi 发版"，而是把"能不能写生产"和"改了什么"解耦：两个仓库各自独立开发、各自跑 CI，但只有一处能做部署决策。

合流时的固定陷阱

lnkpi 的 30a3781e 改了 .github/workflows/deploy.yml；两仓库共享该文件路径，直接 merge 会把"禁用 API 部署"带进 pi-lnk，静默废掉唯一发布门。固定做法：

git merge upstream/main --no-commit --no-ff
git checkout HEAD -- .github/workflows/deploy.yml && git add .github/workflows/deploy.yml
git commit -m "merge: sync lnkpi main" && git push origin master

4 · 验证闭环：三态开关、验收判据、回滚

"切换后做验证如何不相互影响"靠的不是记性，而是三样东西：三态开关（把风险分级暴露）、每次部署固定的验收判据（把"感觉能用"变成可判定）、两条回滚路径（一条秒级止血、一条版本回退）。

4.1 磁盘代价（实测，反直觉）

docker images 显示每个 lnkpi-api 镜像 1.68 GB，但用 docker history 拆开看：依赖层 562 MB + 系统包层（ffmpeg/openssl）473 MB + 基础层 243 MB 都是镜像间共享的，每次部署真正变化的只有业务层 apps/server/dist —— 约 1.1 MB。所以"多保留一个历史版本"的真实磁盘增量约 1 MB（最坏情况依赖层重生成约 1 GB），不是 1.68 GB（那是逻辑大小＝各层之和）。

5 · 这次变化对 lnkpi 独立开发的影响

直接结论：前端开发零影响；后端 API 改动不再自动上线，需要过一次发布门。下面是逐类改动的精确行为（依据 lnkpi 当前 origin/main 的工作流实测）。

5.1 行为矩阵

你在 lnkpi 改什么触发的工作流会自动部署到生产？你要做什么
画布前端 apps/web/** Deploy（web 过滤命中）→ Deploy web to CVM 会，约 1-2 分钟 不用管，照旧。只写 /opt/lnkpi/web/dist + deploy/nginx.conf、deploy/deploy-web.sh
后端 API apps/server/**、packages/** Deploy（api 过滤命中），但 Build API on CVM 的 if 条件已改为「仅手动显式开启」 不会 需过一次发布门（见 5.2）
deploy/**、package.json、pnpm-lock.yaml、.dockerignore 同上（命中 api 过滤） 不会 同 5.2

docs/**、*.md、README、LICENSE 不命中部署过滤；CI 也因 paths-ignore 不跑 不触发 无
任意代码改动 CI（测试 / 构建 / 契约校验） 不部署 照旧，完全不受影响

5.2 API 改动的正确上线路径（一条命令流）

# 1. 先在 lnkpi 正常开发并 push（CI 照跑；API 不会自动上线）
cd ~/workspace/lnkpi && git push origin main

# 2. 同步到发布门（只搬源码；deploy.yml 必须保 pi-lnk 版本）
cd ~/workspace/pi-lnk
git fetch upstream
git merge upstream/main --no-commit --no-ff
git checkout HEAD -- .github/workflows/deploy.yml && git add .github/workflows/deploy.yml
grep -c "allow_api_deploy" .github/workflows/deploy.yml    # 必须是 0
git commit -m "merge: sync lnkpi main (API changes)"
git push origin master
# → 自动触发发布门部署（约 7-13 分钟），完成后跑三条验收
# 完整命令流 + 自检 + 故障排查：pi-lnk docs/ops/RUNBOOK-lnkpi-to-pi-lnk-sync.md
# 注意：git checkout --ours  只在路径冲突时有效；用 HEAD -- 更稳（语义相同）

提示：若只想验证前端效果，第 1 步后即可访问 http://119.29.173.89:8888/；只有"前端调了 API 新接口"这类改动才必须走第 2 步，否则会出现前端已上线、接口还是旧版本的错配。

7.1 验收三件套（每次部署后）

7.2 秒级回滚（不重建）

# 路径 ①：切开关止血（最快，不依赖镜像）
ssh deploy-cvm "cd /opt/lnkpi && sed -i 's/^PI_RUNTIME_MODE=.*/PI_RUNTIME_MODE=shadow/' .env \
  && docker compose -f deploy/docker-compose.prod.yml up -d --no-build --force-recreate api"

# 路径 ②：回退到上一个镜像版本
ssh deploy-cvm 'cat /opt/lnkpi/.last-api-image'                       # 取回滚目标 sha
ssh deploy-cvm 'cd /opt/lnkpi && LNKPI_API_IMAGE=lnkpi-api:<旧 sha> \
  docker compose -f deploy/docker-compose.prod.yml up -d --no-build --force-recreate api'
