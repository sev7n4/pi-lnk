## 0. 为什么写这份规格

2026-10-24 真机走查三条反馈，经代码级审计确认全部属实，且比表面更深：

| # | 反馈                         | 代码级根因                                                                                                                                  |
| - | -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| ① | 创建节点为什么单击就默认打开 studio dock | #578 已修掉「新建后自动弹编辑器」；**残留同源另一入口**：`resolveMobileNodeTapIntent` 对无产物节点返回 `editor`（空节点 tap 进编辑 sheet），#578 还给空瓦片加了「点按生成 / 点按撰写」CTA，把违背制度化 |
| ② | 节点管理操作应走长按                 | 长按已是唯一管理入口（#578 删掉双入口），但**操作集不全**（缺保存到本地 / 存入资产库 / 副本含上游）且**不认状态**（生成中可删可编）                                                            |
| ③ | 文本/图片/视频/音频查看后关不回去、没有 X    | 查看器唯一退出是左上角一枚 `‹`（U+2039 细笔画角引号、透明底、无标签）——不是被遮挡（见 §2），是**识别失败**；且无背 scrim、无下滑手势、音频在查看器是死分支                                             |

tap 策略把「空节点 → 编辑器」写成了默认路径。本规格把这条引导语上升为铁律。

## 1. 交互三原则（铁律）

- **P1 单击 = 查看。** 任何类型、任何状态，单击都**不进入编辑**。具体：空节点 / 生成中 / error（无旧产物）单击 = 无 op + 轻提示（引导长按）；**pending / confirmed 单击 = 查看**（pending 看 propose 产出见 §12，confirmed 看产物见 §4）。
- **P2 长按 = 管理。** 所有「对节点自身的管理操作」（编辑 / 重命名 / 引用 / 副本 /  
  多选 / 删除 / 资产库 / 保存本地）只从长按动作 sheet 进，唯一入口。
- **P3 全屏层必须可退。** 查看器与编辑 sheet 都必须同时具备「右上角 X」与「下滑关闭」  
  两条退出通道；退出即停（停播 / 停朗读），进行中的生成提示不丢。
- **P4 载体服从模式（模式① / 模式②，§16）。** 模式①（agent 驱动）下：  
  **查看 = 类型原生查看器**（不是文本节点）、**编辑 = 轻量「提示词 + 意见」编辑器**（不是 PC studio dock 全量参数）、**生成权归 agent**（移动端不出现「生成」钮，改为「发给 agent 修改」）。  
  模式②（用户主动 FAB+）下才允许用户在移动端直接提交生成。

## 2. 「‹ 是不是被遮挡」专项结论

**结论：没有被遮挡，`‹` 一直在屏幕上、可点。** 证据链（全部 master 直读）：

1. 查看器 `position: fixed; inset: 0; z-index: 90`（`MobileNodeViewer.vue:21-30`），  
   且壳层挂载点在 CanvasPage 根级、**画布容器之外**——挂载处注释明示  
   「fixed 定位组件，挂载在容器外避免被画布 transform 影响避让计算」；  
   CanvasPage 根容器（`CanvasPage.vue:5538`，`relative h-[100dvh] overflow-hidden`）  
   无 `transform / filter / will-change / contain` ⇒ **不存在 fixed 包含块陷阱**，  
   查看器确实贴视口。
2. 唯一可能压住屏幕顶部的 fixed 层是 `MobileTopBar`（`z-index: 85 < 90`）⇒ 查看器在其之上。
3. 常驻引导层 `MobileNodeCoachMark` `z-index: 70` 且仅居底部 ⇒ 与顶部无关。
4. `MediaPreviewOverlay` / `MediaInspectorDrawer` 均为 v-if 对话框，查看节点时不挂载。

真实原因是**识别失败 + 无替代通道**（与 #578 之前编辑 sheet 左上「▾」同一失效模式）：

- `‹` 是细笔画角引号字形、透明背景、无文字标签，不像「返回」也不像「关闭」；
- 没有背 scrim——点媒体以外的区域没有任何反应；
- 没有下滑关闭手势；
- 查看器 `type`  prop 含 `audio` 但模板无音频分支 ⇒ 音频一旦进查看器是**死分支**  
  （空白屏只剩 `‹`）。现行 tap 策略把音频路由到磁贴内联，暂未触发，但契约是漏的。

⇒ 修法不是「把 ‹ 挪出来」，而是按 P3 重建退出形态（§4.2）。

## 3. 节点五态与手势门控

五态沿用 D-C 状态机（`resolveMobileNodeState`，优先级 generating > pending > error > 内容）：

| 状态             | 定义                   | 磁贴呈现                        |
| -------------- | -------------------- | --------------------------- |
| empty 空        | 无产物（无 url / content） | 占位 + 「长按编辑 / 长按撰写」CTA（文案见 §8 M1）         |
| generating 生成中 | 生成任务进行中              | 生成态（计时可见，**不造假 0→100% 进度**） |
| pending 待确认    | propose 产出待用户确认      | 待确认态 + 壳层状态栏确认/取消           |
| confirmed 已确认  | 有已确认产物               | 内容 + 属性行                    |
| error 失败       | 生成失败（可能有旧产物）         | 失败态；有旧内容时可看旧内容              |

> 磁贴「提示词（用户填写的 prompt）」在各状态的显示分级、以及改词 / 局部反馈后的贯穿更新，见 §14（评审补充）。

**术语**：
- **壳层状态栏**：画布常驻条（底部 / 顶部），承载生成中「耗时 · 取消」与 pending「确认 · 取消」等协议动作；非动作 sheet，与长按唤起的 Action Sheet（§11）是两回事。
- **propose 协议**：假定 agent 产出经 propose，生成完毕进入 `pending` 待用户确认；自动确认型（跳过 pending 直接 `confirmed`）不在本规格范围。

**总门控表**（本规格的核心判据）：

| 状态         | 单击（tap）                        | 长按（long-press）           |
| ---------- | ------------------------------ | ------------------------ |
| empty      | 无 op + 轻提示「长按编辑 / 长按撰写」          | 全集（裁剪版，§5.2）             |
| generating | 无 op（壳层状态栏可见：耗时 · 取消）          | 受限集（§5.3）                |
| pending    | 查看（看 propose 产出；确认/取消在查看器底部主栏或壳层状态栏） | 全集（编辑 sheet 内含改词入口，见 §12）            |
| confirmed  | 查看（§4）                         | 全集（§5.1）                 |
| error      | 有旧产物 ⇒ 看旧产物；无旧产物 ⇒ 无 op + 提示   | 全集（含重试引导）                |
| 多选态叠加      | 选择模式内：轻点任意节点 = 切换 membership、不开查看器（模式由长按→「多选」进入，进入后全局节点浮现圆圈，D4，§15） | 动作 sheet 多选项变「加入 / 移出多选」；模式内长按同义切换 |

## 4. 查看矩阵（单击）——看什么 / 在哪看 / 如何退出

### 4.1 按类型 × 状态

| 类型 \ 状态 | empty         | generating | pending | confirmed                      | error（有旧产物） | error（无旧产物）   |
| ------- | ------------- | ---------- | ------- | ------------------------------ | ----------- | ------------- |
| 图片      | 无 op + 「长按编辑」 | 无 op       | 查看（§12） | 全屏灯箱：原图 + 「尺寸 · 比例 · 大小」       | 看旧产物（灯箱）    | 无 op + 「长按编辑」 |
| 视频      | 无 op + 「长按编辑」 | 无 op       | 查看（§12） | 全屏播放器 + 属性行                    | 看旧产物（播放器）   | 无 op + 「长按编辑」 |
| 音频      | 无 op + 「长按编辑」 | 无 op       | 查看（§12，内联播放 propose） | **磁贴内联**播放 / 暂停（不离开画布）         | 旧音频可播       | 无 op + 「长按编辑」 |
| 文本      | 无 op + 「长按撰写」 | 无 op       | 查看（§12） | ≤120 字磁贴直显；>120 字全屏阅读器（可朗读、可停） | 看旧文本（阅读器）   | 无 op + 「长按撰写」 |

> **pending 列**：原稿曾写「无 op」，经 §12 修订为 **查看 propose 产出**（音频为内联播放 propose，不进查看器）。确认 / 取消在查看器底部主栏或壳层状态栏，不在此处重复入口。

「无 op + 提示」= 轻 toast（1.5s 自动消失），不进任何全屏层；壳层状态栏已把  
生成中 / 待确认的进度与确认/取消摆在可见处，tap 不重复入口。

### 4.2 查看器退出形态（对标 iOS 原生，P3 落地）

| 通道      | 规格                                              |
| ------- | ----------------------------------------------- |
| 右上角 X   | 44px 触控目标，式样/令牌与编辑 sheet 的 X 完全一致（#578 已建立）     |
| 下滑关闭    | 拖拽超过阈值（建议 100px 或速度阈值）即关；未过阈值回弹取消               |
| 退出即停    | 视频 `pause()` 并复位；朗读立即停止；查看器状态（缩放/滚动）不保留         |
| 背 scrim | 不做——查看器是满幅媒体，没有「外部」可点；X + 下滑两条通道满足 P3           |
| 音频      | **不进查看器**：删除查看器 `type` 中的 `audio`（死分支），音频永远磁贴内联 |

多选态特例：进入选择模式后，画布所有节点浮现圆形选择指示器，**tap 任意节点只切换选区 membership、不开查看器**（D4，§15）；模式内长按同义切换，不再弹单节点动作 sheet。

**音频例外（无查看器）**：音频永远磁贴内联（§4.2 音频行、§11.5），故所有「依赖查看器的能力」对音频改走内联 / 长按动作 sheet：① pending 查看 = 内联播放 propose + 壳层状态栏「确认 · 取消」（不进查看器）；② confirmed 的改词 / 引用 / 副本 / 资产库 / 保存到本地 / 删除 = 全部走长按动作 sheet（§11.5 的查看器「⋯」对音频不适用）；③ §12 的查看器铅笔「改词」、§11.5 的查看器「⋯」均不出现在音频上。

## 5. 操作矩阵（长按）——有哪些 / 执行后如何退出

### 5.1 全集（pending / confirmed / error）

| 操作           | 行为                            | 执行后如何退出                      |
| ------------ | ----------------------------- | ---------------------------- |
| 编辑【模式①】   | **轻量「提示词 + 意见」编辑器**（改词 + 提意见，**无参数、无生成钮**，§16.4） | 右上 X → 回画布（草稿可保留）         |
| 编辑【模式②】   | 最小参数编辑器（提示词 + 模型 / 比例 / 分辨率，§16.4） | 右上 X → 回画布              |
| 重命名          | 动作 sheet 内联输入                 | 确定 / 取消 → 自动关                |
| 引用           | 加入 Agent 引用 + toast           | 选完即关 + toast                 |
| 副本           | 新建副本（落画布）                     | 选完即关                         |
| 副本（含上游）【拟新增】 | 连上游一起复制                       | 选完即关                         |
| 存入资产库【拟新增】   | 图片 / 视频 / 音频产物入库              | 选完即关 + toast                 |
| 保存到本地【拟新增】   | 图片 / 视频下载                     | 选完即关 + toast                 |
| 多选           | 进入「选择模式」：全局节点浮现圆圈，轻点即选（§15） | 底部动作条「全选 / 取消 / 已完成(N)」+ 批量操作（删除 / 引用 / 副本 / 资产库 / 本地）；「完成」退模式 |
| 删除           | **二次确认** → 删除落库               | 确认 → 节点消失回画布；取消 → 留在动作 sheet |

> **模式① / 模式② 的编辑载体不同**（§16）：agent 驱动模式下编辑 = 改词 + 提意见（生成权归 agent）；用户主动建节点模式下编辑 = 最小参数集（生成权归用户）。本表按模式分行，见 §16.6 对照矩阵。

### 5.2 empty 裁剪集

编辑 / 重命名 / 引用 / 多选 / 删除（无产物 ⇒ 副本含上游、存入资产库、保存到本地不出现）。

### 5.3 generating 受限集

| 操作                    | 行为                        |
| --------------------- | ------------------------- |
| 查看参数                  | **模式①**：编辑器内参数只读摘要（§16.4）<br>**模式②**：编辑器只读态；「生成」钮变「取消生成」 |
| 取消生成                  | 停止生成，磁贴回 error / empty    |
| 重命名 / 多选              | 允许                        |
| 删除                    | 默认禁止（见拍板项 B）              |
| 引用 / 副本 / 资产库 / 保存到本地 | 禁止（产物未定）                  |

## 6. 单节点生命周期时间线

| 阶段      | 界面呈现                           | 用户可做什么                        | 如何退出该层                  |
| ------- | ------------------------------ | ----------------------------- | ----------------------- |
| 1 创建    | ＋FAB → 新建 sheet → 选类型 → 空节点落画布（**模式②**）；**模式① 由 agent propose 建节点** | 模式②：选类型；模式①：无需创建 | 新建 sheet 选完即关；**不弹编辑器** |
| 2 撰写    | **模式①**：撰写发生在**对话页**（原始创作意图），画布侧只见 agent 写的提示词<br>**模式②**：长按空节点 → 编辑 sheet | 模式①：见提示词（只读 / 可改词）；模式②：写提示词 | 右上 X → 回画布              |
| 3 生成中   | 磁贴生成态 + 壳层状态栏（耗时 · 取消）         | 取消生成；查看参数（只读）                 | 无需退（磁贴态可见）              |
| 4 待确认   | 磁贴待确认态 + 壳层状态栏（确认 · 取消）        | 确认 / 拒绝                       | 无需退                     |
| 5 已确认   | 磁贴落内容 + 属性行                    | tap 查看 / 长按全集管理               | 见 §4 / §5               |
| 6 改词重生成 | **模式①**：长按 → 编辑 → 改词 + 意见 → **发给 agent 修改** → agent 重新生成<br>**模式②**：编辑 sheet → 改词 → 提交生成<br>（或 pending/confirmed 查看器内点「改词」铅笔，§12.3/§12.4） | 模式①：同阶段 2 但终态是「意见回传对话」<br>模式②：同阶段 2 | 模式①：提交后回画布，磁贴转生成中（旧产物淡化 + 提示词 chips 更新，见 §14.3）<br>模式②：同阶段 2 |

> **模式①/② 的分工见 §16**：模式① 生成权归 agent（画布页 = 观察 + 表态），模式② 生成权归用户（画布页 = 创作）。本表按模式分列，避免把两套心智混成一套。

## 10. 五态状态机 × 生命周期——关系、边界与最合理设计（评审补充）

> 本节回应评审问题：五态（D-C 状态机 + 多选）与生命周期七阶段的关系与边界、是否维持一套 / 一一对应、如何设计最合理。

### 10.1 本质：两个正交维度，不是一套、也不一一对应

| 维度                  | 是什么                   | 视角      | 回答的问题              | 稳定性                   |
| ------------------- | --------------------- | ------- | ------------------ | --------------------- |
| **五态（D-C 状态机）+ 多选** | 节点的「内容生产状态」+ 画布「选择模式」 | 系统 / 数据 | 节点现在是什么、现在能做什么     | 节点固有属性，跨生命周期持久、可跨会话还原 |
| **生命周期七阶段**         | 用户的「任务流」              | 用户 / 任务 | 用户走到哪了、下一步该什么、节点存亡 | 一次性、有向，随用户操作推进        |

- 五态 = **硬真相源**：驱动呈现、手势门控（tap / long-press 可用性）、操作集可用性（§3 总门控表）。
- 生命周期 = **外层软维度**：驱动引导（新建后提示）、先后次序（先有节点才有生成）、存亡语义（创建 / 删除边界）。**不进入 §3 门控表**。
- 多选态 = **第三个正交维度「选择模式」**（关 / 开（多选）），叠加在五态之上（§3 末行「多选态叠加」），既不是内容状态也不是生命周期阶段；「开」后即进入可批量选取的模式（§15），不存在独立的「单选态」。

### 10.2 七阶段 → 五态映射（证明「不一一对应」）

| 生命周期阶段  | 映射到的五态                     | 性质                             |
| ------- | -------------------------- | ------------------------------ |
| 1 创建    | 节点诞生事件 → empty             | **边界事件（生命周期独有）**，非状态           |
| 2 撰写    | empty                      | 用户动作（写提示词），节点状态未变              |
| 3 生成中   | generating                 | 与状态机同名态                        |
| 4 待确认   | pending                    | 与状态机同名态                        |
| 5 已确认   | confirmed                  | 与状态机同名态                        |
| 6 改词重生成 | confirmed → generating（回边） | 状态机**回边**，非新状态                 |
| 7 删除    | 节点消亡事件                     | **边界事件（生命周期独有）**，五态无对应（删后即不存在） |

⇒ 关系是一**对多**（empty 同时覆盖阶段 1+2；generating 同时覆盖阶段 3+6）+ **缺失**（删除在五态无位置）。硬做一一对应必然失真——要么把「撰写」误当成状态、要么让「改词重生成」与「生成中」争同一格。

### 10.3 边界划分（最合理设计）

1. **维持双模型分层，不合并、不一一对应。**
2. **生命周期收敛为四语义**：诞生（创建）/ 撰写动作 / 生成-确认循环（由状态机表达，不当并列阶段）/ 消亡（删除）。§6 的真正信息只有「两个边界事件 + 一个动作 + 一个循环」。


3. **以五态为交互门控唯一真相源**（§3 总门控表保持不变）；生命周期只驱动 §1 的引导语与入口先后次序。
4. **往返由状态机回边表达**：「改词重生成」= confirmed → generating，生命周期不另设阶段。
5. **删除是生命周期终点边界事件**，不在五态中占一位；删除语义（二次确认、落库、节点消失）在 §5.1 / §8(M2) 处理。

### 10.4 落到本规格的修订点

- §3 门控表 = 状态机 × 选择模式，维持（已是交互硬真相源）。
- §6 定位从「与五态并列的七阶段」改为「用户任务流：由五态驱动的状态穿越 + 两个边界事件（创建 / 删除）」。
- 新增本节 §10 作为两模型边界判据，供 §9 拍板时一并确认。

## 11. 操作全集归类与跨平台形态（评审补充）

### 11.1 iOS / Android 多操作的设计范式
- **iOS HIG**：对象有多个操作时，标准范式是 **Action Sheet（底部上拉动作面板）**——长按或「⋯」触发，列出全部相关操作；**破坏性操作用红色按钮**；配一个 Cancel。iOS 13+ 另提供 **`UIMenu` 下拉菜单**（按钮挂「⋯」/文字，点开是菜单列表），适合聚合而非模态打断。
- **Material（Android）对等**：**Modal Bottom Sheet** + **`⋮` 溢出菜单**，与 iOS Action Sheet 语义一致、用户均熟悉。
- **跨平台统一结论**：采用**底部 Action Sheet** 作为唯一操作容器——iOS/Android 原生都支持、认知一致、不引入平台专属控件。**不**在卡片上铺多个胶囊/文字按钮（拥挤、与「单击=查看」冲突、跨平台不一致）。

### 11.2 操作全集按「频率 × 风险」归类
| 操作 | 频率 | 风险 | 在 sheet 中的处理 |
| --- | --- | --- | --- |
| 编辑 | 高 | 无 | 置顶首项 + 图标，视为默认主操作 |
| 重命名 | 中 | 无 | 列表项 |
| 引用 | 中 | 无 | 列表项 + toast |
| 副本 | 中 | 无 | 列表项 |
| 副本（含上游） | 低 | 无 | 列表项（拟新增，M2） |
| 存入资产库 | 低 | 无 | 列表项（拟新增，M2） |
| 保存到本地 | 低 | 无 | 列表项（拟新增，M2） |
| 多选 | 中 | 无 | 列表项（进入 / 加入多选态） |
| 删除 | 低 | 高（破坏性） | **置底、红色、二次确认**（iOS destructive 范式） |
| 取消生成 | 仅 generating | 中 | 上下文项（仅 generating 出现） |
| 查看参数 | 仅 generating | 无 | 上下文项（仅 generating，只读） |

### 11.3 形态与位置原则
1. **唯一容器 = 底部 Action Sheet**（iOS Action Sheet / Android Modal Bottom Sheet），所有管理操作聚合，符合 P2 长按唯一入口。
2. **频率分层在 sheet 内体现**：高频（编辑）置顶；低频平铺；破坏性（删除）置底红色。
3. **不铺胶囊按钮**：卡片保持极简（仅内容 + 属性行），避免与「单击=查看」冲突，跨平台一致。
4. **画布双入口（可选）**：若长按在真机 discoverability 不足，卡片右上角加「⋯」图标（`UIMenu` / `⋮` 等价），与长按**同源同容器**（避免 #578 双入口分裂）。待拍板（§9-E）。**查看器内的「⋯」为必带**，见 §11.5。
5. **退出一致性**：sheet 内操作执行完即关（§5 已定），删除走二次确认子层。

### 11.4 是否要写进规格
是——跨平台形态原则是评审稿必含的设计判据，明确后实现期各操作形态不再随意。

### 11.5 查看器内的操作入口（沉浸态不退出）

- **查看器（全屏）右上角与 X 并列放一枚「⋯」，必带**，且与画布「⋯」**同源同容器**（同一组件、同一操作集定义，避免 #578 双入口分裂）。理由：全屏沉浸查看时用户随时可能「引用 / 存本地 / 副本 / 改词」，若强制先退出查看器再长按，会打断播放流——iOS Photos 全屏右上「⋯」即此范式。
- **查看器操作集 = 内容强相关裁剪子集**：引用 / 副本 / 副本含上游 / 存入资产库 / 保存到本地 / 改词重生成（编辑）/ 删除。**不含**多选、重命名（二者为画布态语义，查看器是单节点全屏，无批量上下文）。**音频无查看器**（§4.2），此裁剪子集对音频不适用，音频管理全走长按动作 sheet（见 §4.2 音频例外）。
- **不退出查看器**：点「⋯」开 Action Sheet 覆盖于查看器之上（更高 z 层），底层媒体保持（或轻暂停、关 sheet 即恢复）；选非删除操作后关 sheet 回查看器继续查看 / 播放。仅「删除」关闭查看器（节点已不存在）。这与 P3「退出即停」不冲突——P3 的「停」只在真正退出查看器（X / 下滑）时触发。
- **不建议「仅放提示词编辑」**：编辑是跳编辑 sheet，查看器高频需求是内容相关操作（引用 / 存本地 / 副本），编辑价值低；且只放编辑会漏掉其他内容操作，操作集不对称。

## 12. pending（待确认）态专项：查看 + 高频编辑 / 引用（评审补充）

### 12.1 当前缺口
原 §3 / §4.1 把 pending 态 tap 设为「无 op」，等于**剥夺用户查看 propose 产出的权利**——用户被迫在「确认 / 取消」间二选一，却看不到 agent 生成了什么。这违背「确认前应先看」的基本产品逻辑，也是 D3（单击不认状态）的残留。

### 12.2 修正：pending 态必须先能查看
- **磁贴**：保持待确认态 + 壳层状态栏「确认 · 取消」（propose 协议主入口，不另铺按钮）。
- **tap → 进查看器，看 propose 产出**（§4.1 pending 列修订为「查看」）；**音频例外**：音频无查看器，pending 查看 = 内联播放 propose + 壳层状态栏「确认 · 取消」（见 §4.2 音频例外）。
- 查看器内分两层：**决策层**（确认 / 取消）+ **操作层**（改词 / 全集）。
- 确认 / 取消同时出现在「壳层状态栏」与「查看器底部主栏」，两处一致、非重复——前者是画布态常驻入口，后者是沉浸态入口。

### 12.3 查看器内布局（pending 态）
- **底部主操作栏（仅 pending）**：「取消（拒绝）」「确认」——propose 核心，必须醒目；确认即落 confirmed，取消即丢弃 propose。
- **右上高频图标「改词」（铅笔）**：进**轻量编辑器**（模式①：提示词 + 意见，**无参数 / 无生成钮**，§16.4）改词。改词与确认互斥——改词不触发确认，视为放弃当前 propose、把修改意见回传 agent（模式②下才是本地提交生成）。
- **右上「⋯」**：全集（引用 / 副本 / 副本含上游 / 存入资产库 / 保存到本地 / 删除）。
- **引用**：保留在「⋯」内（第二高频但属轻动作，不升常驻图标，避免右上四图标拥挤，违背 §11.3 简洁原则）。若真机走查发现引用发现性不足再升级。

### 12.4 confirmed 态查看器（对照）
- 右上 = X + 「改词」（铅笔，高频）+ 「⋯」（含引用）。**无底部确认栏**（已确认）。
- 即「改词」高频图标在 pending 与 confirmed 查看器都常驻；仅 pending 多底部确认 / 取消栏。
- **查看器内置标注层（§16.3）**：图片圈选区域 / 视频暂停圈当前帧 / 音频波形拖段 / 文本拖选段落 → 生成引用块 → 回 composer（模式①的主闭环）。

### 12.5 本体是否铺高频按钮
**不铺。** 理由（§11.3 第3点克制原则）：
- pending 本体的「确认 / 取消」已由壳层状态栏承载，无需额外按钮；
- confirmed 本体保持极简（内容 + 属性行），改词 / 引用走长按 / 「⋯」（§9-E 拍板是否显式「⋯」）；
- 在每张卡片铺「编辑」「引用」会拥挤、与「单击=查看」冲突、跨平台不一致。
- **结论**：高频图标只进查看器（全屏有空间），本体不铺。

### 12.6 是否需单独评审
是——pending 态「查看 + 高频编辑 / 引用」是此前规格盲区，本节即专项评审结论，纳入 §9 拍板一并确认。

## 13. 基于产物的迭代协作：圈选 / 批注 / 局部引用（评审补充）

### 13.1 当前覆盖度盘点
| 环节 | 当前规格 | 缺口 |
| --- | --- | --- |
| 查看产物 | §4（confirmed tap = 查看） | 无 |
| 审核确认 | §12（pending 确认 / 取消） | 无 |
| 整体改词重生成 | §5.1 编辑 sheet + §12.3 查看器改词图标 | 无 |
| 提出意见 / 圈选局部 | —— | **盲区** |
| 局部引用到 composer | 仅节点级引用（§5.1） | **缺片段级引用** |
| agent 基于反馈重生成 | 改词重生成（整体） | **缺局部反馈驱动** |

⇒ 当前规格覆盖了「查看 → 整体改词 → 重生成」的线性闭环，但**未覆盖「在查看中对产物做局部标注、把局部引用给 agent、驱动迭代」这一协作层**。文本圈选段落、图片圈选元素、视频圈选帧、音频选段，均属此层。

### 13.2 两个迭代粒度
- **整体粒度（已覆盖）**：改词重生成——不看细节，整体换提示词。
- **局部粒度（待补）**：片段 / 区域级标注——圈选文本段、图片区域、视频帧元素、音频时间段，附带意见，引用给 agent。

### 13.3 各类型局部标注设计
| 类型 | 圈选 / 标注形态 | 引用去向 | 改意见入口 |
| --- | --- | --- | --- |
| 文本 | 拖拽圈选段落（原生文本选择） | composer 侧栏（片段引用块） | 圈选后浮层「引用此段 + 输入意见」 |
| 图片 | 查看器内矩形 / 套索圈选区域 | composer 侧栏（区域截图引用块） | 圈选后浮层「引用此区域 + 意见」 |
| 视频 | 暂停后圈选当前帧元素 | composer 侧栏（帧 + 区域引用块） | 同上 |
| 音频 | 选时间段（波形拖选） | composer 侧栏（时间段引用块） | 同上 |

### 13.4 统一交互流
1. 查看器内进入「标注态」（文本长按选 / 图片圈选工具 / 视频暂停圈选 / 音频拖段）。
2. 松手弹轻浮层：「引用到对话」+「附修改意见」（输入 / 语音）。
3. 确认 → 局部片段作为引用块进 **composer 侧栏**（agent 上下文），用户补意见后发送。
4. agent 基于「局部引用 + 意见」重生成（更新该节点或产新节点，由产物类型定）。
5. 退出标注态回查看器。

### 13.5 与现有机制的关系
- **不改 §11 容器范式**：圈选是查看器内叠加编辑态，非 Action Sheet；「⋯」/ 改词图标仍在。
- **引用粒度二分**：节点级引用（§5.1，整节点）与片段级引用（本节，局部）并存；composer 侧栏两种引用块样式不同。
- **与改词并存**：改词 = 整体换提示词；圈选迭代 = 局部反馈。查看器内两者都可触发。

### 13.6 是否含进规格 / 排期
是——这是「生成后协作迭代」核心闭环，此前盲区，本节补入。实现排期待 §9-F 拍板（推荐 F1 与引用 / 操作集同批 M2）。

## 14. 磁贴提示词显示与改词 / 反馈驱动的贯穿更新（评审补充）

### 14.1 当前缺口
规格 §3 的「磁贴呈现」列只描述了每状态的视觉态（占位 / 生成态 / 待确认态 / 内容 / 失败态），**从未定义「提示词（用户填写的 prompt）在磁贴上是否显示、显示到哪几个状态」**。这是与用户迭代工作流直接相关的盲区：用户「查看产物 → 提意见 → 改词 / 局部反馈 → 重生成」的整个闭环都依赖「能随时回看当初的提示词、并能看到提示词随迭代演进」。

### 14.2 磁贴提示词显示分级（贯穿全部存在性状态）
提示词是「产物的来由」，应在节点存在的全周期可回看，但呈现分级，不与产物争主位：

| 状态 | 磁贴提示词呈现 | 理由 |
| --- | --- | --- |
| empty / 撰写 | **主内容**：提示词文本（或撰写占位）填满磁贴 | 无产物，提示词即唯一内容 |
| generating（首生成） | **主内容** + 生成指示（无产物） | 同空态，等待产物 |
| generating（改词 / 反馈重生成，有旧产物） | 旧产物**淡化** + 「重新生成中」角标 + 提示词 chips 可见 | 保留视觉锚点不闪空；提示词 chips 让用户看清「在基于什么重生成」 |
| pending | 产物预览为主；提示词 chips（可点展开） | 决策层看产物，提示词降级可回看 |
| confirmed | 产物为主；提示词 chips（落查看器可展开全文 + 历史） | 产物是主角，提示词常驻轻量回看 |
| error（有旧产物） | 旧产物 + 失败角标；提示词 chips | 同 confirmed |
| error（无旧产物） | 同 empty | —— |

**原则**：提示词在「无产物态」是磁贴主内容；在「有产物态」降级为一行可点的「提示词」chips——不占满磁贴、不喧宾夺主，单击 chips 在查看器内展开全文（及迭代历史，M3 可选）。这样既保持画布简洁，又让迭代工作流随时可取「来由」。

### 14.3 改词 / 局部反馈后，磁贴如何贯穿更新
当用户对已确认节点提修改意见（整体改词 §5.1 / 局部圈选引用 §13），节点回到生成循环，磁贴必须随之重渲：

1. **confirmed → generating**：磁贴从「产物」转「旧产物淡化 + 重新生成中角标」；若提示词被改（整体改词），chips 同步更新为最新提示词；若是局部反馈（§13），提示词本身不变，但附加「含 N 处局部反馈」标记。
2. **generating → pending**：磁贴转待确认态（§3 pending 行），产物预览为 propose 产出，提示词 chips 保持。
3. **pending → confirmed（确认）**：磁贴落新产物 + 属性行，提示词 chips 常驻。
4. **pending → generating（改词放弃 propose）**：回到第 1 步。
5. **generating → error**：转失败态（§3 error 行），旧产物可看、提示词 chips 保持。

⇒ **磁贴内容确实会更新，并完整贯穿 `confirmed → generating → (pending) → confirmed` 的状态链**；提示词显示按 §14.2 分级随之升降级。这是「生成—审核—迭代」闭环在磁贴上的落地，必须显式定义——否则实现期磁贴在重生成时会闪空、或丢失提示词上下文，用户看不到「在基于什么重生成」。

### 14.4 提示词迭代历史（M3 可选，仅记录）
多次改词 / 反馈后，单条提示词 chips 可展开「提示词 v1 / v2 / …」与对应产物版本，支持对比回滚。属 M3 固化范围，本节仅记录，不进 M1 / M2。

### 14.5 是否含进规格
是——磁贴提示词显示与重生成贯穿更新是此前盲区，本节补入；并修订 §3「磁贴呈现」列注脚、§6 阶段 6 以引用本节。拍板见 §9-G。

## 15. 多选「选择模式」视觉与交互（评审补充）

### 15.1 用户痛点（当前实现的坏交互）
进入多选后，要继续选第二个节点仍需「回画布 → 找节点 → 长按 → 弹动作 sheet → 点多选」，每加一个节点都走一遍长按动作 sheet。这违背多选直觉——多选应是一条「进入模式 → 逐个轻点」的直线，而不是「每节点都要重新唤起管理菜单」。

### 15.2 正确设计：selection mode（对标 iOS 照片多选）
1. **进入**：长按节点 → 动作 sheet → 点「多选」；或（若 §9-E2）节点「⋯」→「多选」。点下即进入「选择模式」。
2. **全局视觉信号**：进入选择模式**瞬间**，画布上**所有节点本体右上角浮现一枚圆形选择指示器**（未选 = 空心圆，已选 = 实心 + 对勾），磁贴其余外观不变。这是模式切换的强信号，也是唯一需要用户「发现」的入口——之后纯靠轻点，无需再长按。
3. **模式内单击 = 切换 membership**：在模式内点任意节点（已选 / 未选皆可），仅切换其选中态，**不开查看器、不弹动作 sheet**（落实 D4 + §3 多选态叠加 + §4.2）。即用户描述的「手指点想多选的节点，单击完成多选」。
4. **模式内长按的处理**：模式内长按节点**不再弹单节点动作 sheet**（避免退回单节点管理语境），与单击同义 = 切换选中。推荐「长按同义切换」，降低认知负担。
5. **底部动作条**：模式内画布底部出现动作条，含「全选 / 取消（退出模式）/ 已完成(N)」；当已选 ≥1 时展开批量操作（删除 / 引用 / 副本 / 存入资产库 / 保存到本地，按 §5 全集裁剪）。点「完成」退出模式回普通画布。
6. **退出**：底部「取消」或「完成」；或点画布空白区（若实现允许）。退出后节点恢复普通呈现，圆圈消失。

### 15.3 与现有条款对齐
- §3 多选态叠加：单击 = 切换 membership（已定，本节补「全局圆圈 + 模式内长按同义」）。
- §4.2：多选激活 tap 不开查看器（已定，本节补「长按也不弹 sheet」）。
- §5.1：多选「进入 / 加入多选态；选完即关；多选经底部动作条『完成』退」——本节明确底部条内容与「轻点即选」。
- §11.5：多选是画布态语义，查看器不含（已定）。
- §12.5：多选属画布批量语义，本体不铺高频按钮（已定）。

### 15.4 是否含进规格
是——选择模式视觉（圆圈）与「轻点即选」此前仅在 §3 / §4.2 隐式、未显式设计；本节点用户直指的坏交互必须显式纠正。拍板见 §9-H。

## 16. 移动端两种协同模式与「查看 / 编辑 / 生成」载体分工（评审补充 · 核心专题）

> 本节回应评审问题：移动端节点交互分两种模式（① agent 驱动画布、② 用户主动 FAB+ 手工建节点）；重点是模式①。**点击图片 / 视频 / 音频节点查看，载体是不是文本节点？编辑是不是文本节点？生成交给 agent 还是接 PC 的厚重 studio dock？**

### 16.1 两种模式的定位（本规格只重点覆盖模式①）

| | **模式① agent 驱动画布** | **模式② 用户主动与画布协同** |
| --- | --- | --- |
| 发起方 | 用户在**对话页**写原始创作意图 → agent 推理 → 调用工具驱动画布创建 / 生成 | 用户在**画布页**点 FAB+ → 手工建节点 → 填提示词 → 生成 |
| 产物 | agent 提议（propose）卡片 + 画布上节点实时演进 | 画布上用户自建节点 |
| 移动端定位 | **主战场**（本规格重点） | **次要**（用户明确：此能力主要在 PC 实现） |
| 生成执行者 | **agent**（对话页发起，工具执行） | 用户自己（画布上提交） |
| 移动端要解决的问题 | ① 切到画布**显性看到**生命周期 ② 看产物 → **标记 / 截图 → 定位锚 → 回 composer 芯片** → 在对话里提意见 → agent 再生成 | 简化版：建节点 + 提示词 + 生成 |

⇒ **模式②在移动端保持最简**（选类型 → 填提示词 → 生成），不追求 PC 全量参数；**模式①才是移动端的设计重心**。

### 16.2 模式① 的真实使用链路（用户口述 + 代码事实）

```
对话页：用户写「做一张赛博朋克风格的城市夜景」
   ↓ agent 推理 → 调用工具 → 画布上 propose 建节点（pending_confirm）
对话页：SSE 主动生成「提议生成卡片」→ 卡片带「定位」按钮
   ↓ 用户点定位 → 切到画布页，画布上该节点被聚焦闪烁
画布页：用户 tap 图片 / 视频 / 音频节点 → 进入查看
   ↓ 在产物上标记 / 截图 → 生成「定位锚」引用块
   ↓ 定位锚 → 带回对话页 composer 芯片
对话页：用户对芯片提修改意见 → agent 重新生成 → 节点回到画布
```

**这条链路的三个载体问题**（用户直接提问）：

| # | 问题 | 判决（§16.3–16.5） |
| --- | --- | --- |
| Q1 | 查看载体是不是一个「文本节点」？ | **不是**——查看器是**类型原生的媒体查看器**，不是文本节点（§16.3） |
| Q2 | 编辑的也是文本节点吗？ | **编辑 = 文本（提示词）载体，但执行者是 agent**——移动端不做 PC studio dock 全量参数（§16.4） |
| Q3 | 生成交给 agent，还是接 PC studio dock？ | **模式①：生成权归 agent**，移动端只做「改词 + 提意见 + 回传」；studio dock 只在模式②以最小集出现（§16.5） |

### 16.3 裁决一：查看载体 = 类型原生查看器（不是文本节点）

**判决：查看器不是文本节点，是「按类型原生的全屏媒体查看器 + 一层可标注」。**

- **图片**：全屏灯箱（可缩放 / 双指放大）+ 属性行（尺寸 · 比例 · 大小）+ **可圈选标注层**（矩形 / 套索）。
- **视频**：全屏播放器（播放 / 暂停 / 逐帧）+ 属性行 + **暂停后对当前帧圈选标注**。
- **音频**：**不进查看器**（§4.2 音频例外），磁贴内联波形播放 + 波形拖选时间段。
- **文本**：全屏阅读器（≤120 字磁贴直显）+ **可拖选段落**。

**为什么不复用「文本节点」当查看载体**（这是用户提问里的关键岔路）：

1. **能力不等价**：图片要缩放、视频要逐帧、音频要波形、时间轴——文本节点承载不了，只能退化成"一个链接"，等于把 agent 生成的产物降级。
2. **违背 agent 驱动初衷**：模式①的产品价值恰恰是「**看得见产物本身**」，让用户对一张图说"这栋楼太亮"——必须看到图。
3. **已有实现方向一致**：R1-R4 已经把移动端查看器做成类型原生（`MobileNodeViewer` 分 img / video / text），继续这条线即可，不必推翻。

**查看器必须新增的一层：标注（annotation）**——这是模式①闭环的关键缺口：

- 现有 `annotateModel.ts`（PC：画笔 / 矩形 / 文本 / 马赛克 / 水印 / 签名）**只做像素标注，不做「引用回对话」**；移动端需要的是**「圈选 → 生成引用块 → 回 composer」**，两者目的不同（前者改图，后者反馈 agent）。
- 因此新增概念：**标注片段（annotation fragment）** = `{类型, 节点 id, 区域坐标 / 时间区间, 截图 blob, 附带意见文本}`。
- 落地形态：
  - **图片**：矩形 / 套索圈选 → 松手浮层「引用此区域 + 意见」→ 生成**区域截图**（可复用 PC `refine/cropExport.ts` 的 `renderCropBlob` 把区域裁成 PNG blob ⇒ 引用块自带截图，无需另存）。
  - **视频**：暂停 → 对当前帧圈选 → 裁出该帧截图 + 携带时间码。
  - **音频**：波形拖选时间段 → 携带时间区间（无截图）。
  - **文本**：拖选段落 → 携带选中文本。
- 引用块进 composer 的载体 = **既有 composer 引用芯片体系**（`useSidebarAttachments` 的 `pendingAttachments` **已是模块级单例**，`useCanvasRefPickAdd` 是单一真源 ⇒ 画布页 → 对话页跨页携带**天然可行**，与 #571 修复同一条通路）。

### 16.4 裁决二：编辑载体 = 文本（提示词），但**不是 PC studio dock**

**判决：模式① 的编辑 = 「提示词文本 + 我的意见」两栏轻量编辑器；不接 PC studio dock 全量参数。**

**理由（关键）**：

1. **模式①的生成权不在用户手里，在 agent 手里**。用户点「生成」时，agent 已经在 propose 里定了模型 / 比例 / 分辨率 / 参考图（服务端 `proposeGeneration` 写入 `imageModel` / `imageAspect` / `imageResolution` / `videoSettings`）。用户在移动端再调这些参数 ⇒ **两套参数语义打架**（谁的为准？）。
2. **移动端做全量参数是不合格的交互**：PC studio dock = 6 个 panel + 12 个 shared ≈ **4800 行**，含模型选择器 / 比例 / 分辨率 / 张数 / 种子 / 视频时长 / 音色 / 积分徽标。窄屏上做这些必然拥挤，且 #578 走查⑥ 已经实证过：参数选择器在移动端**根本弹不开**（PC popover 包含块陷阱 + `overflow:hidden` 裁剪），最后是靠 `:deep()` 打补丁才勉强贴底卡片。
3. **agent 驱动的心智是"我说，你做"**：用户在对话页说「改成夜景风格」，agent 调工具重新生成——这才是模式①的价值。移动端画布页的角色是**看清 + 标注 + 表态**，不是**配参数**。
4. **文本是最自然的意见载体**：改词 = 文本（`node.data.prompt`），提意见 = 文本，两者都在同一处输入，天然可与 composer 的对话意见合并。

**模式① 轻量编辑器结构（`MobileNodeEditorSheet` 应改造为）**：

| 区 | 内容 |
| --- | --- |
| 提示词区（可编辑） | `node.data.prompt` 全文（改词）—— 已有字段，无需新契约 |
| 意见区（可编辑） | 「你想让 agent 怎么改」（自由文本） |
| 参数区 | **只读摘要一行**（模型 · 比例 · 分辨率），不可改；带「让 agent 改」提示 |
| 引用区 | 节点引用 chips（已有 `NodeRef` 体系） |
| 提交按钮 | **「发给 agent 修改」**（不是「生成」）——把改后提示词 + 意见 + 引用块回传对话页 composer |

**模式② 的编辑（次要，最小集）**：类型 + 提示词 + 生成按钮；参数保持默认（模型 / 比例可后置到 M3）。**明确不在移动端做 PC 全量参数。**

**这条判决对现有实现的影响（必须记录）**：移动端 `MobileNodeEditorSheet.vue` 现在**直接复用 PC 的 `DockStudioRouter`**（全量参数面板）。按本判决，模式① 下应**不再复用**——改为独立的轻量编辑器；模式② 也只取最小子集。⇒ 新增缺陷 **D8：移动端编辑载体与模式不匹配**（详见 §17）。

### 16.5 裁决三：生成归属

| | 模式① agent 驱动 | 模式② 用户主动 |
| --- | --- | --- |
| 谁发起生成 | **agent**（对话页发起，工具执行） | 用户（画布页提交） |
| 移动端节点上的「生成」按钮 | **不出现**（改为「发给 agent 修改」） | 出现 |
| 用户表达意图的地方 | **对话页 composer**（含引用芯片） | 画布页编辑器 |
| 画布页的角色 | **观察 + 表态**（看产物、标注、提意见） | **创作**（建节点、写提示词、提交生成） |

**为什么模式①不能在移动端放「生成」按钮**：

- **违背提议协议**：`proposeGeneration` 把节点置为 `pending_confirm`（服务端硬守卫：客户端无权把 `pending_confirm` 翻成终态）。用户在移动端直接点「生成」= 绕过 propose 确认语义，与 PC 行为分叉。
- **产生双执行路径**：同一节点可能既被 agent 重生成、又被用户手动生成 ⇒ 状态归属混乱（`generating` / `pending_confirm` 谁在跑）。
- **丢失对话上下文**：用户此刻在画布页，他的修改意见只有回到对话页才有效（agent 只看对话 + 引用）。在画布页生成 ⇒ agent 这轮不知道用户改了什么，下一轮回复会与画布状态脱节。

⇒ **模式① 移动端节点的终态是「把意见交给 agent」，不是「自己生成」。** 这与 §13（局部迭代协作）天然合流：圈选 → 引用块 → composer → 对话提意见 → agent 再生成，**闭环完全在对话页收口**。

### 16.6 载体分工总表（模式① 为准）

| 角色 | 载体 | 形态 | 谁执行 |
| --- | --- | --- | --- |
| 查看 | **类型原生查看器** | 灯箱 / 播放器 / 阅读器 / 波形内联 | 用户（只读） |
| 标注 | **查看器内标注层** | 圈选 / 框选 / 拖段 / 选段 | 用户 |
| 编辑 | **轻量编辑器**（提示词 + 意见） | 全屏 sheet，**无参数编辑** | 用户填写 |
| 意图提交 | **composer 引用芯片 + 对话** | 跨页携带（`pendingAttachments` 单例） | 用户 |
| 生成 | **agent 工具调用** | 对话页 | agent |

### 16.7 与既有条款的冲突修订（本节带来的连带改动）

| 条款 | 原内容 | 修订后 |
| --- | --- | --- |
| §5.1 编辑 | 「全屏编辑 sheet（撰写 / 改词 / 参数 / 生成）」 | 拆为模式①（轻量编辑器，**无参数 / 无生成钮**）/ 模式②（最小参数集） |
| §6 阶段 2 撰写 | 「长按空节点 → 编辑 sheet」 | 模式① 下空节点由 agent 创建并 propose ⇒ 撰写发生在**对话页**；画布页的空节点撰写属模式② |
| §6 阶段 6 改词重生成 | 「长按 → 编辑 → 改词 → 重新生成」 | 模式① 改为「改词 + 意见 → **发给 agent 修改** → agent 重新生成」 |
| §12.3 / §12.4 改词铅笔 | 「直接进编辑 sheet 改词重生成」 | 模式①：进轻量编辑器，改完**发给 agent**（不自行生成） |
| §13 局部迭代 | 圈选 → 引用块 → composer → agent 重生成 | **维持**——本节确认它就是模式①的主闭环，并补齐载体细节（§16.3） |
| §5.3 generating 受限集 | 「查看参数 → 编辑 sheet 只读态」 | 模式① 下编辑 sheet 无参数 ⇒ 该项**仅模式② 保留** |

### 16.8 是否含进规格 / 排期

是——这是模式① 的**结构性判决**，此前规格把「移动端编辑 = PC studio dock 全量」当既定事实（`MobileNodeEditorSheet` 直接复用 `DockStudioRouter`），与 agent 驱动模式的心智冲突。纳入 §9 拍板（I / J / K 三项），并新增缺陷 **D8**（见 §17）。
