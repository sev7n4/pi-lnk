**版本号约定（语义化）：**

- `MAJOR` —— 规格结构或范围发生重大变化（如新增/删除整条设计原则、拆分文件）。
- `MINOR` —— 增删条目、补充子任务、调整严重度归属。
- `PATCH` —— 措辞修正、验收判据补强、基线数据更新，**不改变任务集合**。

每次更新在文末 **§8 变更日志** 追加一条，并同步 bump 顶部版本号。改动一律**原位更新**（In-place），不另存历史文件；历史靠 git 跟踪。

**验收判据纪律（沿用 `spec-driven-doc-hardening`）：**

1. 判据卡**类别**，不卡具体值（例：不写「grep 不到 2.59」，写「任何引导文字对比度 ≥ 4.5:1」）。
2. 写进规格的每条事实都已在 §3 用 `文件:行号` 标注来源，并尽量经两种路径核实。

## 1. 目标与范围

**目标：** 在保持 lnk π composer 已领先同行的功能完备度（流式插话队列、引用芯片、双层 mention 高亮）前提下，把「同时做 9 个决定」的交互密度，收敛为「每个时刻只做一个决定」的分层、克制、可自解释形态，并补齐基础可用性与正确性（键盘契约、对比度、主题阴影、触控目标）。

**范围（本规格负责）：**

- `apps/web/src/components/agent/AgentSideRail.vue`（面板外壳 + 输入 dock + 空态 + 引导文案）
- `apps/web/src/components/canvas/MentionInput.vue`（输入控件 + 候选菜单语义）
- `apps/web/src/components/canvas/dock-studio/shared/{DockGenerateButton,DockMicButton}.vue`（发送 / 语音）
- `apps/web/src/components/canvas/dock-studio/panels/SceneComposerDockPanel.vue` 及模型/技能选择器相关组件
- `apps/web/src/constants/agentSkillMap.ts`（占位符、技能清单）
- `apps/web/src/styles/neowow-tokens.css` / `design-tokens.css`（令牌修正与守卫）
- `apps/web/src/composables/useAgentMobileLayout.ts`（移动端断点形态）

**不在范围（Out of Scope）：**

- 消息流内部渲染（气泡、执行轨迹、时间线、产物卡片）—— 仅 §5.4 产出发票作为 composer 侧入口挂接，不重构消息渲染本身。
- 画布节点编辑器、DockStudio 工具栏、社区/工作台等其它页面。
- 后端 runtime 能力本体（除非条目明确要求新增 runtime 工具，见 P1-4.2）。

## 2. 设计原则（整改须遵守，不可违反）

1. **三态模型**：composer 在同一时刻只呈现一种状态之一 —— **① 空闲（首屏）/ ② 输入 / ③ 生成中**。详见 §5。
2. **分层克制（A/B/C 三级）**：
   - **A 级（每轮必用，常驻）**：附件、模型、语音、发送。
   - **B 级（有非默认值时才出现）**：思考强度 chip。
   - **C 级（收进 `+` 抽屉，非默认隐藏）**：本地上传、资产库、参数预设。
   - **画布节点引用（composer ↔ 画布的一等公民）**：**不进 C 级**。它是 agent 在写提示词时与画布协调操作的最高频桥梁，作为 composer **左顶点常驻图标**（`@` / ◎，圆形图标圆心与 composer 左顶点重合、衔接输入区光标、不内嵌挤压文本区）存在；**可见性按态门控**：输入态 / 生成态可见，**空态（空闲）隐藏**（空态无光标可衔接，其位置由「按住说话」affordance 承担）；键入 `@` 在任意态仍触达同一动作（空态键入 `@` 亦打开选择器，不依赖图标可见）；与 AgentRefStrip / 双层 mention（保护项）打通。
3. **双主题保护**：深/浅主题均为一等公民。任何视觉量（阴影、对比度、底色）必须深浅成对，禁止只对深色优化。
4. **不破坏已有能力**：流式插话队列、引用芯片、双层 mention 高亮、生成中变停止块、双主题是**保护项**，整改不得削弱（见 §6）。
5. **结构自解释**：引导靠控件本身，不靠堆叠文案。每新增一层说明文字前先问「这个控件能不能自己说清楚」。
6. **可机器化校验优先**：能用脚本卡的判据不做成人肉清单。
7. **composer 视觉极简（单一干净表面 + 无背景控件）**：composer 在视觉上呈现为**单一干净表面**（PC 为整张卡片、移动端为单条裸条），其上所有可操作控件（`＋` / 模型 / 语音 / 发送 / ◎）**均无背景**（ghost / 纯图标按钮），**不引入内部嵌套面板或分区**——文本直接落表面、**无内嵌输入框描边**，focus 以表面边框→`border-focus` + 2px ring 表达；**两层契约**：草稿内容（ref 芯片条）位于表面**内部**、输入文本上方（同表面、无独立面板背景，表面随内容生长）；「条/卡上方浮层」仅承载**系统层**内容（生成状态行、插话轻选项、PC 首屏样例 chips），不在 composer 内堆控件。这是移动端「一个 composer 条 + 其上几个组件」、PC「恒定输入区 + 默认收起 chrome」的共同底层视觉契约；生成态「停止」红块为唯一强调色例外。

**基线复算脚本（P0-2 验收用，源自分析文档附录）：**

```bash
node -e '
const lin=c=>{c/=255;return c<=0.03928?c/12.92:Math.pow((c+0.055)/1.055,2.4)};
const L=([r,g,b])=>0.2126*lin(r)+0.7152*lin(g)+0.0722*lin(b);
const over=(fg,a,bg)=>fg.map((c,i)=>Math.round(c*a+bg[i]*(1-a)));
const R=(a,b)=>{const l1=L(a),l2=L(b),[h,l]=l1>l2?[l1,l2]:[l2,l1];return((h+0.05)/(l+0.05)).toFixed(2)};
const bgL=[0xee,0xf0,0xf5], bgD=[0x13,0x13,0x18];
console.log("浅 muted 现", R(over([23,25,35],0.42,bgL),bgL));   // 期望 2.59
console.log("深 muted 现", R(over([244,244,248],0.40,bgD),bgD));  // 期望 3.60
console.log("建议浅 #5a6478", R([0x5a,0x64,0x78],bgL));          // 期望 5.22
console.log("建议深 #9aa3b2", R([0x9a,0xa3,0xb2],bgD));          // 期望 7.28
'
```

## 5. 三态设计目标（整改的统一定向）

composer 的核心动作只有一个：**把「同时做 9 个决定」改成「每个时刻只做一个决定」**。

### 5.0 统一原则：状态机跨端一致，视觉按断点分化

- **状态机一致**：① 空闲（首屏）/ ② 输入 / ③ 生成中 三态及其触发条件、可中断性、停止键同位置等约束，**跨 PC 与移动端完全一致**，不因断点改变。
- **视觉分化**：PC 为右侧 500px 侧栏内的完整分层面板；移动端（≤767px，依据 `useAgentMobileLayout.ts:4`）为底部输入条 / 抽屉。**两者不是同一套样式**，分化点必须在 §5.1（PC）与 §5.2（移动端）分别列出，**不得假设一套图两端通用**。
- **PC 极简翻译**：PC 不照搬移动端裸条，而是把同一极简思想译为「恒定内嵌输入区 + 默认收起的外围 chrome」，详见 §5.4。
- **规范契约优先**：下方各态文字描述为本规格验收锚；来源分析文档 §5.1 的三张 PC 线框（`Agent Composer UI-UX 现状与对标分析.html`）是 **PC 态权威视觉参考**，落地以本节文字判据为准、以线框为视觉对齐基准。

### 5.2 移动端三态（独立定义，与 PC 分化）

移动端是**比 PC 更简洁的状态机实现**，且**三态共用同一条「裸条」**（具备内嵌输入的单一 bar，形态对齐 WorkBuddy 小程序截图，评审提供）：**条本身形态恒定（单一干净裸条、自身无嵌套视觉、其上控件均无背景）**，差异只发生在 bar 的**内嵌草稿内容**（输入文案 + ref 芯片，芯片位于条内文本上方）与**条上方系统内容层**（状态行 / 插话选项）；参考 WB 但**更克制**——`+` 置于条**内**左侧（非条外独立按钮），模型/发送也同处条内、无背景，整条视觉上就是「一个 composer 条 + 其上几个组件」。按 `P1-5` 底部裸条落地；三态可见组件完整清单见 **§5.5**。

**移动端贴底容器的系统承载（v0.5.4 实施期补全）：** 裸条所在的贴底容器（无遮罩、空区穿透、画布仍露出上半）自下而上为：**裸条 → 系统层（状态行 / 插话选项 / ask·propose 卡）→ 对话流**（`agent-chat-wrap`，`max-height: 40vh` 滚动区，消息渲染本体不动、属 Out of Scope 的只读承载）→ **顶栏**（`新建对话` / `会话历史` 保留；`收起` / `浮窗` 为桌面限定）。对话流与顶栏属**系统层**内容（非草稿、非控件），不进入裸条表面；历史 popover 在移动端作用域内**向上展开**（贴底容器视口安全）。

**移动端空闲条的手势双模式（P1-5.3 / P2-2.2）：**

2. **点击**（tap）= 直接切换到输入态，可输入文字。

> **语音入口只放空闲态（已确认）：** 输入态**不**采用「长按输入区即语音」—— 原因：① 移动端长按已聚焦的可编辑输入框会被系统抢为**文本选择/放大镜**，与录音冲突且破坏复制粘贴；② 输入态无「按住说话」affordance 标签，不可发现；③ 输入态软键盘升起、光标在闪，按住 bar 与正在输入的上下文矛盾。故语音仅在空闲态条上（按住）触发；输入态按本规格要求只放 `+` / 模型 / 发送。若日后确需输入态就地语音，规范做法是键盘上方独立 mic 工具条（非长按劫持），届时再立项，不在本期 3 组件约束内。

PC 端仍保留独立 mic 按钮的按住说话（P2-2.1）。这是移动/PC 的核心交互分化点之一。

### 5.3 落实顺序建议（不强制，供排期参考）

先 P0（正确性）→ P1-1/2/3（首屏 + 分层 + 生成中三态骨架）→ P1-6/7（体系与引导）→ P1-4/5（产出收据 + 移动端形态，含空闲 2 组件 / 输入 3 组件收敛）→ P2（含移动端按住说话 P2-2.2）。C 级抽屉与 P1-2 强耦合，建议同个任务内完成。

### 5.4 PC 端极简审视与优化（§5.0 的落地延伸）

移动端已确认「单条裸条 + 上方内容层 + 外围默认收起」的极简范式。PC 因屏幕与输入方式不同，**不照搬裸条**，而是把同一套极简思想翻译为「**恒定内嵌输入区 + 默认收起的外围 chrome**」：

- **输入区恒定**：PC composer 的文本输入区在空闲 / 输入 / 生成中三态保持同一形态（与移动端「同一条裸条」同义）；差异只发生在输入区**上方**的系统内容层（样例 chips / 状态行；ref 芯片属草稿内容、位于卡内输入区上方）与**默认收起**的参数区。
- **默认只露 A 级（均为无背景 ghost 控件）**：空闲 / 输入态外围只默认显示 A 级（+ / 模型 / 语音 / 发送），三者居同一 composer 卡片、无内部嵌套面板/分区，控件均无背景；B 级（思考档位）仅非默认值时出现、C 级（本地上传 / 资产库 / 参数预设）收进 `+` 抽屉 —— **画布节点引用不在此列**（其一等公民内嵌入口见 P1-2.3、§5.1/§5.2）—— 这是 PC 版的「2/3 组件」等价物，消除原 9 控件同屏（B10）。
- **persona 轻量化**：空闲态去掉 hero 大块（π 大头像 + 多行文案），改为输入框上方**一行轻量人格文案**（与移动端「人格靠一句话承担」一致），不放大标题；首屏主体由 4 条动态样例 chips 承担（P1-1.1 / P1-1.3）。
- **不引入 PC 专属语音手势**：PC 保留独立 mic 按钮的按住说话（P2-2.1），不引入「长按输入框即语音」（同 §5.2 取舍，与桌面文本选择冲突）。

**两端极简对称性小结：** 都做到「输入区恒定 + 内容层按需浮起 + 外围 chrome 默认收起」；差异仅在载体形态（PC 右栏 / 移动端底条）与语音入口实现（PC 独立键 / 移动端整条按住），属断点合理分化，非极简破坏。
