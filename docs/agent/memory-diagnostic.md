# 记忆机制诊断报告：pi-lnk 实例 vs WorkBuddy 三层记忆设计

> 配套：[2026-10-08-workbuddy-three-layer-memory-design.md](./../superpowers/specs/2026-10-08-workbuddy-three-layer-memory-design.md)（设计 SPEC）
> 日期：2026-10-08　范围：pi-lnk 的 agent 侧记忆（`.workbuddy/memory/`）

## 0 摘要

WorkBuddy 的三层记忆设计是一套**带配额、带蒸馏纪律、索引/证据分离**的长期记忆机制。pi-lnk 的 agent 侧记忆在**结构上已对齐** L3 三件套（`MEMORY.md` + 每日日志 + `MEMORY-details.md`），但在**执行纪律**上偏离，导致 2026-10-08 出现 `MEMORY.md` 超限截断（17047 字节 ≈ 5.7× 硬限）、9 月日志从未蒸馏、`MEMORY-details.md` 无序膨胀。

本诊断给出 6 个缺口、可借鉴点、补缺口优先级，并映射到 SPEC 的验收标准 G1–G6。

## 1 对比维度

| 维度 | WorkBuddy 设计意图 | pi-lnk 实例（2026-10-08） | 缺口 |
| --- | --- | --- | --- |
| 配额硬限 | L3 ≤3000 / L2 ≤4000 字符，超出即截断注入 | L3 实测 17047 字节（超限截断，**高频判据反而读不全**） | 🔴 缺口 A |
| 索引/证据分离 | `MEMORY.md` 只放结论，证据下沉 `*-details.md` | 两者都在，但 `MEMORY.md` 正文仍是近全量副本；`MEMORY-details.md` 209KB 无序 | 🔴 缺口 B |
| 蒸馏纪律 | 每日日志 >30 天按主题蒸馏进索引，旧日志删除 | 9 月共 9 份日志（最大 369KB）从未蒸馏 | 🔴 缺口 C |
| 压缩不删判据 | 超限时只压措辞，数字/file:line 下沉，判据不可删 | 历史多次压缩做过，但每次都重新逼近上限 | 🟡 缺口 D（机制在，护栏缺） |
| 编辑前先读 | 累积文件编辑前先读，防重复追加 | 2026-10-03 曾因未读产生 7 行重复；本次重写已先读 | 🟢 已具备，需固化 |
| 落盘复核 | Write/Edit 报成功 ≠ 落盘，需 `wc -c`+grep 复核 | 多次因此吃亏，已有纪律但**非强制** | 🟡 缺口 E |
| 账号绑定 | L2 绑账号 UUID；账号切换 = 换目录 = 旧滞留新空 | 2026-10-08 账号切换致 L2 个人记忆丢失，靠旧目录残留找回 | 🔴 缺口 F |

## 2 缺口详述

### 缺口 A — 配额超限未强制（最关键）
`MEMORY.md` 膨胀到 17047 字节，本会话注入被截断（系统提示 `ACTION REQUIRED`）。**违反设计的核心约束**：配额是「主动防止旧记忆淹没上下文」的机制，超限反而让最高频的判据读不全。
**修复**：压缩到 ≤3000（本次已做：17047→2923 字节）+ 字符护栏脚本（`scripts/check-memory-size.ts`）+ CI 强制。→ 对应 G1/G3。

### 缺口 B — 索引/证据未真正分离
`MEMORY.md` 头部已声明「全文快照按标题搜 details」，但正文仍是近全量拷贝；`MEMORY-details.md` 209KB 只是历次压缩的快照堆叠，无主题组织。
**修复**：索引只放「结论 + 标题锚点」，证据按标题组织在 details（已部分具备）。→ 对应 G4。

### 缺口 C — 蒸馏纪律缺失
9 月 9 份每日日志（22.7KB–369KB）从未蒸馏进 `MEMORY.md`。日志是 append-only 流水，不蒸馏会无限膨胀，且重复信息散落多日。
**修复**：30 天蒸馏循环（本次只修当前超限，9 月日志蒸馏列为待排期）。→ 对应 G6。

### 缺口 D — 压缩机制在但护栏缺
历史已有「第 N 次压缩」实践，但每次都重新逼近上限，说明**没有硬性护栏**兜底。压缩依赖人工自觉。
**修复**：护栏脚本 + package.json 入口 + CI。→ 对应 G3。

### 缺口 E — 落盘复核非强制
Write/Edit 在本环境可能被 broker 吞写，曾多次「报成功 ≠ 落盘」。目前靠自觉 `wc -c`+grep，未固化进流程。
**修复**：把复核作为写入 `.workbuddy/memory/` 的标准最后一步（写入约定文档 + 护栏脚本顺带校验字节数）。→ 对应 G4/G5。

### 缺口 F — 账号切换导致 L2 丢失
L2 `~/.workbuddy/user-<UUID>-personal/MEMORY.md` 绑账号 UUID。2026-10-08 切换账号后，新账号 L2 为空，旧账号的跨项目偏好滞留旧目录（靠手动迁移找回）。这是**设计的可预期后果**，非 bug，但项目未做任何「账号切换时迁移/合并 L2」的预案。
**修复**：约定「切换账号后主动核对 L2」；跨项目偏好优先写项目级 L3（本项目已把用户偏好并入 `MEMORY.md`，降低对 L2 的依赖）。→ 对应 G5。

## 3 可借鉴 / 学习的点（设计做对的地方）

1. **分作用域**：L2（账号级）与 L3（项目级）分离，避免项目事实污染其它项目，也避免每项目重复写偏好。本项目已正确采用。
2. **配额即纪律**：硬限不是 bug，是「防止上下文被旧记忆淹没」的主动约束。值得在 CI 用脚本守住。
3. **索引/证据分离 + 标题锚定**：让索引永远轻量，证据可追溯。本项目 `MEMORY-details.md` 机制已建立，只需落实意图。
4. **追加写优先**：每日日志 append-only，降低并发覆盖风险（多窗口并行开发时尤为重要）。
5. **召回不假设单一真相源**：同一事实可能在 L1/L2/L3/日志多处，按「最新 + 最权威」选择，并带时间戳。本项目「本地 ref 不可信，结论带时间戳」正是该原则的延伸。
