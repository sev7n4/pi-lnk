§ 1 现状：审计结论与生产事实的落差

审计写的是「调度主干吃满了」，这句话对，但只说了一半——主干的尽头没接通货。

审计结论实际情况（本次核实）判读
「addedToolNames + tool-placement 100% 走原生 ⇒ 动态激活是吃满典范」 机制确实 100% 原生，无 host 侵入；但生产 tool_search_activated_total = 0，该通道从未被走过 机制对 无流量 典型「接了线没接负载」
延迟集已建成（buildToolEnsemble + tool_search） 47 工具（tools/*.ts 实测）：常驻 36（含 load_skill + tool_search），延迟集 11 个（apply_asset_to_node / delete_nodes / duplicate_node / focus_nodes / grid_slice_image / introduce_nodes_to_agent / open_image_editor / redo / save_node_to_asset_library / undo / upload_media_to_canvas） 货太少 77% 常驻 ⇒ 模型几乎不需要搜，渐进披露无收益
C 类工具「无任何资产点名 ⇒ 只能靠 description 猜」 2026-10-05 复核修正：tool_search 在常驻集里、每轮都下发（非「不可达」）。真正的死锁是「77% 常驻 ⇒ 没什么可搜」+「没有任何资产告诉模型什么时候该搜」——是动机问题，不是可达性问题 自锁 #184 补了触发条件，但载体文件正在暂存删除态（见 §6）
「护城河 = 只走包公共入口，零内部路径穿透」 成立，仍是本项目最值钱的结构优势 守住 别为了方便去 import 内部路径
「风险点：vendor 升级零门禁」 成立。verify-contract.ts 比的是模型 API schema，工具框架契约 0 覆盖；4 个 hook 的 event 靠运行时读字段，无类型约束 ⇒ 上游改字段会静默 fail-soft 最高优先级 0.x 无 semver 兜底
一句话
审计的「吃满」是能力接线条数的口径；产品要的是这些能力被真实业务用到的口径。两者目前差着 0 次真实调用。

§ 2 重新分类：8 个零消费钩子，按「有没有对应产品需求」

审计按「不吃的代价」排序，那份排序对代码成立、对产品不成立。这里按产品是否长出了承载它的业务重分四档。

A 档 · 值得吃  有明确产品载体，吃进来立刻有业务

replay:"safe"
onUpdate{checkpoint}		 agent 层崩溃恢复：进程/容器挂掉后，已完成的工具结果不重算（不是传输层断线重连） ① 工具幂等分级（读类标 safe）② 产物落盘可重放 与 T1 互补不互斥：checkpoint 只替换 entry.buffer 的存储层（内存环形缓冲 → 持久化快照），seq + isReplayComplete 的契约保留。

  • constrainedSampling —— provider 约束采样，当前无产品场景（无结构化输出落库需求）。

§ 3 三条产品主线（按必须做的顺序）

A 必须先于 B；C 可以插在中间。三条线不是并列关系，是递进关系。

主线 A · 能力目录先行
不是钩子，是所有「吃满」的前置
  • 现在「用户这句话 → 哪个 skill → 调哪些工具」散在三张互不相通的清单里：prompt 规则、skills/*、tiering.ts 常量
  • 产出一张 capability-map：工具 × 技能 × 规则 × 触发话术
  • 它是渐进披露的输入、toolset 化的依据、新垂类上架的清单
不吃钩子，但决定 B/C 能不能落地
主线 B · 技能包化
让工具集成为产品单元
  • 一个技能包 = 一组 activeToolNames + 一份 prompt 规则 + 一组验收入口
  • 吃 setTools/setActiveTools（会话中装/卸）+ 已吃的 addedToolNames
  • tool_search 从「搜工具」升级成「搜技能包」
吃 2 个钩子：setActiveTools、addedToolNames
主线 C · 长任务可重放
两层分开做：存储层换持久化快照，重连契约原样保留
  • 工具幂等分级（读类标 replay:"safe"）+ 产物落盘可重放
  • 吃 replay:"safe" + onUpdate{checkpoint} ⇒ agent 层崩溃恢复
  • checkpoint 落地后：entry.buffer 由内存环形缓冲（BUFFER_LIMIT=500 溢出丢事件）换成持久化快照
  • seq / isReplayComplete / droppedFromSeq：属传输层，归 T1，不动
吃 2 个钩子：replay、onUpdate.checkpoint
为什么 B 排在「再接 4 个钩子」前面
在能力目录成型前吃 setActiveTools，只是把 36 个硬编码白名单搬进 API 调用——换皮，不是能力。先有目录，才有「该给这个会话哪套工具」的答案。
两处表述已按 R4 窗口的实测反馈修正（2026-10-05）
① 重放是两层，不是一层。原稿把「上游 replay + checkpoint」写成「替掉 T1 的 entry.buffer+seq」，混淆了： seq / isReplayComplete / droppedFromSeq 是传输层断线重连契约（T1）， entry.buffer 是存储层。上游 checkpoint 能替换的只有存储层；契约要保留，否则客户端断点续传失去判据。
② 不能拿「迁上游 replay」当关掉 T1 的理由。上游 replay 的定位是 agent 层崩溃恢复（进程挂了不重算已完成的工具）， 与 T1 的断线重连互补而非互斥。它值得做，但立项依据要写对 —— 依据写错会导致 T1 的 3 个文件被误判为沉没成本。

P2长任务 durable 重放 + checkpoint
checkpoint 落地后只换存储层：entry.buffer 的内存环形缓冲 → 持久化快照（治 BUFFER_LIMIT=500 溢出丢事件）。seq + isReplayComplete 契约保留，droppedFromSeq 继续作为「丢过」的可判读信号 —— 它属于 T1 传输层，不随 checkpoint 删除。
P2terminate 早停 + 门禁常态化
生成批次中途收手；升级前跑门禁，eval 从 12 case 扩到 20+ 并覆盖工具激活路径。
预算死结已解开：skills 是不占 L6 的独立通道（2026-10-05 实测）
此前把「tool_search 触发线索写进 prompt 规则」判为预算上不可行（L6 硬线 3200，最紧组合 core+writeTools+genTools = 3192 ⇒ 余量仅 8 字符）。实测核对后该判断不成立：
  • L6 量的是 renderStatic(snap, combo).length —— 只算 prompt-registry 规则，不算 skills
  • skills 是独立通道：index（name+description）常驻 systemPrompt，正文经 load_skill 按需加载，COPY skills ./skills 已进镜像，且有独立指标 pi_runtime_prompt_skills_tokens
  • ⇒ 「什么时候该用 tool_search」的线索可以写在 skill 正文 / index 描述里，零 L6 成本
但要注意边界：load_skill 的返回值不带 addedToolNames ⇒ skill 只能做「点名/线索」，不能做激活。 激活只有一条路：tool_search 的 addedToolNames（vendor tool-placement 原生合并）。 所以正确组合是：skill 里点名 + 引导调 tool_search，由 tool_search 完成激活。

§ 5 度量：把「吃满」变成可验证

不要用一个综合百分比糊弄——「吃到 6/14」是今天的代码现状，不是产品目标。

① 激活路径占比
常驻 / tool_search / addedToolNames 三条路的工具调用占比。

现在 100% 常驻。目标：新增能力走后两条 ≥ 30%（不是 100%——全走动态会伤弱模型，这正是 0.0.29/0.0.30 的教训）。
② 钩子消费矩阵
14 个能力位逐个标 consumed / unconsumed，进 eval 或 tiering.test.ts 断言；vendor 升版后自动 diff 出「掉了哪个」。
③ 升级门禁通过率
工具契约断言失败数（目标恒 0）+ eval 用例通过率。这是「能不能持续吃满」的唯一硬指标。
反模式
拿「hook 消费 6/14」当 KPI 写进周报 —— 那会诱导团队去为吃而吃，产出 executionMode 这类零场景的死代码。
