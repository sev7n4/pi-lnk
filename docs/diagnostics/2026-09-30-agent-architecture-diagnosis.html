00执行摘要

一句话：PI-Lnk 把「模型即 Agent」贯彻到了极致，也因此继承了裸模型的全部结构性缺陷。 四个维度里，工具调用是唯一做到工业级的一维（tier 分级 + HITL Gate + 指标 + 超时覆盖表都齐全）； 而任务规划和记忆管理基本是空白，意图识别停留在「交给模型隐式判断」的 L0 阶段。 四家对比下来，差距不在于某一行代码，而在于是否存在「对话之外的结构化状态」—— Codex 有 plan 与 memory pipeline，Claude 有 Task 图与 subagent，WorkBuddy 有三层记忆文件； PI-Lnk 的会话状态几乎只有 JSONL 消息流本身。

头号发现：上下文压缩链路是断的，且已在线上显形

精查后修正：能力其实一应俱全，唯独缺一个触发点。vendor 的 shouldCompact() 决策函数、 AgentLane.compact() 执行 API、CompactionSettings 配置，全部已写好并从 @earendil-works/pi-agent-core 主入口导出。但 harness 源码内零处调用决策函数， pi-runtime 亦零处调用执行 API。结果是 enabled:true 这个开关什么都不控制—— 传动到一半就断在那儿。叠加 agnes 侧 contextWindow 声明为 100 万导致阈值 983,616 永不触及， 长会话必然退化。已知的线上症状「S6 删除轮空轮」正是它的必然表达。

02维度一 · 意图识别

四家在意图上分成了两条明确路线：「能力派」把意图留给模型内生判断，只提供澄清工具； 「状态派」把意图固化为运行时状态和协议。PI-Lnk 属于前者，而且是其中最彻底的一个。

PI-Lnk 现状：唯一的显式意图入口是 @ skill

session-manager.ts:142 的 withForcedSkills() 是全部 Circuit Breaker 式的意图处理： 用户点名某个 skill，就把 SKILL.md 正文拼到 prompt 前缀。除此之外，意图全部由模型隐式完成。

// session-manager.ts:495 tools: [...this.tools, ...(this.skills?.tools ?? [])], // 37 个工具一次性给全 systemPrompt: () => composeSystemPrompt(entry.staticPrompt, entry.turn.dynamicBlocks ?? [])

Skill 索引只是在 prompt 尾部追加一段「可用技能」清单，靠语义相似让模型自己选： skills/loader.ts:55 buildSkillIndexBlock() 生成 - name: description 列表，配合提示语「用户意图匹配某技能描述时先调用 load_skill」。

结论：skill 选择率、误选率、无人跟上的情况统统不可观测——因为它只发生在模型的一次隐含判断里。

Claude Code 把意图升级为可验证的协议

最值得偷的不是 AskUserQuestion，而是 ProposeGoal。它的工具描述里写死了约束：

"The completion condition to propose, written so a separate evaluator can verify it from the conversation (e.g. \"all tests in test/auth pass (bun test exits 0)\"). At most 500 characters — the user must be able to read the whole condition in the approval dialog." —— sdk-tools.d.ts, ProposeGoalInput.condition

三个设计点：① 由独立评估器验证（不是自证）② ≤500 字符（用户在批准对话框里能读完） ③ ask_user 默认 true，仅当用户原话已明示该目标时才直接设定，并在 transcript 留可见痕迹。 同时 AskUserQuestion 强制 2-4 个结构化选项（multiSelect 可多选），把开放式填空压缩成受限决策。

Codex 模式即意图：Plan Mode 是运行时的一个 态

二进制里抽出两条互斥指令，说明 Plan Mode 由 developer message 显式进出，不是建议：

"You are now in Default mode. Any previous instructions for other modes (e.g. Plan mode) are no longer active." "You are in **Plan Mode** until a developer message explicitly ends it."

更狠的是按模式配推理预算——配置里 plan_mode_reasoning_effort 与 model_reasoning_effort 是两个独立字段。 规划阶段和收尾阶段用不同的思考强度，这是把意图识别的成本也纳入了设计。

WorkBuddy 把意图识别外化成资源匹配

三条横线 shipping 在一起：会话模式（Agent/Plan/Ask）+ 强制前置方法 skill（创造前 brainstorming、bug 前 systematic-debugging、 提交前 verification-before-completion）+ 连接器/专家推荐。最后一条尤其聪明： 「用户提到某个外部系统」本身就是强意图信号，路由到对应连接器比让模型猜参数可靠得多。

对 PI-Lnk 的启示：澄清必须是「态」，不能是「工具」

PI-Lnk 已经有 ask_user 工具，但它和 save_memory 平级——模型可以任何时刻跳过它直奔 run_*。 区别在于：Callaude 的 EnterPlanMode 会改变后续可用工具集（进入规划态后写工具被封），这是机制约束，不是提示建议。 建议：给 pi-runtime 引入一个 planMode 会话状态位，置位时 before_tool hook 直接拦截 tier: gen/destructive， 把「先想清楚再动手」从 prompt 里的祈使句变成 gate 里的代码。

03维度二 · 任务规划 —— 差距最大的一维

这一维度 PI-Lnk 与三家的差距不是「做得糙」，而是有没有。 全部 37 个工具里没有任何一个承载计划状态；会话的结构化状态只有 SessionEntry 里的 prompting / cancelRun / nextSeq / thinkingLevel——全是执行控制位，没有一个是任务语义位。

Claude Code 双轨外化：轻量 TodoWrite + 重量级 Task 图

两层设计分别解决两个不同问题：TodoWrite 是会话内轻量清单（content/status/activeForm）， 成本极低、模型愿意用；TaskCreate/TaskGet/TaskUpdate/TaskList 是持久化、跨会话、多 agent 共享的任务图：

// TaskUpdateInput —— 注意依赖不是一个字段，而是一对关系操作 addBlocks?: string[] // 我完成后，哪些任务被解锁 addBlockedBy?: string[] // 我被哪些任务挡着 owner?: string // agent 级归属 status?: 'pending' | 'in_progress' | 'completed' | 'deleted' metadata?: Record<string, unknown>

blocks/blockedBy 的存在意味着依赖可以增量追加而不必重写整个任务——这是一个成熟的图结构 API， 而不是一个 todo 数组。叠加 Agent（subagent，支持 isolation: "worktree"、 model 覆盖、run_in_background）和 Workflow（phase/parallel/pipeline 脚本编排）， 形成「清单 → 任务图 → 委派 → 多阶段流水线」的完整阶梯。

Codex update_plan + 一段教科书级的「何时该委派」策略

从二进制抽到的原文，直接定义了关键路径判定：

### When to delegate vs. do the subtask yourself - First, quickly analyze the overall user task and form a succinct high-level plan. Identify which tasks are immediate blockers on the critical path, and which tasks are sidecar tasks that are needed but can run in parallel without blocking the next local step. - Do not delegate urgent blocking work when your immediate next step depends on that result. If the very next action is blocked on that task, the main rollout should usually do it locally to keep the critical path moving. - Do not repeatedly wait by reflex. Only call wait_agent when you need the result immediately for the next critical-path step and you are blocked until it returns. - For code-edit subtasks, decompose work so each delegated task has a disjoint write set.

「disjoint write set」这条尤其值得注意：并行委派的安全性由写集合不相交来保证，这是工程约束而非祈祷。 此外 Codex 把上下文预算也做成配置项（model_auto_compact_token_limit、 model_post_turn_compact_threshold_percent），plan 与 context 生命周期被统一管理。

05维度四 · 记忆管理 —— 差了一个时代

PI-Lnk 有「存东西的地方」，但没有「记忆系统」。三家对照下来，共同点不是存得多，而是 都在做「写入前的过滤」和「长期的知识蒸馏」——而 PI-Lnk 这两层都不存在。

PI-Lnk 现状：两个工具 + 子串扫描

tools/memory.ts 全文 86 行，save_memory（≤2000 字符截断）与 recall_memory， 走 Nest /agent/internal/memory-save 与 memory-search。检索语义写在工具描述里：

"Recall durable facts saved about the user. Omit query to list the most recent memories; pass a query to match as a case-insensitive substring (only your most recent 200 memories are scanned)."

四个缺失很致命：① 无写入门——模型任何冲动都会落库；② 无蒸馏——2000 字符原文堆积，从不合并冲突与去重； ③ 检索是子串匹配，无语义召回，且召回窗口随记忆增长反而变窄（用户越活跃，200 条覆盖的时间越短）； ④ 无分层——项目知识与个人偏好混在一个表。

Codex 一段值得整段抄的 memory prompt

这段从二进制抽出的 prompt 定义了记忆 pipeline 的写入端，两个约束是真正的核心：

0. Apply the minimum-signal gate. - If this rollout fails the gate, return either all-empty fields or unchanged prior values. 1. Triage outcome using the common rules. 2. Read the rollout carefully (do not miss user messages/tool calls/outputs). 3. Return `rollout_summary`, `rollout_slug`, and `raw_memory`, valid JSON only. You are part of an agent memory system. Your job is to extract information from this rollout that would be useful for the user on future tasks. Future agents may read this record ... and a later memory-writing agent will distill it with other records into brief context injected into future tasks. It is important to not write over-confidently and not over-generally to avoid misleading future agents.

注意最后那句，以及它给出的置信度分级范例：

if the user says "show me the plan before editing this", you can write "the user asked to show a plan before editing", but should not write "the user prefers the agent to show plans before editing". if the user said "I prefer you to show plans before editing", you can write "the user explicitly stated that they prefer the agent to show plans before editing".

也就是说：「一次请求」不能被升华成「跨任务偏好」，除非用户自己用了泛化措辞。 这是 PI-Lnk 的 save_memory 最容易犯、且一旦犯了极难纠正的错误——把临时偏好写成永久规则，污染未来所有会话。 再叠加三层结构（rollout → raw_memory → distill 摘要）与配置项 external_agent_memory_import、 local_thread_store_compression，以及项目文档层 project_doc_max_bytes / project_doc_fallback_filename（AGENTS.md 等价物）。

WorkBuddy 三层 + 维护规则写死在 prompt 里

workbuddy-memory-system.md 直接给出可复制的分层：L1 云画像（只读、服务端生成、本地写会被覆盖）、 L2 用户级 MEMORY.md（跨项目、明确 ask 才写）、L3 工作区 YYYY-MM-DD.md 日志 + MEMORY.md（项目内、append-only）。 更关键的是它定义了怎么维护：

Maintenance: Distill daily logs older than 30 days into MEMORY.md by topic, then delete the old files. Do not record transient information (search results, temporary paths, tool errors). Only persist what has lasting value across sessions.

顺带建立了混合检索策略：项目内 → 读本地日志（最近优先）；跨项目/不确定 → conversation_search 服务端排序； 无历史依赖 → 跳过读文件。这是「先选源再检索」，而不是无差别全扫。

Claude Code 把记忆再往上推一层：经验固化成技能

ProposeSkills 工具的输入里有一行特别说明——description 直接决定技能何时被调用：

"One short sentence saying when to use this skill: aim for under 200 characters, never more than 1024 ... Shown on the review card and saved as the skill's description, which is what decides when the skill is used." // ProposeSkillsInput: name, description, evidence, kind('new'|'improvement'), skillMd, target

「记忆 → 复用 → 固化成技能」形成闭环，且要求携带 evidence（观察到该流程的 memory 文件路径）。 PI-Lnk 的 8 个 drama skill 目前是人工编写的，若不加这条链路，经验永远停在 MEMORY.md 里。

在 save_memory 的 description 里直接写死 Codex 那两条规则：minimum-signal gate + 反过度泛化的措辞分级。零代码改动，立刻降低污染率。
中期
加第二层作业（离线或轮结束触发）：把 N 条 raw memory distill 成一条综述写回，原始条目标记 superseded 而非删除；检索改为「先召回综述、按需下钻原文」。

07借鉴落地路线图

按「止血 → 结构 → 跃迁」三阶段排。每一项的共同特征是：先把外部状态造出来，再谈让模型用得好。

Phase 1 · 止血（建议 1–2 周）

  1. 接通 compaction（F-01）：host 侧实现阈值判定 → OperationRequest{kind:"compaction"}，打开 compaction.enabled；注入参数一律 --set-string。验收标准：连续 20 轮对话后 >=50 轮不出现语义退化。
  2. 给记忆加写入门（F-05/F-06）：save_memory 描述内写入 minimum-signal gate + 置信度措辞分级；同时去掉 recall 的 200 条窗口。零后端改动。
  3. planMode 状态位（F-03）：会话级布尔量，置位时 before_tool 拦截 gen/destructive 两档。比新增一个工具便宜得多。

Phase 2 · 结构（3–5 周）

  1. update_plan 工具 + 前端进度条（F-02）：Codex 形态的最小版，整体覆盖语义，随 SSE 旁路下发。
  2. 渐进披露 ToolSearch（F-04）：先只读工具仍需常驻（高频），把 gen/destructive 转成 deferred。前置check：Gate 的 tier 判定必须改为查完整注册表，否则会踩新一轮 #76 式 fail-closed。
  3. 记忆分层 + 蒸馏作业（F-06）：加 scope 列，加一个轮后/定时任务做 N→1 摘要，原条目标记 superseded。
  4. run_* 异步化（F-07）：提交 + 轮询 + 取消三段式，复用已有的 get_generation_status / cancel_generation。

Phase 3 · 跃迁（6–8 周）

  1. code-mode 旁路（F-09）：借鉴 Codex code_mode_host 思路，对「多工具组合编排」类需求，让模型生成一段受控脚本在沙箱里跑，把 N 次往返压成 1 次。对短剧链路这类固定多步流程收益最大。
  2. 有限 subagent：vendor pi 无 subagent，但可用嵌套 Agent 实例 + 独立 lane 做最小实现，先支持只读探索类委派（参考 Codex 的 disjoint write set 约束）。
  3. 经验 → 技能闭环（对齐 Claude ProposeSkills）：记忆里反复出现的流程，自动生成 SKILL.md 草案交由人工确认。
贯穿全程的一条原则

这三家的差异表面在功能，底层在一件事：有没有把「本该属于系统的责任」显式化。 Plan Mode 是把「先想清楚」显式化，Task 图是把「任务依赖」显式化，ToolSearch 是把「工具选择」显式化， Memory pipeline 是把「什么值得记」显式化。PI-Lnk 现在把这些全部委托给模型的同一次内隐判断—— 短任务上这没问题（模型很聪明），长任务上一定会退化（上下文很贵）。 所以每一阶段的验收标准都应该问同一个问题：这条责任现在由代码承担，还是仍然只是 prompt 里的一句请求？
