一句话结论：现状不是「缺组件」，而是信息放错了区域—— 当前轮的过程被追加到正文末尾（所以「过程在最后」），产物卡又排在过程之前（所以「产物在中间」）， 而唯一钉在底部的状态行只显示秒数（所以「无可读语言」）。修法是把当前轮的三件事全部上提到 底部钉住区，完成后才「沉降」进正文历史。全过程复用已有组件，不新造协议。

1.1 截图四个问题的根因，逐条定位到代码

问题 ①

等待期白色方块

AgentSideRail.vue:269

shouldShowMessageBubbleText() 开头就是 if (msg.streaming) return true —— 只要在流式，不管内容是否为空都渲染气泡；模板 :2671 再补一个闪烁光标 ▊。

而阻塞式 propose_generation 等待期根本不产生 token（模型在等确认）， 于是得到一个 0 内容 + 闪烁光标的空气泡。

问题 ②

产物在中间、过程在最后

AgentSideRail.vue:2696-2715

气泡内 DOM 顺序是固定的：正文 → 引用条 → 复用按钮 → AgentCanvasOutputs（产物卡） → AgentExecutionTrace（过程） → AgentPresentationHost。

所以任何一轮都是「先看到产物、再看到折叠的过程」，而过程本该是产生产物之前的现场。 顺序颠倒 + 默认折叠 = 用户永远先看结果后看过程。

问题 ③

过程无可读语言

toolPresentation.ts

注册表 6 条，其余兜底：run_* → 🎨 生成 · image_generation（还是英文内部名）， 其他 → ⚙ 调用 {name}。而 canvas_action / task_update 这类步根本不走工具注册表。

结论：**工具名不是用户语言**，缺的是「动词 + 业务对象」的第二层。

问题 ④

下一步做什么

目前不存在。

部分补救散落在 composer 上方：awaitingConfirm 三按钮（确认方案 / 换方向 / 自己说明修改）、 awaitingGenerationPropose（确认生成 / 取消）、AskUserCard。三者互斥、且只在特定条件下冒出来， 用户没有「当前这一步之后我该干什么」的稳定预期。

另外两个实测事实（影响设计取舍）： ① propose 的确认注册键是 canvasSessionId，同一画布多线程会串台（今天的「卡通小狗」事故）， 所以「下一步」动作必须带 nodeId 定位，不能只给一个裸「确认」。 ② 阻断等待的兜底超时已从 30 分钟改为 5 分钟（ASK_USER_TIMEOUT_MS=300000，已在生产生效）， 因此等待态文案必须把倒计时说出来，否则用户 5 分钟后会突然收到「已取消」而不知道为什么。

3.2 「下一步」为什么要走白名单

如果让模型自由生成按钮文案与动作，就会出现「按钮点了没反应」「动作和当前状态不匹配」—— 这正是 A2UI 的核心设计决定：agent 只能引用客户端预先注册的组件，不能注入任意类型。 同样的约束搬到动作上：动作由前端注册表定义，事件只说「现在是 awaiting_atomic_confirm，nodeId=X」， 前端据此渲染该状态对应的 chip 集合。这样：

  • 按钮与状态强一致（不可能出现「已完成」态还挂着「确认生成」）；
  • 多线程串台问题被 nodeId 天然抑制（chip 绑节点，不绑会话）；
  • 新增动作只改前端注册表，不改事件契约。

6外部生态对照：有没有现成轮子？

这个问题值得认真回答，因为答案决定了我们是「造协议」还是「改组件」。结论是： 三个现成方案都研究过，全部不引入协议本体，但每个都拿一样东西。

方案它解决什么对本项目的判断结论
AG-UI
CopilotKit 主导，事件式 Agent↔前端协议		 标准化事件词表：RunStarted / StepStarted / StepFinished / ToolCall* / TextMessage* / StateDelta / Activity / Interrupt，且 RunFinished.outcome = interrupt 专门表达「人机中断」 我们的 SSE 事件集已经是它的超集（waiting_user / task_update / canvas_action 都有对应物）。引入协议 = 换一层序列化 + 全套适配器， 不产生任何 UX 改善。但它的事件分类法值得抄： 「Activity（进行中的活动）」与「Interrupt（中断）」是两类不同东西——我们目前都塞在 waiting_user 里。 借词表不引协议
A2UI
Google 开源，声明式「生成式 UI」		 Agent 发扁平 JSON 组件描述，客户端用自己的组件目录渲染； 组件目录白名单 = 安全边界；支持流式渐进渲染 我们是单一宿主应用（画布工作台），不是「agent 要塞任意 UI 到别人家」的场景， 引 A2UI 属于杀鸡用牛刀。但它的核心设计决定直接可用： agent 只声明意图与 id，渲染与动作由客户端目录决定 —— 这正是「下一步 chips」应该遵循的约束。 借约束不引渲染协议
pi 自带 TUI
vendor 内 tui-plan.md + packages/tui		 已经在仓库里解决了同一个问题：transcript 滚动， 而 pending / status / widgets / editor / footer 固定钉在底部； 还明确了「主屏不能假装有受限视口」这类边界 这是最该重用的一个，而且是零成本——它是一份设计决定文档，不是运行时依赖。 我们的三区模型（§2）就是它的 Web 移植版。 照搬区域模型
取舍理由（一句话）：协议解决的是「跨实现互通」，我们缺的是「同一界面内的信息分层」。 前者引入成本高、对本次诉求零收益；后者只需要改渲染顺序 + 扩文案函数。 唯一实质性的「借」是把 AG-UI 的 Activity / Interrupt 二分落到事件层： waiting_user 只表示中断，另设 activity 表示进行中的活动 （带 label + 可选 done/total），状态行的「在做 / 做得怎样」就有了干净的两个数据源，而不必从执行轨迹里猜。
