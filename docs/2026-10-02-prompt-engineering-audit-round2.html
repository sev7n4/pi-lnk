00二轮做什么、不做什么

首轮回答的是「哪里不行」，本轮回答「怎么改成、按什么顺序改、改完怎么证明变好了」。三条边界先说清楚：

  • 路线图的排序逻辑改了。首轮把「eval + 版本化」排在 1–2 周、规则重写排在 3–4 周；本轮把其中两项合并提前（见 §01 第 1 条），因为 vendor 自带的 eval 基建把「建体系」的成本压到了「写一个适配层」。

01结论摘要：五条会改变排序的判断

判断 1　首轮 P0-1「自建 eval 体系」这个建议本身要降级需修正
证据
vendor/…/packages/evals/ 是一整套已写好的评估框架：vitest-evals 集成（src/vitest-evals/{reporter,summary,artifacts,harness-table}.ts）、 createPiCodingAgentHarness()（src/pi-harness.ts:246）、evalHarnessTable() 对比表（README.md:104-153）—— 支持多候选对基线重复采样、pass-rate lift、配对遥测差值（token/延迟/成本）。
为什么降级
首轮按「eval = 0 ⇒ 从零建」写的，隐含 3–4 周工作量。实际框架是现成的，真正要写的只有一层 adapter（见 §07.1）。
但有个坑
vendor 那个 harness 是 coding-agent 形态（临时工程目录 + AgentSession，依赖 @earendil-works/pi-coding-agent）， pi-lnk 是 durable Lane + pi-runtime HTTP，两条路。所以 createPiCodingAgentHarness 不能直接拿来用， 要照它的方法写一个 createPiRuntimeHarness。另外 vitest-evals@0.15.0 是私有包 @earendil-works/pi-evals 的 devDependency，vendored 树里没有装好的 node_modules，接入前要先解决依赖。
结论
P0-1 仍是 P0，但工作量从「建体系」降到「适配 + 攒 case」，因此可以提前与 W1 合并。
判断 2　规则原子化不该落在 promptTemplate 上需辨明
证据
首轮 §07 建议的规则骨架是「XML 分区 + 连续编号 + 反例段」。vendor 确实有 promptTemplates 机制（harness/prompt-templates.ts:31-64， .md + YAML frontmatter + $1/$ARGUMENTS/${@:N} 参数替换，formatPromptTemplateInvocation :268-270），但它 不是 system prompt 分段机制——唯一消费点是 lane.ts:544-552 的接收（accept）路径，模板展开后成为这一轮用户 prompt 本身。
后果
把规则拆成 N 个 .md 用 promptTemplate 装配 = 概念错配，规则会变成「用户消息」而不是系统约束。
正确用法
两条分开走：规则走 composeSystemPrompt 静态串拼装，但源文件 .md 化 + 版本化 + CI 校验（方案 A）； promptTemplate 留给首轮 P1-3/P2-4——「可参数化话术模板」和「vision 子提示词带参数」，这两处它天生合适。
判断 3　load_tools 触发率 0 的根因是门槛设计，不是提示词强度需自建能力
证据
延迟索引块只有「名字 + 一句话摘要」，头部一句 «需要时调用 load_tools 按名加载»（tools/tiering.ts:82-88）； 13 个条目没有任何一条携带自然语言触发条件。而 arrange_nodes 被强行放进常驻集，注释自己写「依赖 load_tools 激活，而 load_tools 触发率实测为 0 ⇒ 延迟即不可达」（tiering.ts:56-59）。
判断
渐进披露的门槛是「让模型主动去捞」。业界（Anthropic Skills / Claude Code 的渐进披露模型）一致的做法是： 索引条目本身必须带触发条件，读正文才是显式动作。让模型先想起「有个工具没加载、我要去捞它」，这一步最容易被漏。
可用能力
vendor 已有同构基础设施：技能渐进披露（formatSkillsForSystemPrompt 输出 XML <available_skills>，harness/system-prompt.ts:3-25）、 disableModelInvocation（frontmatter disable-model-invocation，skills.ts:304，可把低相关技能移出常驻索引）、 以及 load_tools 已在用的 addedToolNames 自动激活（tiering.ts:1-17 有自述）。缺的只是索引块的写法。
判断 4　首轮 P2-1「压缩保留段」是全场性价比最高的一项一行常量
证据
通道已经端到端打通而不只是接口存在： lane.compact({customInstructions})（lane.ts:1200）→ 进 before_compaction 事件的 event.customInstructions → compaction.ts:567-568 把 customInstructions 拼成 `\n\nAdditional focus: ${customInstructions}` 追加进摘要 prompt； 分支摘要同理（branch-summarization.ts:256-259）。
但没填值
pi-runtime 的自动压缩路径调的是 lane.compact(undefined, context)（session-manager.ts:1395）——从未传过这个参数。
补法
在压缩触发点传一段中文领域保留策略（节点 id、待用户确认态、已确认偏好、本轮关键工具结论）， 压缩后的摘要就会带上「必须跨压缩保留」的指令，而不是靠事后白名单告警。
边界
customInstructions 只能追加 focus，不能替换摘要骨架。vendor 的摘要模板是英文通用 Markdown （## Goal / ## Constraints & Preferences / ## Progress / ## Key Decisions / ## Next Steps / ## Critical Context，compaction.ts:420-455）， 为编码助手写的（结尾是「保留精确的文件路径、函数名、报错信息」）。中文生产会话压缩后变英文摘要，这是需要单独决策的产品问题， 不是 customInstructions 能解决的（要换骨架就得 fork vendor，触碰 D-γ' 红线）。
判断 5　per-task 推理预算走 before_request，但拿不到 temperature需分流
证据
before_request 的 event 带 step: "assistant" | "deferred" | "compaction" | "branch_summary" 与 attempt （agent-harness.ts:447-455），可以按任务阶段分流——但它的 result 只能 patch AgentHarnessStreamOptions： transport / timeoutMs / maxRetries / maxRetryDelayMs / headers / metadata / cacheRetention / deferred （types.ts:130-156）。这里面没有 temperature。
结论
「确定性输出走低温度」不能在 before_request 里做。temperature 归 Model（packages/ai/src/types.ts:185， 经 proxy.ts:63,106 透传），要做的是在 model-assembly 里按输出类型分两条 Model 分支， before_request 只负责按 step 调 timeout / 重试 / 缓存保留策略。两条路别混。

05方案 B：注入架构从「字符串拼装」升级到「按边界编排」

对应首轮 P1-2 / P2-1 / P2-2 / P2-3。现状是所有东西都往 system prompt 里塞（composeSystemPrompt 一个函数扛全部，session-manager.ts:1380-1386），本轮的建议是：把「每轮都会变」的东西从 system prompt 里挪出去，用 hook 在更合适的边界注入。

5.1 六个未用 hook 各自的归属

hook用它做什么对应首轮 / 约束
before_run注入任务级一次性指令：用户本轮已确认的偏好（「这批图统一横构图」）、或压缩后必须补回的上下文P2-1。transition-consumed：与 checkpoint 一起提交，不落历史、压缩不掉
before_run_end返回 followUp，在 run 收尾时注入一条用户轮做「重新落地」；也可用于把确定要问的问题变成一次续跑P2-1 的第二手段。transition-consumed：续跑与提交同生共死，中途崩会重来
after_response输出守卫：剥掉与工具轨迹矛盾的措辞（「我已经帮你生成好了」而实际没有 propose_generation）、归一 ⟦task-done⟧ 标记P1-2 的兜底层。必须保留 assistant role（harness.md:1204），且只在 abort 已起时能返回 aborted
before_request按 step 分派：compaction / branch_summary 摘要请求用更短的 timeout 与更少重试；assistant 主请求反过来P2-3 的一半（且是唯一能按阶段区分的地方）。不含 temperature，见判断 5
before_navigation分支回退后补 customInstructions，避免回到旧分支时丢掉领域约定P2-1 的分支变体。仅在会被摘要的导航触发；未摘要的导航不能 decline
before_tool除现有指标埋点外，加参数级护栏：未确认就调 run_* 直接 block 并返回理由P1-2。fail-closed：handler 抛错会拦下工具（harness.md:1201），护栏要自己 try/catch

5.2 顺序与生命周期是硬约束（照抄 vendor 契约，别自己发明）

  • transform_context 跑在 toProviderMessages 之前（harness.md:1192）——想改发给 provider 的最终形态，得挂在它之后或改用 toProviderMessages。
  • pass-local / request-local / transition-consumed 三档生命周期（harness.md:1203）。 需要「崩了也没关系、重跑一次」的（如输出守卫）放 request-local； 需要「必须留痕且不重放」的（如任务级注入）放 transition-consumed。放错档 = 生产上偶发行为不可复现。
  • before_run / before_compaction 不保证恰好一次：崩在提交前会重跑。任何外部副作用都要自己加幂等键（harness.md:1206）。
  • before_drive fail-closed：它抛错会拒绝整轮，别拿它做可选逻辑。

5.3 trust-boundary 的一个被忽略的口子

首轮 P2-2 限于「消息级标注 + 500 字符硬截断」。但 transform_context 的 result 类型是 { messages?: AgentMessage[]; systemPrompt?: string }（agent-harness.ts:445）—— systemPrompt 是可整体替换的。这意味着「目标复述」这段不必再受 500 字符硬截断点的限制， 可以在改写 messages 的同时把复述段一起重写成句边界完整、带修订语义的版本（「这是最新指令，取代同主题的前序要求」）， 两条首轮建议（句边界 + 修订语义）在同一个 hook 里一次做完，不用再改 trust-boundary 的截断逻辑。

06方案 C：结构化协议迁移（⟦plan⟧ → custom entry）

对应首轮 P1-3 的一部分，以及 P2-1 的「结构化状态跨压缩保留」。这是本轮唯一一处「不是改文案、是换实现」的建议。

6.1 现状的三个结构性代价

  • 占输出预算、且是文本协议。⟦plan⟧/⟦task-done⟧ 是夹在正文里的字符串， Nest 侧靠 stripPlanMarkers 剥掉再派生成 task 事件（agent.service.ts:806-812，测试里甚至有 ⟦plan⟧{oops 的容错分支， planMarkers.test.ts:27）——一个没有 schema 校验的文本协议。
  • 压不掉。它会进 transcript，被摘要覆盖；plan 的完成状态没有任何机制保存。这正是首轮 P2-1「压缩后信息丢失」的一个具体实例。
  • 无法承载结构化状态。「第 2 项待确认」只能靠模型每次重新输出 JSON 来表达，没有类型、没有版本、不可断言。

6.2 目标形态：custom entry + entryProjector

vendor 已经给了完整的两块：lane.appendCustomEntry(customType, data, ctx)（agent-harness.ts:544，落盘、 durable）与 EntryProjector = (entry, ctx) => AgentMessage[] | undefined（session/types.ts:58-62，把自定义条目投影成模型消息）。

// 1) run 开始时写一条自定义条目（durable，压缩不会删）
await lane.appendCustomEntry("plan", { items: [{n:1,title:"起稿"},{n:2,title:"配图"}] }, ctx);

// 2) harness 配置里声明它怎么变成模型消息（只投影需要给模型看的部分）
entryProjectors: {
  plan: (e) => [{ role: "user", content: `⟦plan⟧${JSON.stringify(e.data.items)}` }],
  task_done: (e) => [{ role: "user", content: `⟦task-done⟧${e.data.n}` }],
}

// 3)  wire 协议不变：Nest 仍从 assistant 文本里剥标记派事件，逐步收敛到读 entry
收益（对应首轮三条）：① plan 状态跨压缩存活（custom entry 落盘）；② 类型化，可被 eval 断言； ③ 标记行不再占每轮输出预算、也不再污染历史消息；④ 协议版本独立于提示词版本，可单独回滚。 风险：entryProjectors 是 harness 级配置，投影顺序会进 prompt，改动要同步看 attachEvents； 建议与 Nest 侧 stripPlanMarkers 双写至少一个版本周期，前端 task 事件一条都不改。

07迭代优化：eval 体系、在线观测、灰度

7.1 eval：复用 vendor，只写一层 adapter（首轮 P0-1 的降级实现）

三层，每层的成本与门槛不同：

  • L0 契约层（零 token，PR 必跑）。Registry schema、规则编号连续性、工具元信息（≤2 句 / summary 必填 / 单一语言）、prompt hash 稳定性。这段就是方案 A 的 CI，不消耗模型。
  • L1 行为回归集（≥30 条，离线，PR 必跑）。{ 用户话术, 画布初始态, 期望调用序列 }，混合硬断言与 LLM-judge。判据要可判定而不是「是否满意」——例如「是否调了 propose_generation 且未调 run_*」。
  • L2 对比表（evalHarnessTable，baseline vs candidate，repetitions ≥ 6）。这一层直接回答首轮 P0-2「改文案有没有变好」：vendor 会自动算 pass-rate lift 与 token/延迟/成本的配对差值（README.md:104-153）。judgeThreshold 按 vendor 建议设 null——正确性只观测、不卡闸，硬断言留给套件不变量（:136-138）。

要自己写的只有 adapter：createPiRuntimeHarness 参照 packages/evals/src/pi-harness.ts:246 的形态，但走 pi-runtime 的 /sessions + /prompt HTTP，而不是 coding-agent 的临时工程目录。前置条件：先解决 vitest-evals@0.15.0 与私有包 @earendil-works/pi-evals 的依赖（vendored 树里没装）。

首批 case 来源沿用首轮：线上三类真实失败样本（「只看到文件名」/「假称已出图」/ 模糊工具名），不要自造。

7.2 在线观测（首轮 P0-3）

  • pi_runtime_prompt_info{version,hash} gauge（复用 BuildInfo 写法）+ writeSessionMeta 落 promptVersion/promptHash，resume 时不一致要 warn。
  • load_tools / load_skill 触发率——这是 P1-4 唯一的判据。现在没有它，你无法判断「改了索引块有没有用」，所以这条要在动索引块之前就上线（见 §08 W2）。
  • 规则违反计数器（首轮 P0-2 建议的「反例是否真的被丢」的量化口）。
  • 工具 schema 估算 token gauge + 工具调用频次——P0-4 的「按频次裁剪常驻名单」需要它才有依据。

7.3 灰度（首轮 P2-5）

systemPrompt 已是函数形态（session-manager.ts:709），会话级 variant 注入天然支持；vendor 没有内置分流，按 userId 哈希自建即可。 硬前置：7.1 + 7.2 必须先落地，否则拿到指标也读不出是哪一版——这与首轮的劝阻一致，但门槛低了：有 evalHarnessTable 之后，大量判定可以在离线完成，在线灰度反而不是第一选择。

08落地路线图（本轮重点）

相对首轮的三个改动：① eval 提前（vendor 有基建，W1 就要有可跑的东西）；② 压缩保留提到 W2（一行参数，纯止血）；③ 规则重写仍压在 W4–W5，不提前——它是全项目风险最高的提示词变更，必须有 L1 回归集在旁边。
