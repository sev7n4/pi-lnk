# ADR-0015: 多端单会话——会话身份恒定（sessionId），重跑分支内部化，退役多对话 UI

| 字段 | 值 |
|---|---|
| 状态 | Accepted |
| 日期 | 2026-10-26 |
| 决策者 | 产品拍板（用户）：1 项目 = 1 画布 + 1 对话，只暴露 1 个对话；技术方案由多端一致性规格评审产出 |

## 背景

多端一致性规格（2026-10-21）落地复核发现：PC 与手机从未共享同一条对话——`createAgentThreadId` 由**前端**派生 `{sessionId}:{随机后缀}`，每端各生成一条独立线程（2026-08-07「对话隔离」设计的遗产），多端实时与续聊从未成立；单端 shared-subscription 的成功掩盖了这个盲点（伪解决）。

同时对照上游与行业（ADR-0009 能力优先纪律的延伸取证）：

- **上游 pi**：会话 = 单文件内树（entry `id`/`parentId`），`/tree` 同会话内切分支；`/fork`（新文件）只在显式需要分文件时用。
- **ChatGPT**：`conversation_id` 恒定 + mapping 树 + `current_node` 指针；编辑/重生成都是**同会话内**加兄弟分支 + 移指针，从不改会话身份——这正是多端单会话体验的来源。
- **Codex CLI**：编辑重发 = fork 出**新 ThreadId**（带 `forked_from_id`）——单机工具语义，照搬即为本仓已发生的跑偏。

根因归纳：threadId 承担了**双重职责**（pi 会话键 + 用户可见会话身份），且身份由前端生成、服务端从不拥有对话身份，产品 UI（历史面板/新建对话/切换）顺着底层建模长出了从未被要求的「多对话」形态。

## 考虑过的方案

| 方案 | 优点 | 缺点 | 为什么没选 |
|---|---|---|---|
| 维持 2026-08-07 隔离设计 + 服务端聚合归并读 | 不动前端身份生成 | 投影层要把 N 条设备线程聚合成「一个对话」：排序、身份、实时订阅键全要改造；「隔离聊天」从未是产品要求，纯为迁就旧实现 | 复杂度最高且服务于伪需求 |
| ChatGPT 全套 mapping 树 + current_node | 语义最完整，将来可扩展分支浏览 | 当前分支来源**只有重跑一个**；线性消息表 + 线性 UI 下是过度设计 | 等真有分支浏览需求再扩（活跃叶子模型可平滑升级为树） |
| Codex 式 fork = 新对话身份（跑偏现状） | 直接复用上游 forkSession 的键语义 | threadId 身份随 fork 漂移 ⇒ 多端发散的结构性根因 | 与产品目标（多端单会话）正面冲突 |
| **选定：sessionId 恒定 + 重跑分支内部化 + 服务端权威活跃叶子** | 会话身份零漂移；fork 继续吃满上游能力；多对话 UI 直接退役而非改造 | 存量历史须一次性 backfill；fork key 单端补丁与服务端指针存在双轨过渡期 | 复杂度净下降，且每个阶段可独立验收 |

## 决定

**用户可见的对话身份恒定 = `sessionId`（确定式、服务端可推导）；`threadId` 退为内部实现细节，只允许两个来源：共享线程（= `sessionId`）与服务端活跃叶子（重跑分支）。** 重跑分支一律走上游 `forkSession`（禁止自制 truncate）；「当前在哪条叶子」由服务端按 `updatedAt` 派生并随 bootstrap 下发；多对话 UI（历史面板/新建对话/切换对话）退役。产品形态：1 项目 = 1 画布 + 1 对话。

关键约束：J1–J5（见 [`specs/2026-10-26-unified-single-conversation-design.md`](../superpowers/specs/2026-10-26-unified-single-conversation-design.md) §4.1）；其中 **J5 为部署门禁**——legacy backfill 未跑不得把 bootstrap 收敛逻辑部署到生产（否则存量用户看到空对话）。

## 后果

**正面**：跨设备实时/续聊/重跑跟随全部成立且复杂度净下降（三维「多对话×分支×多端」坍缩为单对话）；上游 forkSession 能力被完整消费（不造轮子）；多对话 UI、每端随机线程、localStorage 真相源等历史包袱成批退役。

**负面 / 代价** ❗：① 存量用户的对话历史都在旧随机线程里，必须做一次性幂等 backfill 才能部署（J5），backfill 有数据风险需先备份演练；② 过渡期存在 fork key（客户端）与服务端活跃叶子双轨，两套状态有短暂不一致窗口；③ 「每项目多对话」被产品层面放弃，将来反悔需重新设计 UI 与产品语义（技术模型可扩展为树，但成本不低）；④ 观察端订阅键在 fork 后仍会指向死 lane，会话级广播（T3）落地前跨设备重跑跟随不成立（已知限制，已写入规格 §10.3 S2）。

**将来要注意**：① 产品若要恢复多对话/分支浏览/对话重命名，须重开规格并重评本 ADR（活跃叶子 → 树是自然扩展点）；② 部署上多实例时，会话级事件源（进程内 pubsub）需改进程间方案，届时重评；③ 若上游 pi 未来提供「原地截断/重生成」端点，可替代 forkSession 路径，届时重评 J3。
