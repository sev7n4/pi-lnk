# ADR-0008: 283 份历史文档只建索引，不改正文

| 字段 | 值 |
|---|---|
| 状态 | Accepted |
| 日期 | 2026-10-03 |
| 决策者 | 项目发起人 |

## 背景

`docs/superpowers/` 下积累了 **283 份 spec/plan**（137 specs + 146 plans，5.7M），
**无索引平铺**，看起来"全都还活着"。问题：

- 分不清哪份还有效、哪份已成历史
- 找不到相关主题的文档，只能靠文件名猜
- 于是倾向于"全留着"，越积越多

## 考虑过的方案

| 方案 | 优点 | 缺点 | 为什么没选 |
|---|---|---|---|
| 给每份文档开头插统一状态字段 | 机器可读、CI 可校验 | 改动 283 个文件，diff 失控；且要逐份判定 | ❌ |
| **建索引表，文档正文零改动**（选中） | 改动面= 1 个新文件；可随时重跑 | 状态在索引里，文档本体看不到 | ✅ |
| 按月份删历史 | 目录立刻变小 | **决策追溯价值丢失**（"当初为什么这么定"） | ❌ |
| 按月份归档 | 保留但挪走 | 挪走 = 删的另一种形式，同样丢检索 | ❌ |

## 决定

1. **正文不动，只建索引**：`docs/superpowers/INDEX.md`，按主题 + 状态分组。
2. **状态三态**：
   - `🟢 living` —— 仍在演进，**改代码前先看这份**
   - `🔒 frozen` —— 已定稿或功能已落地，作为历史依据
   - `⛔ superseded` —— 已被取代，**勿再参考**
3. **判定依据可复现**：`gen_index.py` 读文档开头的状态字段（最高优先级），
   否则按月份 + 主题推断。规则写在索引文末。
4. **判定错了的修法**：改文档开头的状态字段，重跑脚本 —— 不在索引里手工涂改。
5. **可重跑**：新增文档后重跑 `gen_index.py && gen_index_md.py`。
6. **文档状态字段的推荐写法**（写进 [`docs/agent/docs.md`](../agent/docs.md)「文档管理规范」）：
   `**状态：** 已实现（YYYY-MM-DD）` —— 机器可识别，下次重跑自动采信。

## 后果

**正面**
- 改动面只有 1 个新文件 + 2 个脚本，review 成本极低
- 283 份文档的现状一眼看清
- 判定规则公开可查，不是"我觉得它过期了"
- 以后加文档只需重跑，不用手工维护

**负面 / 代价** ❗
- **状态在索引里，文档本体看不到** —— 单独打开一份文档时不知道它是否 frozen
  （缓解：靠推荐的状态字段写法，下次重跑就会被采信）
- 判定是**规则化**的，不等于逐份人工确认 —— 可能有误判（已抽查 vision/memory/
  context-engineering/prompt-registry 等关键主题，准确）
- 索引会与实际状态漂移，需要养成"加文档后重跑"的习惯

**将来要注意**
- 规则化判定对"两个月的文档"最准，越老越粗 —— 7-8 月一律 frozen 是简化处理
- 若将来文档数超过 500，索引本身需要分片

## 关联

- 索引：`docs/superpowers/INDEX.md`
- 脚本：`gen_index.py`（判定）、`gen_index_md.py`（生成）
- 规范：[`docs/agent/docs.md`](../agent/docs.md)「文档管理规范」、`docs/README.md`
- 配套：ADR-0002（哪些资产不能删）
