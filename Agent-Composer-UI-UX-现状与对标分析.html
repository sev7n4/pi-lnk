Agent Composer 的 UI/UX 现状与对标分析

对标：Muse · Dots · WorkBuddy 小程序 代码基线 master e6116e10 2026-10-15

一句话结论：lnk π 的 composer 在「功能完备度」上已经领先同级产品——插话队列、引用芯片、画布选点、双层 mention 高亮这些能力，WorkBuddy 小程序没有，Muse 也没有。 但它缺的是「少即是多」的取舍：一个 420–760px 的面板里塞了最多 9 个同级可交互控件，首屏空态只有两行灰字，提示文案的对比度只有 2.59:1， 并且它整体没有接入本项目的设计体系（157 处 --neo-* vs 43 处 --lnk-*）。 对比 Muse / Dots / WorkBuddy 小程序三家，差距不在能力，在「分层、克制、可被看见」这三件事上。

01七个结论

按「离用户最近」排序，每条都在下面第 3 节给出代码证据。

键盘契约自相矛盾占位符写着「Cmd/Ctrl + Enter 发送」，而输入框实际是 submit-on-enter——回车就发。移动端软键盘下这是直接误发。
提示文字被令牌吞掉了--neo-text-muted 是 rgba 透明度色，实测浅色主题 2.59:1、深色 3.60:1，却专门用在 10px 的引导文案上。低于 AA，等于没有提示。
浅色主题下输入框是「重黑投影」输入 dock 的阴影硬编码 rgba(0,0,0,.42)/(.3)，只有深色一套、无浅色覆盖。这是 composer 里唯一没有被主题化的视觉量。
首屏空态等于零面板没有消息时只有两行灰字（「描述你的创意」+ 副标题）。没有样例、没有可点入口、没有人格。而样例能力已经存在于产品视觉技能分支里。
一行里 9 个同级控件，没有分层附件、模型、深度思考（开关+high/max）、技能、画布选点、麦克风、发送全在一行且视觉权重相近。WorkBuddy 小程序同一位置只有 4 个，Dots 是 1 个输入框加 0 个参数。
「生成中」是一段视觉空白发送键变方形停止块（这点做得好），但没有预估时长、没有进度、没有产物落点预览。Muse 有状态面板，Dots 有 Activity 面板。
设计体系对 composer 没有约束力墨流 Ink Flow 的 --lnk-* L1/L2/L3 体系覆盖不到 agent 面板；neowow-tokens.css 只反向引用 --lnk-* 6 次。任何主题/密度调整都要改两处。

03对标：三家产品的 composer 范式

三者代表三条互斥的路线。lnk π 目前哪一条都不是——它在做「全都要」。

Muse AI MIDI composer

路线：单入口 + 专家面板。主界面「只有一个输入框」，参数收进可开合的分区面板（生成组件 / 生成类型 / MIDI 控制 / 输出控制 / 状态 / 预估）。

  • 输入框下方左侧是模型下拉（明示在用哪个模型），右侧圆形生成键
  • 生成中再点即取消（与 lnk π 的方形停止块同构）
  • 过程以极简单色行呈现：Thought for 3 seconds / > Reading track: Lead
  • 产出用内联批注收口：+16 −0 + Undo / Keep 逐条 + Undo all / Keep all
  • HQ Mode 把「更慢但更好」做成显式选项，并标注 2× credits

Dots OpenAI 常驻 agent

路线：极简到反直觉。官方形态是「左边 agent 列表、右边活动串、底部一个输入框」。

  • 刻意不暴露模型选择与推理强度——就一个输入框。这是取舍，不是缺失
  • 单一持续会话，不鼓励按话题新建窗口（对应 lnk π 的「新建对话」按钮语义相反）
  • 信息挪到另一个平面：点 agent 头像才展开活动 / 输出 / 云电脑面板
  • 人格化通过可定制外观（形状、颜色、眼睛、配饰）建立，不靠首屏大字
  • 配套 Codex 的 Composer Predictions：输入框内灰字预测下一句，Tab 接受、可改再发

WorkBuddy 小程序 移动端

路线：形态随意图切换。截图给出的收缩态 / 伸展态是两个不同的交互模型，不是同一个输入框的两种宽度。

  • 收缩态：整条「按住说话」，左侧九宫格、右侧 +。语音是一等公民
  • 伸展态：文本行 + 一行 4 控件（语音 / 模型档位 Step-5-P…⌄ / + / 深色圆形发送）
  • 首屏：吉祥物 + 「WorkBuddy，我帮你」大字 + 4 条建议 chips + 「换一换」+ 顶部 banner
  • 底部 Tab 栏常驻（任务 / 定时任务 / 发现 / 我的）——输入条属于页面，不属于会话
  • 纯浅色单主题、大圆角、无边框白底卡片

矩阵读法

Muse 用分层消化复杂度，Dots 用转移平面（信息挪到头像面板）消化复杂度，WorkBuddy 小程序用形态切换消化复杂度。 三家都在做同一件事：让当前这一刻只需要一个决定。

lnk π 现在是把所有决定同时摊在 500px 宽的一行里——能力最全，认知成本也最高。

04差距清单

按「不修会不会伤到基本可用性」排序。每条给出代码证据与建议，不写无法落地的形容词。

P0 · 基本可用性与正确性

P0键盘契约自相矛盾：文案说 Cmd/Ctrl+Enter，行为是 Enter
现状
默认占位符由常量给出，明写「Cmd/Ctrl + Enter 发送」；同一控件在流式态的占位符又写「回车加入待发队列」。而 MentionInput 收到 submit-on-enter 后，裸 Enter 即发送（仅 Shift+Enter 换行）。
constants/agentSkillMap.ts:30 export const AGENT_INPUT_PLACEHOLDER_AUTO = '描述需求，@ 引用素材，Cmd/Ctrl + Enter 发送…' components/agent/AgentSideRail.vue:3385-3388 :placeholder="agent.isStreaming ? '输入消息，回车加入待发队列…' : inputPlaceholder" submit-on-enter components/canvas/MentionInput.vue:146-150 if (props.submitOnEnter) { if (e.shiftKey) return; e.preventDefault(); emit('submit') }
差距
同一个控件在两处给出不同的键盘契约，且二者都与真实行为不一致。桌面端用户按提示按 Cmd+Enter 会得到一次空提交或重复提交；移动端软键盘的回车键会直接发出未完成的句子。
对标
Muse / Dots / WorkBuddy 小程序三家都用「按钮发送」作为唯一确定路径，回车语义从不写进 placeholder。WorkBuddy 小程序干脆把它变成「按住说话」。
建议
统一为 Enter 发送 / Shift+Enter 换行（桌面），移动端 回车换行、只由按钮发送；placeholder 不再描述键盘，改为描述能做什么（Muse 的做法：Compose MIDI, explore theory, discover new ideas…）。
P0提示文字对比度 2.59:1 — 低于 AA，且用在 10px 上
现状
--neo-text-muted 是 rgba 透明度文字色，违反本项目设计令牌硬规则第 3 条（「文字色一律用实色 hex，禁止用 rgba 透明度当文字色」）。实测对比度：浅色主题 2.59:1、深色 3.60:1。而它恰好被用在 composer 最需要被读到的地方：10px 的引用提示、素材提示、回合摘要、输入占位符。
styles/neowow-tokens.css 深色:67 --neo-text-muted: rgba(244, 244, 248, 0.4); 浅色:225 --neo-text-muted: rgba(23, 25, 35, 0.42); 实测（WCAG 相对亮度公式，脚本见第 6 节） 浅色 合成 #949699 on #eef0f5 → 2.59:1 ✗ 浅色 合成 #9e9ea3 on #ffffff → 2.67:1 ✗ 深色 合成 #6d6d72 on #131318 → 3.60:1 ✗ 对照：--neo-text-secondary（同为 rgba）浅 5.02:1 / 深 7.02:1 ✓ --neo-accent-text 浅 #5b4ce6 = 5.09:1 / 深 #a89dff = 7.88:1 ✓ ⇒ 只有 muted 一档是坏的。
差距
10–11px 的字号本就处在可读性下沿，再叠加 2.6:1 的对比度，等于把「引导」和「状态」全部变成背景噪点。这也是本报告里唯一一条可以量化证明用户看不清的问题。
建议
把 --neo-text-muted 换成实色：浅色用 --lnk-ink-600 #5a6478（实测 5.22:1），深色用 --lnk-ink-400 #9aa3b2（实测 7.28:1）。同时把 10px 的引导文案提到 11.5px 并减少条数（见 P1-4）。
P0浅色主题下，输入 dock 用深色硬编码阴影
现状
输入 dock 的阴影是四层硬编码值，其中两层是纯黑大半径投影；:focus-within 把同一串值又抄了一遍，没有任何浅色主题覆盖。dock 的背景（--neo-glass-bg）本身是双主题成对定义的，唯独阴影不是。
AgentSideRail.vue:4169-4174（.agent-input-dock） box-shadow: 0 20px 44px rgba(0, 0, 0, 0.42), 0 2px 6px rgba(0, 0, 0, 0.3), inset 0 1px 0 rgb(var(--lnk-overlay-rgb) / 0.14), inset 0 -1px 0 rgba(0, 0, 0, 0.3); 全文件搜 .agent-input-dock：只在 4156/4177/4188/4198 定义， 无 [:root[data-theme='light']] 覆盖块（对照：.composer-canvas-pick-btn 在 4448 有覆盖）。
差距
浅色主题下面板底色是 #eef0f5，上面压一层 42% 纯黑 44px 半径的投影，观感是「浮起来的黑板」。深色主题里这是对的，浅色主题里它把整个 dock 的层级说反了——输入区看起来比消息区更高、更重。
建议
抽出 --neo-glass-shadow 并在深浅两块同名成对：深色保留现值的强度，浅色换成 0 8px 24px color-mix(in srgb, var(--lnk-ink-900), 12% transparent) 一类的轻投影。守卫侧：这是 design-token.test.ts 自然能覆盖的形状（成对性），补一条即可，不需要新机制。
P0触控目标 24/28px，移动端大面积低于 44pt
现状
发送 28px、语音 24px、面板图标按钮 28px、画布选点 28px、附件 32px。移动端全屏 sheet 里这些尺寸一个没变。
DockMicButton.vue:42-43 width:24px; height:24px DockGenerateButton.vue:59-60 width:28px; height:28px AgentSideRail.vue:4334-4335 .composer-canvas-pick-btn 28×28 AgentSideRail.vue:3738-3740 .agent-head-btn 28×28
差距
iOS HIG 44pt / Material 48dp 是下限而非建议。移动端「语音 + 发送」这两个最常点的目标只有 24 与 28，且相邻间距 8px——误触率会直接吃掉语音功能的可用性。
对标
WorkBuddy 小程序的发送键是明显 ≥44px 的深色圆形，语音占满整条。
建议
移动端把发送/语音提到 44px（视觉尺寸可保持 28，用透明扩边把命中区撑到 44），并在 useAgentMobileLayout 生效时给 dock 加一档 --composer-ctl-size 变量。桌面端可保持现状。

P1 · 体验高度

P1首屏空态等于零：有样例能力，没有样例入口
现状
无消息时只渲染两行 <p>。同文件的「产品视觉」技能分支里已经有一套 exampleUtterance 按钮组（label + 两行示例文案，点击即填充输入框）——能力已存在，只是没有推广到通用首屏。
AgentSideRail.vue:2826-2829（通用空态，全部内容） <div v-else-if="!agent.messages.length" class="agent-empty px-3 py-10 text-center"> <p class="text-sm">描述你的创意</p> <p class="mt-1 text-[11px] opacity-70">我会驱动画布创建节点、连线与生成任务</p> </div> AgentSideRail.vue:2809-2824（产品视觉分支才有样例按钮） PRODUCT_VISUAL_GUIDANCE.exampleUtterances → fillExampleUtterance(example.text)
差距
lnk π 的输入范式与普通 chat 不同：它的输出是画布上的一张图/一串节点，用户的第一句话必须同时指定「做什么」和「什么样的」——这是最难的第一句话。首屏两行灰字没有承担任何降低这层门槛的责任。对比 WorkBuddy 小程序的 4 条 chips + 「换一换」，差距不是美化程度，是有没有替用户开口。
建议
把 exampleUtterances 从技能分支提升为通用首屏能力，按「当前画布状态」动态选 4 条（空画布 / 有选中节点 / 有产物），每条点击后不是直接发送而是填充输入框（保留改写余地）。这正是 Muse 的「模板 → 专家面板」两步法的前端半部。
P1单行 9 控件，没有主次分层
现状
输入 dock 的参数区在同一行里并排：附件 +、模型选择器、深度思考开关（关/开 + high + max 共 3 个可点片段）、技能菜单；主行再放语音与发送。加上绝对定位悬在输入框左上角的画布选点球，与 ref 芯片条，一屏最多 9 个同级可交互元素。
AgentSideRail.vue:3416-3584 .agent-dock-params / .agent-dock-primary 附件(h-8 w-8=32) · UniversalModelSelector(ghost) · 深度思考开关组(3 片段) · 技能菜单 .agent-dock-primary: DockMicButton(24) · DockGenerateButton(28) AgentSideRail.vue:4334-4350 .composer-canvas-pick-btn 绝对定位 translate(-50%,-50%)
差距
三处具体问题：①「深度思考 开/关」+ 裸英文 high/max 是同一条连续光谱被切成三个按钮，术语未本地化也未设计；②模型选择器与技能菜单都能决定用哪个模型（技能里写着「平台路由，单张/图生图优先」），两个入口语义重叠；③画布选点球悬在输入框角上，仅 hover 才显示 tooltip（.composer-canvas-pick-tip），不 hover 时它是一个无法自解释的装饰球。而它其实是本项目最有价值的能力之一。
对标
Muse 把同类参数收进可开合的「专家面板」分 6 区；Dots 一个都不留；WorkBuddy 小程序留 4 个且模型折叠为一档 chip。
建议
按 A/B/C 三级分层（第 5 节给完整方案）：
A 级常驻（每轮都用）：附件、模型、发送；
B 级 chip 化（有值才占位）：技能、思考强度——把「深度思考 关」+ high + max 收成一个 思考·高 ⌄ 单 chip，点开才展开档位；
C 级抽屉：画布选点、语音、参数预设，收进输入框左侧的 + 菜单；画布选点同时保留一个更小的、在输入框内的 @ 提示入口。

P2 · 提升项

P2

输入预测（Composer Predictions）

Codex 已在输入框内用灰字预测下一句、Tab 接受、可改再发。本项目做这件事的上下文其实更足：有完整会话历史、有执行轨迹、有本轮 ref 芯片状态。冷启动成本高的输入框，最该有预测。

P2

语音从「点击开关」升级为「按住说话」

现在是一个 24px 的开关图标。.dock-mic-btn.is-listening 只有 1.2s 透明度脉冲作为反馈，没有录音时长、电平、可取消滑动。能力在，形态没给。

P2

死样式与尺寸口径未收敛

.agent-prompt-field 在 CSS 出现 2 次、模板 0 次，是一个死块；它的 min-height: 76px 与实际生效的 96px 冲突，说明输入框高度曾有两套口径。守卫 dead-styles.test.ts 目前只是 1 个选择器的棘轮，不覆盖这类漏删。

P2

mention 菜单缺少列表语义

@ 候选是一个 <ul> + mousedown 选词，没有 listbox / option 语义、没有 aria-activedescendant。键盘上下键能走（ArrowUp/Down 已实现），但屏幕阅读器无法播报当前项。

P2

技能菜单：1 个技能 + 「自动」

AGENT_SKILLS 当前只有 1 条（实物产品视觉出图）。一个下拉菜单承载 2 个选项，交互成本大于收益。建议降级为 ref 芯片旁的 chip，菜单保留给 ≥4 项时。

P2

术语与本地化

「深度思考 开/关」+ 裸英文 high / max 三个按钮；模型 chip 显示 Step-5-P…。中英混排在同一行、同一控件内，且 truncate 后无法辨认。需要一套统一的档位命名（如 思考·标准 / 思考·深入 / 思考·极限）。

06不建议动的部分

这次盘点也发现了明显高于对标产品的模块。改版时不要顺手抹平它们。

1 · 流式插话队列（queued bubble）

把「打断」拆成 steer（run 内下一个 turn 边界接住，事件流不断） 与 followUp（本轮收尾边界接住，人可以走开），并明确二者互斥、不做自动派发；四态（待发 / 未送达 / 已接住 / 已入队）+ 「取回内容」。 Muse 没有对等物，Dots 的「审查 / 追问 / 停止」也没到这个粒度。这是本项目 composer 里最成熟的一块，对标产品反而不如它。

2 · 双主题支持

三家对标产品都是单主题（Muse 深色、WorkBuddy 小程序浅色）。lnk π 有完整的深/浅成对令牌与守卫测试。这是结构性优势——要修的是 composer 没接进来，不是这套机制本身。

3 · 生成中把发送键换成方形停止块

代码注释里写得很清楚：clearer cancel affordance than a spinner-only control。Muse 的做法（同一个按钮再点即取消）本质相同。保持。

4 · 引用芯片（AgentRefStrip）与双层 mention 高亮

芯片可拖拽排序、可移除、可 @ 插入；mention 用同步滚动的 backdrop 层做染色高亮。WorkBuddy 小程序没有这个能力，Muse 也没有。问题是它没有被放在首屏可见的位置，需要的是「给位置」而不是「重做」。
