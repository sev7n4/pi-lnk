0. 本轮复核：对上一版结论的修正与加固

上一版结论是「一次 run 被 4 条流并发消费 → 事件切片被各自落库」。本轮按先证伪再采信重跑，结论在因果主链上成立，但有两处必须修正，且根因要再往下挖一层。

上一版说法复核结果修正
4 条消息各自带一个「事件窗口切片」 证实 已升级为数学实证：切片是完整回合事件序列的子序列（54/55、15/16 匹配），ts 起点晚于回合起点、终点与回合终点同一时刻。
切片导致「卡片被 unshift 到顶部」 修正 前端用的是 parts.push（turnTimeline.ts:345）。卡片之所以在最前面，是因为切片的首个事件就是孤儿 tool_result，此时 parts 为空，push 后即为 parts[0]——是「第一个落地」而非「被插队」。
根因 = 用户重复发送 降级为诱因 重复发送只是触发条件。真正的根因是系统缺少「回合身份」这一层抽象：回合 = 一次 HTTP 流（隐式），而上游权威的回合 = runId。缺了它，任何第二个订阅者（刷新页面、新标签页、recovery 排空）都会复制出一条独立回合。
一句话根因（v2）

我们把「一条 SSE 订阅」当成了「一个回合」，而上游 runId 这一等身份在归一化时被丢弃；于是同一 run 的多个订阅者各自持有一个按订阅起点切出来的残缺事件集，并各自落库成独立的助手消息。残缺集的首事件是孤儿 tool_result，被前端渲染成时间线第一项——即「提议生成卡片漂到思考之前」。

1. 证据链（四重取证交叉验证）

1.1 生产库：同正文 · 同秒 · 事件集是子序列

该线程在 1792069341707~710（3 毫秒内）落库 4 条 assistant 消息：

…jtdsd16tool_result{propose_generation}滞后 +1520s15/16
为什么正文一致而事件集不同？

正文累积走 text_delta（agent.service.ts:1428），集中发生在 run 的尾段——4 条流都活到了结尾，所以拿到同一份正文。事件累积走订阅窗口，起点各异，所以是残缺集。这一「一半全量、一半切片」的形态，正是缺陷的指纹：它不是「重复生成了 4 次」，而是同一次生成被记了 4 本账。

1.2 代码：409→steer 之后，流并没有终止

// apps/server/src/agent/agent.service.ts:1248-1279

语义错位：上游 steer 的含义是「把这句话并入正在跑的那个 run」（session-manager.ts:2084-2118，durable inbox）。但 Nest 这边，发起 steer 的这条 HTTP 流仍然把自己当作一个独立回合，继续旁听并在 agent_end 时落库。结果：1 个 run → N 条流 → N 条消息。

1.3 运行时：live 订阅 = 窗口切片（设计如此）

app.ts:436-437 的注释自陈：「agent.service.ts 的两处生产调用都传 { live: true } ⇒ 首连走 from=now」——即不重放、只收订阅之后的事件。这正是切片的生产机制。而 app.ts:429-443 也已经识别到 buffer 淘汰会造成「断头的流」，但刻意不回 409，只加了 droppedFromSeq 供观测——缺陷已知但未闭环。

2. 上游 pi-agent 能力盘点：哪些我们没吃满

关键前提：pi-runtime 已经在用上游能力（package.json 固定 @earendil-works/pi-agent-core@0.85.1，session-manager.ts 直接 import AgentHarness / AgentLane / JsonlSessionRepo）。所以这不是「没接上游」，而是接了但只用了六成。

上游已有能力上游出处我们缺口后果
runId / operationId：run 是一等身份，事件自带 lane.ts:667 {type:"run_start", runId: operationId}；restore.ts:137-161 从持久化恢复 operation 丢弃 NormalizedEvent 只有 type/lane/ts/seq/data（session-manager.ts:150-157），runId 在归一化时被丢掉（内部 turnBudget 用了 evt.runId，却没透传）。落库事件 PersistedExecutionEvent 同样无 runId。→ 回合失去主键，无法去重/归并。
steer / followUp：run 进行中输入的官方通道（durable inbox） lane.ts:145-173 steeringMode/followUpMode；session-manager.ts:2099-2118 半用 通道接了，但 Nest 在用它之后仍把本次 HTTP 流当新回合。且上游注释自陈：propose/ask_user 阻塞期连 checkpoint 边界都没有（session-manager.ts:2093-2096）→ steer 也要等到阻塞结束才被消费。
SessionRouter：托管 session + 多客户端 attachment（compute once, deliver many） server/src/session-router.ts:22-29, 62-72：HostedSession{attachments: Set<ClientAttachment>}、attachClient/detachClient 未用 我们在 Nest 层没有 fan-out 层：每个订阅者都被当成回合发起者。上游的模型里，detach 绝不等于 cancel。
transcript / entry_added / commit.seqs：可重放的持久化账本 runtime/transcript.ts:23-48；session/commit.ts；JsonlSessionRepo 未用 落库只依赖「订阅窗口」，不去 transcript 补全。上游的账本是权威 SSOT，我们的却是二手转述。
单一权威写者（设计公理） docs/mobile-handoff/01-delta/delta.md：「since there is exactly one authoritative writer」；lane.ts:386「the Drive continuation remains the sole top-level state writer」 违反 我们有 N 个写者（N 条流各自 finalizeTurn），且互相不知道对方存在。
LaneBusy：run 在跑时的显式拒绝 compaction-check.ts import LaneBusy；app.ts:211-215 → 409 已用 409 本身是对的，错的是 Nest 收到 409 之后的行为。

3. 架构缺陷分层诊断

A · 数据模型层 根

回合无身份。PersistedExecutionEvent = {type, data, seq, ts, messageIndex}——没有 runId、没有 streamId、没有完整性标记。seq 还是每条流各自从 1 开始的局部计数（agent.service.ts:1309），因此不同流的事件无法归并。回合边界因此退化为「一次 HTTP 连接的生命周期」。

B · 传输层 根

订阅即切片。生产一律 live:true（from=now），不重放；buffer 还会淘汰（droppedFromSeq）。没有「缺口标记」下发给消费方，消费方无从知道自己是残缺的。

C · 落库层 根

无单一写者。每条流独立 finalizeTurn，无 runId 幂等。上游公理被违反，直接产物就是 4 条同正文消息。

D · 渲染层 放大器

残缺被当完整。孤儿 tool_result 被 push 成 parts[0]；重放按 seq 保序 ⇒ 残缺顺序被固化进历史，刷新可复现。

E · 产品交互层 触发源

阻塞期零出口。propose_generation 阻塞最长 300s；等待态仅由 dock 状态行渲染（turnTimeline.test.ts:231），无确认卡；且上游 steer 在阻塞期也消费不到。用户唯一能做的动作就是重发——即触发本缺陷的唯一入口。

F · 门控层 帮凶

前端 isStreaming 是每页面内存态，刷新/新标签页即失效；幂等键 buildIdempotencyKey 每次带 Date.now()+random（streamRecovery.ts），对重复发送零防护。

因果链（从触发到表象）

E（阻塞期无出口）→ 用户重发 → prompt 撞 409 → Nest 转 steer 但流不终止（F 门控失效放行）→ B（live 订阅只收窗口内事件）→ A（无 runId 可归并）+ C（每条流各自落库）→ 残缺事件集入库 → D（孤儿 tool_result 成为 parts[0]）→ 卡片漂移，刷新后永久复现。

治理要义：只修 D 是治标（卡片不漂了，但库里仍是 4 本烂账）；只修 F 是转移（用户发不出去了，但刷新页面仍会复制回合）。必须先立 A（回合身份）+ C（单一写者）+ B（账本可补全），D/F/E 才有意义。

4. 行业反模式对照

生态共识（行业实践）我们具体表现
run 是资源：202 Accepted + Location: /v1/runs/{id}；客户端 attach/detach，detach 永不 cancel；流按 seq 可重放 违反 没有 run 资源概念，「开流」隐式等于「开回合」。
single-flight / brokered fan-out：一次计算、多路分发；行业数据显示 5–12% 的 LLM 调用由「刷新页面 / 切换设备」重复触发 违反 N 条流 = N 份账；上游 SessionRouter 的 attachment 模型本可直接提供 fan-out。
幂等键由内容确定性派生；「uuid/时间戳当幂等键比没有更糟，因为重试会生成新键」 违反 buildIdempotencyKey 含 Date.now()+random。
事件幂等且带稳定 item ID；重放是重建状态而非破坏状态 部分 tool_result 有 callId 兜底，但孤儿场景直接 push 新 part。
Never treat "stream closed" as "run finished"；重连拿不到完整重放时返回 gap marker + snapshot，UI 诚实重绘 违反 agent_end 即落库，无缺口概念；UI 把残缺当完整渲染。
「不要把流工具结果的断言提前」——只在工具真正返回后才声明结果 符合 本项无问题，列出以说明不是全盘否定。

5. 工程型方案

唯一架构原则

回合 = run（上游 runId），不是一次 HTTP 流。「计算一次、分发多路、单一写者、账本可补全」——这四条全部是上游已提供的语义，我们只需要在适配层停止与之对抗，而不是自研一套。

P0-1 · 补 runId 透传（pi-runtime，约 1 处改动，整条链的钥匙）

services/pi-runtime/src/session-manager.ts:150 给 NormalizedEvent 加 runId?: string；:2623 dispatch() 与 :1282 attachEvents() 在归一化时带上（上游事件本就有 runId，仅透传）。app.ts:420 的 SSE 帧无需改结构（已在 data 里）。

export interface NormalizedEvent {
  type: NormalizedEventType; lane?: string; ts: number; seq: number; data: unknown;
  runId?: string;  // ← 上游 run_start/run_end 及 in-run 事件本就携带，此前被丢弃
}

验收：新回合的 SSE 帧里 run_start 事件带 runId，且同回合后续所有事件 runId 一致。这是后面三条的前置。

P0-2 · 单一写者：只有 owner 流持账本（Nest）

apps/server/src/agent/agent.service.ts:1248-1279：prompt 的结果必须被 await 判定，而不是 fire-and-forget 后用 catch 兜底。

const accepted = await client.prompt(...).then(() => true).catch(e => e.status === 409 ? false : throw e)
const role = accepted ? 'owner' : 'shadow'      // 409 ⇒ 本流只是旁听者
if (!accepted) await client.steer(sessionKey, promptText, "main", { turnContext })
// … 事件照常转发给前端（UI 体验不变）…
if (role === 'owner') await this.finalizeTurn(...)  // ← 只有 owner 落库

为什么这是正解：与上游语义一致——steer 的含义就是「并入在跑的 run」，那么发起 steer 的连接自然不是一个新回合。同时 /pending 端点已在生产可用，shadow 流可据此立即给前端「已并入进行中的任务」的确定性反馈，而非静默旁听。

P0-3 · 落库以 runId 为幂等键（Nest + 数据模型）

PersistedExecutionEvent 增 runId；AgentMessage.metadata 增 runId / partial。finalizeTurn（:1556）落库前按 (threadId, runId) 查重：已存在则 UPDATE 事件集而非 INSERT。

价值：即使未来出现未预料的第二写者（recovery 排空、多标签页），也不可能再产生重复消息——从「靠约定保证唯一」升级为「靠主键保证唯一」。这是把 P0-2 的契约固化进数据模型。

P0-4 · 账本可补全：落库前用 transcript 补齐全量（根治切片）

owner 流在 agent_end 后、finalizeTurn 前，用订阅起点 lastEventId 向 pi-runtime 拉该 runId 的完整事件（pi-runtime 已有 subscribe(afterSeq) 重放 + isReplayComplete 判据，session-manager.ts:171-176），替代「只用自己窗口内的事件」。

  • 重放完整 ⇒ 落库全量账本，历史渲染与实时渲染一致；
  • 重放不完整（buffer 已淘汰）⇒ 落库带 partial:true + gapFrom，前端按缺口渲染（见 P1-2）。不假装有全量。

这一步是「治本」的关键：它让账本来源从「二手转述（订阅窗口）」回到「一手账本（上游 transcript/事件日志）」，切片问题从根上消失，而不只是不再重复。

P1-1 · 阻塞期给出口（消除触发源）

把 propose_generation 的等待语义对齐 ask_user 已有的交互形态：等待期前端出确认卡（复用 pendingAskUser 交互位 + waiting_user{nodeId} 已下发的定位信息），用户点「确认 / 取消 / 改需求」→ 走已存在的 /answers（decision: decline 或 answers）。上游 PendingToolRegistry 已支持 answered/timeout/aborted 三态与 resolve 不 reject 的铁律（pending-registry.ts:13-17），无需改上游。

顺带修掉一个更深的坑：上游注释已指出阻塞期没有 checkpoint 边界 ⇒ steer 也要等到阻塞结束（session-manager.ts:2093-2096）。所以「用户插话」在阻塞期只能靠 /answers，不能靠 steer。这一点必须在前端交互上体现，否则会出现「提示已收到但迟迟不动」的二次失信。

P1-2 · 前端诚实降级（渲染层）

  • 孤儿 tool_result 且时间线无前置 → 渲染为「本轮前半段事件未捕获」的 notice，而不是一个「已完成」的工具行（turnTimeline.ts:345）。
  • partial:true 的回合在历史渲染时顶部标注，不假装完整。
  • 发送门控改为服务端权威：发送前探 thread 活跃 run（可用 /pending + 新增轻量 state），取代纯内存 isStreaming。

P1-3 · 幂等键改为内容派生

buildIdempotencyKey（streamRecovery.ts）改为 hash(threadId + 消息正文 + 附件指纹) + 短 TTL，同内容重复提交命中缓存，直接返回「已并入进行中的回合」。

P2 · 观测（让同类缺陷自己冒出来）

四个计数器：shadow_stream_count（409 后仍开流的次数）、duplicate_turn_persist（同 runId 二次落库尝试）、orphan_tool_result（孤儿结果数）、replay_gap（重放不完整次数）。前两个应恒为 0，非 0 即回归。

明确不做的事（避免重复造轮子）

① 不自研事件总线/去重框架——用上游 runId + 现有 SSE id 帧；② 不自研 fan-out broker——P0-2/3 已达成「计算一次、单一写者」，无需引入 Redis Streams；③ 不改上游 vendor 源码（VENDORED.md 纪律：只读镜像，适配上推 L2）；④ 不靠前端判断去重——前端只做降级呈现，唯一性由数据模型保证。
