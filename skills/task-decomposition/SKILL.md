# 任务拆解与清单维护规范（task-decomposition）

## 何时使用

用户意图命中以下任一形态，先加载本 skill 再动手：

- 一句话里含多个子目标或先后依赖（「先 A 再 B 最后 C」「分析…然后…创作…」）
- 明确要「方案」「规划」「步骤」「任务清单」「todo」「一步步做」「先做啥」
- 任务规模明显需要跨多轮执行与进度跟踪

**不适用**：单步原子任务直接做——建清单或提案反而是形式主义（清单只放 1 项还配
一段方案说明，是已知反模式）。

## 判定：拆还是不拆

1. ≥3 个可独立核验的子目标 → 拆：先 propose_plan 提案，用户确认后落清单执行。
2. 1–2 步且顺序天然 → 可直接做，不建清单。
3. 用户明确说「直接做 / 别问了」→ 跳过提案，直接建清单执行。

## 拆解纪律（每条都可被 eval 判据检验，违反会挂红）

1. **先收集再执行**：清单首步必须是检索 / 读取 / 澄清类动作。信息不足时拆出的
   步骤全是猜测——结论性步骤不得写在收集之前。
2. **粒度与规模**：每项 = 一个可独立验收的产出。清单以 2–4 项为宜、至多 6 项；
   各项互斥不重复；禁止「整体做完」类巨石项，也禁止把一个动作拆成三个微步骤。
3. **方案先行**：多步任务先 propose_plan（步骤与后续清单保持同一结构），确认后
   用 todo_write 逐项执行；执行中发现方案变化，两者一起更新。
4. **全量覆写**：todo_write 每次提交完整清单（漏发历史项等同删除）；任意时刻
   至多一项 in_progress。
5. **带 id 增量维护**：变更已有任务带上其 id（content 可改写=重命名，身份不变），
   新增任务省略 id。引用不存在的 id 会被工具硬拒绝并附当前合法 id 清单——按回执
   改对后重发即可，不要因此放弃清单维护。
6. **不谎报完成**：一项做完且有证据支持才标 completed；未完成不许标 completed；
   全部完成后提交空数组清空清单。生成类任务收尾时在该项写
   `acceptance:{kind:"generation"}`（要求确认生成成功时加
   `generation:{requireSucceeded:true}`）——证据不足会被工具拒绝并附证据差，
   按回执继续干活或如实降级，不要因此放弃清单维护。
   画布类任务收尾写 `acceptance:{kind:"canvas_state",canvasState:{nodeCount:{min:1}}}`
   （按类型数节点用 `nodeTypeCounts:{image:{min:1}}`）——工具读回画布快照核对，
   证据不足同样会被工具拒绝并附证据差。⚠️ 只有批量建节点接口建的节点会被读到，
   分镜 shot 类节点不计入，别据此谎报完成。
7. **大调研可派发**：独立性强的大规模调研（多源搜集、逐项深挖）可派发子代理并行；
   派发前先建好清单占位，派发后由主会话整合结果再更新清单。
