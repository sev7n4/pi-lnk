0. 最关键的结构事实：存在三条互不相交的「文本生成」链路

在分析任何「文本生成」问题前必须先澄清——本仓的「文本生成」实际上是三条独立链路，它们入口不同、prompt 组装不同、产物落点不同、额外处理也不同。把它们混为一谈是诊断文本侧问题的头号陷阱。

链路入口走 PiPromptAssembler？走 prompt-modes？产物落点额外处理成熟度
A. Agent 对话流 用户在画布侧边栏打字 → POST /api/agent/chat/conversation（SSE）→ pi-runtime → 模型 是 静态规则 + 动态世界状态 否 模型若决定给节点生成文案，会调 run_text_generation 工具 → 落到链路 B 成熟（鉴权/幂等/心跳/孤儿锁已修）
B. Studio 直生成（text） ① 模型调 run_text_generation 工具 → Nest /agent/internal/run-text-generation；② 用户在画布点「生成」按钮 → useNodeGeneration → studioApi.generateText 否 裸 LLM 调用 否 update_node{content} + GenerationRecord(type:'text') 半成品（零重试/占位假成功/悬空扣费）
B′. Studio 提示词生成（prompt） 模型调 run_prompt_generation 工具；或 turnaround 图片管线扩写 否 是 classify → mode 专属 system update_node{content, promptMode} + GenerationRecord(type:'prompt') 中等（有分类/overlay，但仍走链路 B 的扣费/超时模式）
结构性断点（本次诊断最重要发现）：Agent 对话流（链路 A）把完整的世界状态（画布摘要 / 侧栏素材 / 用户选中指代 / 长期记忆 / 侧栏识图结果）注入 system prompt，模型据此决策调用 run_text_generation。但工具一旦落到 studio.generateText（链路 B），这些上下文被全部丢弃——工具只拿到节点自身的 prompt + refs 裸调 LLM。即「决策有上下文、执行无上下文」。详见 §5。

3. 额外处理逻辑清单（本报告核心）

这是本次诊断的最核心部分。文本生成链路上的每项额外处理逐项落实，并标注「有/无」与位置。文本 vs 图片的修复进度差异是主要发现。

3.1 超时

文本有超时，但来自 upstreamFetch 通用 45s，无文本专属 env、无 TS 消费点。
  • text-provider.ts:65 OpenAITextProvider.generate() 调 upstreamFetch(baseUrl/chat/completions, ...)，未传 timeoutMs → 用默认 UPSTREAM_FETCH_TIMEOUT_MS = 45_000（upstream-fetch.ts:23）
  • upstream-fetch.ts 注释的「最坏 3*45+4.5=139.5s < LNKPI_IMAGE_GEN_TIMEOUT_SEC=180」只对图片成立（图片裹 withUpstreamRetry 3 次）；文本不重试，最坏就是单次 45s
  • git grep LNKPI_TEXT 全仓零命中 → 文本没有任何专属超时环境变量
  • git grep LNKPI_IMAGE_GEN_TIMEOUT_SEC 只命中注释和测试 → 生产已设但 TS 零消费（印证 MEMORY）
超时后行为：抛 UpstreamTimeoutError（文案含 ASCII timeout，upstream-fetch.ts:42-46），冒泡到 generateText catch 走失败退款。不会挂起（#271 修法对文本也生效）。

3.2 重试

文本零重试——是四类生成里唯一无重试的。
  • upstream-retry.ts:60-79 withUpstreamRetry 默认 attempts=3、baseDelayMs=1500、退避 base * 2^i（1500/3000/6000）
  • 可重试判定 isRetryableUpstreamError：429 / 5xx / fetch failed / timed out / ECONNRESET；NON_RETRYABLE 优先（402/403/content_policy/已取消）
  • 关键纪律：!res.ok 必须显式 throw，否则 fetch 对 4xx/5xx 正常返回、重试永不触发（upstream-retry.ts:18 注释明示「最容易做错的一处」）
  • image-provider.ts:96-103 / :130-137 图片在 async_task + sync 两分支都把 upstreamFetch 包进 withUpstreamRetry
  • text-provider.ts:67 文本直调 upstreamFetch，无 withUpstreamRetry 包裹
  • 视频：upstream-retry.ts:104 withVideoRetry = withUpstreamRetry 别名
生产影响：上游 429 抖动时，图片会自动退避重试 3 次，文本直接判失败退款 → 文本侧最直接的韧性缺口。

3.3 降级 / 占位

文本有 PlaceholderTextProvider 占位（与图片同病：仅图片+文本保留，视频#166/音频#165已下线）。
  • text-provider.ts:34-43 PlaceholderTextProvider 返回硬编码「【AI 创作草案】…（配置 OPENAI_API_KEY 后可获得真实 LLM 输出）」
  • text-provider.ts:80-88 createTextProvider()：无 apiKey 且无 OPENAI_API_KEY 时返回 new PlaceholderTextProvider()
  • 这意味着无凭据场景下文本静默返回占位草案并被标 completed——与图片 PlaceholderImageProvider（image-provider.ts:23/:200）同构，是「假成功」文本版
  • 对照：video-provider.ts:486 注释「2026-10-04 已下线 PlaceholderVideoProvider，返回明确错误」；音频 PlaceholderAudioProvider master 全仓零命中
BYOK 失败兜底：studio.service.ts:816-830 不退占位，写 status='fallback_pending' 等用户点平台重试（与图片 studio:1276 同构）。

3.4 reaper（在飞任务清理）

文本没有 reaper 覆盖，且 reaper 只收 image。
  • generation-reaper.service.ts:57-84 GenerationReaperService 实现 OnModuleInit/OnModuleDestroy，启动后 15s 首扫 + 每 5min 周期巡检（非 @Cron，用 setInterval，全仓 git grep @Cron 零命中）
  • 明确只收 image：where: { type: 'image', status: 'generating', createdAt: { lt: cutoff } }，注释明示「video/audio 走各自编排层超时，不在此越界」
  • 阈值 DEFAULT_REAP_MINUTES=30（可由 LNKPI_GENERATION_REAP_MINUTES 覆盖）；事务内 updateMany 守卫 + 退款，exactly-once
文本侧 reaper 盲区：文本同步执行，正常路径不产生 generating 孤儿；但若进程在 consume（studio:711）之后、generateTextForRefs（:752）期间崩溃 → 已扣费、零 record、零退款的悬空扣费，reaper 按 type:'image',status:'generating' 查 GenerationRecord 根本扫不到。这类泄漏在文本侧没有任何兜底机制。

3.5 计费与账本

文本账本不对（generationId:null）——图片已修，文本/视频/音频仍停在旧模式。
  • 文本：studio.service.ts:707-712 cost=5，consume(consumeMeta('text', { model, generationId: null })) — 扣费时 record 还没建
  • 图片：studio.service.ts:1143 先建 record（generating）→ :1175 consume 带 generationId: record.id（B2 已修，注释「账本对账 B2」）
  • 视频 studio:2145、音频 studio:2293 同样 generationId:null（账本不对）
  • 退款三处：cancelled（studio:763）/ 平台失败 failed_refund（:789）/ BYOK byok_refund（:821），均 generationId:null
  • 退款幂等守卫：charge-session.ts:20-22 alreadyRefunded(meta) 看 refundedPoints>0
影响：扣费 tx 与生成 record 无法用 generationId 直接 JOIN，对账只能靠 metadata.chargedPoints/refundedPoints（印证 MEMORY「退款对、账本不对」）。

6. 问题诊断（按严重度排序）

P0 · 严重

① 文本零重试韧性缺口
text-provider.ts:67 直调 upstreamFetch，未包 withUpstreamRetry。上游 429 抖动时图片自动退避 3 次，文本直接判失败退款。文本是四类生成里唯一无重试的。
② PlaceholderTextProvider 假成功
text-provider.ts:34/:88 无 OPENAI_API_KEY 时静默返回硬编码草案并被标 completed。与图片 PlaceholderImageProvider 同病，是「假成功」文本版。视频#166/音频#165 已下线占位，文本+图片是仅存遗漏。
③ 悬空扣费无 reaper 兜底
进程在 consume（studio:711）之后、generateTextForRefs（:752）期间崩溃 → 已扣费、零 record、零退款。reaper（generation-reaper.service.ts:83）只查 type:'image',status:'generating'，文本无 generating record 可扫。这类泄漏在文本侧没有任何兜底。

P1 · 重要

④ 文本账本不对（generationId:null）
studio.service.ts:712 consume 时 record 未建 → generationId:null。图片已修（B2：先建 record 后扣费），文本/视频/音频仍停旧模式。扣费 tx 与生成 record 无法 JOIN，对账只能靠 metadata.chargedPoints/refundedPoints。
⑤ 结构性断点：工具执行丢弃世界状态
链路 A 把完整世界状态注入 system prompt，但 run_text_generation 落到 studio.generateText 时上下文被全部丢弃，只拿节点 prompt + refs 裸调 LLM。「决策有上下文、执行无上下文」——模型可能基于画布上下文决定生成某节点文案，但执行时 LLM 看不到画布状态，生成质量受限。
⑥ 生成调用无幂等键
重复 run_text_generation（网络重试/并发）会重复扣费、重复建 record。仅靠 gate V-γ 重试预算（同节点第3次拦截）+ SSOT status 兜底，非幂等键。文本生成是扣费+建 record 两步，缺幂等键意味着并发触发有重复扣费风险。
⑦ 无文本专属超时 env
git grep LNKPI_TEXT 零命中。文本只能复用 upstreamFetch 45s 常量；若需按业务调超时，无任何环境变量可调，只能改 UPSTREAM_FETCH_TIMEOUT_MS（会影响所有上游调用）。

P2 · 提示

⑧ conversation 入口无限流
controller 层无 throttle，只有 busy 409 串行守卫。恶意/异常高频对话无 rate limit 防护。
⑨ 规则段无运行时缓存
assembler:135 注释「有意每次重读目录」。每次请求 IO 读盘，虽 fail-soft 但有性能损耗（生产可观测性盲区，apps/server 无 prom-client/metrics）。
⑩ pi-runtime 端点无用户鉴权
靠 K3s 网络隔离 + AgentInternalGuard token 信任边界。若网络策略变化或 NodePort 暴露，存在信任越界风险。
